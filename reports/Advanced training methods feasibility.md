# Skip the exotic methods, prune and quantize instead

**None of the three methods can turn Granite 4.1 3B into a lighter, sharper .NET model on free T4s and a 15 W CPU. Next-Concept Modeling: skip. Nested Learning: replace it with a cheap approximation (LoRA, replay, and memory kept outside the weights). CompreSSM: skip.** Each one needs pretraining-scale compute, needs a new architecture that llama.cpp cannot run, or targets layers that Granite 4.1 3B does not have. The only published retrofits of concept prediction and of Nested Learning onto existing checkpoints used about **9.6B and 15B tokens** of continued pretraining on 8B models. Free Kaggle time yields roughly 10^8 tokens a week, so those recipes are about 100× out of reach. ConceptLM's retrofit gained only **+0.1 to +0.4 points** even at full scale. The working replacement is a well-proven pipeline:

1. Build an eval set from your own Eni-M repos.
2. Generate .NET data by distilling from Qwen2.5-Coder-14B (Apache 2.0) and filter it by compiling.
3. Fine-tune with QLoRA, mixing in about 5% general "replay" data.
4. Optionally drop 15–25% of the layers and retrain briefly to recover ("heal").
5. Quantize to GGUF using an importance matrix (imatrix) built from your domain.
6. Accept the model only if it passes KL-divergence, benchmark and speed checks.

All of it fits a T4 and ends in a standard GGUF file. None of the three methods changes the base-model choice. One related question is worth 30 minutes, though: **Granite 4.0-H Tiny** (7B mixture-of-experts, about 1B active parameters per token, Apache 2.0, vendor MBPP 80) could generate faster on your CPU than Granite 4.1 3B, which you measured at about 6 tok/s. It also costs about twice the RAM and loses llama-server's `--cache-reuse` prefix shifting, so run a CPU speed test before deciding. (Correction, 2026-11-02: it doesn't lose the shifting on llama.cpp build 11982; see the correction below.) Most code benchmarks cited here are vendor- or author-reported. The 2026 papers are mostly unreviewed preprints, some only days or weeks old.

## None of the three methods fits a 3B model, a T4 and llama.cpp

All three share the same disqualifying pattern. Each is either a new architecture trained from scratch or a retrofit that needs billions of tokens. None has a code-benchmark result, and none exports to GGUF. The table gives the verdicts. The evidence column rates how much the underlying claims can be trusted, which is separate from whether the method fits this project.

| Method | Verdict | Main reason | Evidence strength |
|---|---|---|---|
| Next-Concept Modeling / next-concept prediction | **Skip** | Needs a new model or 9.6B-token retrofit; no code results; no GGUF path | Weak: author-only preprints; NCM is weeks old |
| Nested Learning (Hope / CMS) | **Cheap approximation** | 15B-token retrofit recipe; no official code; weights must change during inference, which llama.cpp cannot do | Moderate venue (NeurIPS 2025), but author-only results, mostly in charts |
| CompreSSM | **Skip** | Built for training from scratch on small SSMs; Granite 4.1 3B has no SSM layers | Peer-reviewed (ICLR 2026), but only small LRU models on synthetic benchmarks |

### Next-Concept Modeling replaces the decoder; it does not improve one

The exact name refers to Stanford Hazy Research's October 2026 paper. It encodes text into a coarse-to-fine hierarchy of discrete codes and generates each level in parallel. It is pitched as a faster alternative to diffusion language models, with **self-reported 10–31× speedups** over those baselines ([arXiv 2610.14162](https://arxiv.org/abs/2610.14162); [Hazy blog](https://hazyresearch.stanford.edu/blog/2026-10-12-ncm)). It replaces the BPE tokenizer with its own VQ code hierarchy. Its released checkpoints are small task-specific models (97M–725M) evaluated on TinyStories, LM1B, OpenWebText, XSum, WMT14 and Sudoku, with no code tasks. Its repository documents evaluation only, with no fine-tuning path for existing LLMs ([GitHub HazyResearch/ncm](https://github.com/HazyResearch/ncm)). There is nothing in it to bolt onto Granite.

A separate family with a similar name, "next concept prediction" (NCP), does add concept layers to ordinary autoregressive models. The only retrofit of an existing checkpoint is ConceptLM on Llama-3.1-8B. It ran about **9.6B tokens on 8× H200 for 71–80 hours** and averaged **47.6 versus 47.5** for the same data trained without concepts ([arXiv 2602.08984](https://arxiv.org/html/2602.08984)). That is a gain within noise for compute you cannot get. The 8.9B NCP-ArchPreview model claims real gains, but only after full pretraining on 5.73T tokens ([arXiv 2609.10715](https://arxiv.org/abs/2609.10715)). CoCoMix trains its models from scratch on 20B–200B tokens and adds inference FLOPs ([arXiv 2502.08524](https://arxiv.org/html/2502.08524v1)). None of these papers reports HumanEval, MBPP or any other code benchmark. None integrates with Unsloth or PEFT, and their custom graphs (concept layers with vector quantization, interleaved concept vectors, multiscale decoding) would need new llama.cpp C++ code before they could run as GGUF.

The one cheap imitation is a "CoCoMix-lite" auxiliary loss. During LoRA training, a small linear head predicts a frozen teacher's pooled hidden state a few tokens ahead, and the head is thrown away at export. The model stays a standard architecture, so GGUF export still works. This is my own untested inference. At 10^7–10^8 tokens any gain is probably too small to measure against plain SFT, so treat it as a curiosity, not a pipeline step. Revisit concept prediction only if IBM, Qwen or Intern release a small NCP-pretrained open model. NCP-ArchPreview claims such models can adapt to a new domain by updating only a **17M-parameter VQ module**, which would make a genuinely cheap PEFT-like option ([arXiv 2609.10715](https://arxiv.org/abs/2609.10715)).

### Nested Learning's real feature is updating weights during inference, which llama.cpp cannot do

Nested Learning (Behrouz et al., Google, NeurIPS 2025) treats a model and its optimizer as nested learning problems that update at different rates. Its concrete product is the **Continuum Memory System** (CMS): MLP blocks that keep rewriting themselves at different rates, including during inference. Hope is a self-modifying model built on CMS ([Google Research blog](https://research.google/blog/introducing-nested-learning-a-new-ml-paradigm-for-continual-learning/); [arXiv 2512.24695](https://arxiv.org/abs/2512.24695v1)). The paper does describe a retrofit, "Ad-hoc Level Stacking," which initializes CMS levels from a pretrained model's MLPs. Its only demonstration used Llama-3 backbones with **15B tokens of continued pretraining** ([arXiv 2512.24695 §7.3, §9.1](https://arxiv.org/html/2512.24695v1)). Hope's from-scratch results are modest: at 1.3B parameters and 100B tokens it averages **58.04 versus 56.82 for Titans** ([arXiv 2512.24695 Table 2](https://arxiv.org/html/2512.24695v1)). Google itself calls Hope a "proof-of-concept." There is no official code. The only runnable reproduction is a **30.6M-parameter** community toy ([HF smallhours19/nested-learning-hope](https://huggingface.co/smallhours19/nested-learning-hope)). Inference also gets heavier, because the memory writes add compute and per-session state ([LessWrong analysis](https://www.lesswrong.com/posts/Lby4gMvKcLPoozHfg/are-we-in-a-continual-learning-overhang-1)). A Q4 GGUF also cannot be updated in place.

What you actually want from Nested Learning is "learn my domain without forgetting, and keep learning my preferences." Proven tools cover both. LoRA "learns less and forgets less" than full fine-tuning on code ([Biderman et al., TMLR 2024](https://mlanthology.org/tmlr/2024/biderman2024tmlr-lora)). About **5% general replay** prevented forgetting in a 1B model during domain training, and both less and more replay hurt ([EvoLM, arXiv 2506.16029](https://arxiv.org/pdf/2506.16029)). For preferences, the cheap equivalent of CMS's fast and slow levels is a preference file or retrieval injected into the prompt (fast), plus a periodic small LoRA refresh trained on accumulated preferences plus replay (slow). Keep the preference block in the stable prompt prefix so llama-server's cache absorbs its cost. Sparse memory finetuning forgets far less than LoRA (**11% versus 71%** drop on held-out QA) but needs a model with a memory layer, so it is also an architecture change ([arXiv 2510.15103](https://arxiv.org/abs/2510.15103v1)).

### CompreSSM compresses SSM state, which Granite 4.1 3B does not have

CompreSSM (Chahine, Nazari, Rus, Rusch; ICLR 2026) prunes the internal state dimensions of state-space-model (SSM) blocks early in training, using a control-theory technique called balanced truncation. It is validated on small LRU models on synthetic long-sequence benchmarks: for example, CIFAR10 went from **384 to about 93 states** while accuracy fell from **86.5% to 85.7%**. It reports no language-modeling results. Mamba-1 appears only as an appendix case study on IMDB classification, and Mamba-2 is listed as future work ([arXiv 2510.02823](https://arxiv.org/html/2510.02823v3); [ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/b57ec011a4a1c0c97fdc7ccebb672db4-Abstract-Conference.html)). The code is JAX, MIT-licensed and supports LRU only ([GitHub camail-official/compressm](https://github.com/camail-official/compressm)). **Granite 4.1 3B is a pure dense transformer** ([HF Granite 4.1 blog](https://huggingface.co/blog/ibm-granite/granite-4-1)), so CompreSSM does not apply to it at all.

The post-hoc follow-ups would apply to Granite 4.0-H. GHOST halves Mamba-2's state dimension using 128 calibration samples and no fine-tuning, at a cost of **+1.06 perplexity on Mamba2-1.3B** (13.17 → 14.23). LAMBADA, a recall-sensitive benchmark, drops sharply (65.55 → 51.76). GHOST also masks states rather than removing them, so it measured no speedup ([arXiv 2602.11408](https://arxiv.org/html/2602.11408)). A preprint posted two days before this research claims only +0.3 perplexity, with no code ([arXiv 2610.36617](https://arxiv.org/abs/2610.36617)). The payoff is small even if it works. In Granite 4.0-H Micro's config, the weights tied to state size are under 1% of each layer, and the recurrent state is about 75 MB per sequence ([config.json](https://huggingface.co/ibm-granite/granite-4.0-h-micro/raw/main/config.json)). By my arithmetic from that config (not measured), halving the state saves about 38 MB of RAM and at most a few percent of decode time. Quantization and active-parameter count matter far more. Code completion depends on exact recall of identifiers, which is the capability that degrades first, so this is a low-priority experiment even on a hybrid.

## A boring pipeline delivers the specialization and the slimming

The replacement plan uses only methods with published results, open tooling and a standard GGUF at the end. Each stage below has a gate. Any slimming step has to beat the plain quantized base on your own eval, or it is dropped.

| Stage | What to do | T4 / CPU feasibility | Must be measured |
|---|---|---|---|
| 0. Eval set | Mask spans for fill-in-the-middle (FIM) and regenerate methods from your Eni-M C# repos; check with `dotnet build` plus existing tests; 50–200 rubric-graded networking, system-design and security questions; MultiPL-E C# for comparison | CPU only | Baseline scores for every candidate base |
| 1. Data | Qwen2.5-Coder-14B-Instruct-AWQ on Kaggle generates instruction and FIM pairs seeded from your repos' training split and Microsoft Learn topics; keep only samples that compile | Fits a T4 (~4 GB of weights); throughput unmeasured | Tokens/hour; compile pass rate |
| 2. QLoRA SFT | Unsloth, fp16, rank 16–64, about 5% general code/instruct replay, FIM-format examples included | Easy (~3.5 GB minimum for 3B) | Repo-eval gain vs MultiPL-E C# loss |
| 3. Optional layer drop | Remove a contiguous 15–25% block chosen by Block Influence or C# validation loss; heal with QLoRA on teacher outputs | Feasible: scoring needs only forward passes | Quality loss vs speed gain on your eval |
| 4. Domain imatrix quantization | `llama-imatrix` on held-out-free C#/.NET text; Q4_K_M, Q4_0, IQ4_XS, IQ3_M | CPU, 30 min to hours | KL divergence vs F16 on held-out C# |
| 5. Gate and ship | `llama-perplexity --kl-divergence`, repo eval, `llama-bench` on the laptop; check the chat template | CPU | Pass/fail against the base |

### Your own repos are the quality bar, so the eval comes first

Building the benchmark only from your personal Eni-M repos is the right call, and keeping employer code out of it entirely is a hard rule, not a preference. Models do poorly on private code because its APIs and dependencies never appeared in pretraining ([Repoformer, ICML 2024](https://icml.cc/media/icml-2024/Slides/33155.pdf)). That gap is exactly what specialization should close. Two tasks capture "match or beat my code." The first masks method bodies or statement spans and scores the fill on exact match, edit similarity and, above all, whether `dotnet build` and the existing tests pass. The second regenerates a method from its signature, XML doc comment and surrounding file. It passes on the tests, and "beat" is ranked by Roslyn analyzer warnings or a noisy pairwise judge.

Your repos are public, so they may already be in Granite's or Qwen's pretraining data. Split by commit date, prefer code committed after each base model's data cutoff, and **never let eval files leak into SFT data, the imatrix text or teacher prompts**. Splitting by commit history follows the Long Code Arena method ([arXiv 2510.04349](https://arxiv.org/pdf/2510.04349)). Run MultiPL-E C# alongside your own eval as the forgetting alarm. Qwen2.5-Coder-1.5B-Instruct scores **64.6** there and the 3B scores **78.5** ([arXiv 2409.12186](https://arxiv.org/pdf/2409.12186)). No C# score exists for Granite 4.1 3B, so your first job is measuring it with the same harness.

### Distillation and QLoRA are cheap; healing a pruned model is the uncertain step

Sequence-level distillation means fine-tuning the student on the teacher's generated outputs. It fits the budget because the teacher only generates text and never sits in memory alongside the student. Qwen2.5-Coder-14B is Apache 2.0, while the 3B is not ([Qwen blog](https://qwenlm.github.io/blog/qwen2.5-coder-family)). On a T4, vLLM falls back to Triton attention, and validated dual-T4 coverage is narrow ([kaggle-vllm](https://pypi.org/project/kaggle-vllm/)). Measure throughput in the first session rather than trusting estimates. Logit-level distillation (training on the teacher's full probability distributions) needs teacher and student to share a tokenizer. Qwen to Qwen works, by precomputing top-k logits offline. **Qwen to Granite does not**, which is a real point in Qwen2.5-Coder-1.5B's favor if you later want logit distillation. A Granite 4.1 8B teacher (Apache 2.0, vendor HumanEval 85.4 ([HF](https://huggingface.co/ibm-granite/granite-4.1-8b))) might share the 3B's tokenizer. I have not verified that.

QLoRA itself is the low-risk step. Unsloth exports GGUF directly ([Unsloth: Saving to GGUF](https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-gguf)), and a T4 easily holds a 3B QLoRA run. Use fp16 on the T4, not bf16. A few thousand examples teach conventions and idioms (DI style, minimal APIs versus controllers, EF Core patterns, your naming), but they inject little new knowledge. For Qwen 2.5, never set the pad token to `<|endoftext|>`, or generation never stops ([Unsloth Qwen-Coder blog](https://unsloth.ai/blog/qwen-coder)). Unsloth's free notebook is confirmed for Granite-4.0-H, and Granite 4.1 3B has Unsloth GGUF builds ([unsloth/granite-4.1-3b-GGUF](https://huggingface.co/unsloth/granite-4.1-3b-GGUF)), but 4.1 *fine-tuning* on a T4 is only indirectly confirmed. Validate it in the first hour.

Layer dropping is the only shrinking step that beats quantization on speed and stays GGUF-native. Removing whole layers only changes `num_hidden_layers`, so the model remains a standard Granite or Qwen2 architecture. ShortGPT removed **10 of 40 layers** from LLaMA-2-13B and MMLU fell only from **55.0 to 52.2**, with no retraining ([arXiv 2403.03853](https://arxiv.org/html/2403.03853v3)). Code is more fragile than MMLU, though. Even with **94B distillation tokens**, Minitron's 50% prune of Llama 3.1 8B dropped MBPP from **42.3 to 30.7–32.4**. The depth-pruned version ran **about 2.7× faster**, and removing a contiguous block of layers beat removing scattered "unimportant" ones ([arXiv 2408.11796](https://arxiv.org/html/2408.11796)). You will have about 100× fewer healing tokens than that. Cap the cut at **15–25%**, heal on teacher outputs plus replay, and keep the pruned model only if it holds your repo-eval score. Granite 4.1 3B's 40 uniform dense layers make it an easy candidate for this ([HF Granite 4.1 blog](https://huggingface.co/blog/ibm-granite/granite-4-1)). Width pruning keeps more quality per parameter, but non-uniform per-layer widths may not fit a standard GGUF architecture. That is unverified.

### Quantization is the baseline every slimming trick must beat

A domain imatrix costs nothing but CPU time. Build it with `llama-imatrix` from the F16 GGUF on a diverse C#/.NET corpus that excludes eval items. Calibration quality and diversity matter more than quantity, and the payoff is largest at low bit-widths ([llm-gguf-tools imatrix docs](https://git.tomfos.tr/tom/llm-gguf-tools/src/branch/main/docs/imatrix_data.md)). Then compare Q4_K_M, Q4_0, IQ4_XS and IQ3_M with `llama-perplexity --kl-divergence` against F16 ([llama.cpp perplexity README](https://docs.rs/crate/llama-cpp-sys-4/0.4.4/source/llama.cpp/tools/perplexity/README.md)). No controlled study shows that a code-specific imatrix beats a generic one at 1–3B, so your measurement is the evidence.

The floor is set by evidence on a close neighbor. For Qwen2.5-Coder-3B, **Q4_K_M matched fp16 on HumanEval-Infilling (64.7% vs 64.4%) while Q2_K collapsed to 0%**, and the authors recommend Q8_0 below 3B ([arXiv 2605.04894](https://arxiv.org/pdf/2605.04894)). Treat Q4_K_M or Q4_0 as the default. IQ3_M is a candidate only if it passes your compile-and-test eval, and skip IQ2. Unsloth/TorchAO quantization-aware training (QAT) claims "up to 70%" accuracy recovery ([Unsloth QAT docs](https://unsloth.ai/docs/blog/quantization-aware-training-qat)), but it produces TorchAO INT4 checkpoints with no established path to GGUF K-quants, so it does not fit this pipeline.

## Granite 4.0-H Tiny earns a 30-minute CPU speed test

None of the three methods justifies switching base models. CompreSSM in particular is not a reason to adopt a hybrid. Two pipeline facts do bear on the choice, and one alternative deserves a speed test.

**Granite 4.0-H Tiny** is a 7B mixture-of-experts hybrid with about 1B active parameters per token, Apache 2.0. Its vendor scores are **HumanEval 83 and MBPP 80**, against 81 and 73 for the 3B H-Micro ([HF granite-4.0-h-micro card](https://huggingface.co/ibm-granite/granite-4.0-h-micro)). Granite 4.1 3B's vendor scores are HumanEval 81.7 and MBPP 71.2 ([HF](https://huggingface.co/ibm-granite/granite-4.1-8b)), but those come from a different release, so the comparison is only rough. On your CPU, Granite 4.1 3B Q4_K_M measured **about 30–35 tok/s prompt processing and 5.5–6.3 tok/s generation**, which works out to about 12–13 GB/s of a roughly 38 GB/s bandwidth ceiling. Generation is bandwidth-bound, and H-Tiny reads only about a third as many weights per token. So by estimate it could generate noticeably faster.

There are three reasons to doubt that. First, all 7B of weights must sit in RAM (about 4–4.5 GB at Q4) next to the IDE and the 1.5B autocomplete model. Second, IBM itself notes that llama.cpp's Mamba-2 support may not be fully optimized ([IBM Granite docs](https://www.ibm.com/granite/docs/models/granite)). The scan-kernel speedups found so far are for GPU, not CPU ([llama.cpp commit](https://app.semanticdiff.com/gh/ggerganov/llama.cpp/commit/793c0d7f46384001738c337d7afa46b45ae32745)). Third, **KV shifting does not work on hybrid Mamba models**, so `--cache-reuse` stops working. **Correction, 2026-11-02:** wrong on llama.cpp build 11982. Measured on H-Tiny, a history cut reused the cache with "shifting KV cache" in the log, 11 s instead of 228 s from scratch, because the shift check asks only the attention cache. See `reports/Local inference sources for Jazari.md`. llama-server's default prefix cache, which reuses only an identical leading prefix, still helps. Prompt processing is your bottleneck, and the prefix cache is your biggest saver, so a faster generator that processes prompts more slowly could be a net loss.

Run `llama-bench -m h-tiny-Q4_K_M.gguf,granite-4.1-3b-Q4_K_M.gguf -dev none -t 4 -tb 8 --poll 0 -p 512 -n 64 -r 5` and watch RAM. Switch only if H-Tiny matches or beats about 30 tok/s on pp512, clearly beats 6.3 tok/s on generation, and wins on your repo eval. Fine-tuning it on a T4 is plausible but unverified: the Unsloth notebook is for "Granite-4.0-H" without a confirmed size, and Unsloth's MoE-kernel claims cover Qwen3 ([Unsloth Notebooks](https://unsloth.ai/docs/get-started/unsloth-notebooks)).

The second fact concerns the lightest viable model. If "lightest" wins over "smartest," **Qwen2.5-Coder-1.5B** (Apache 2.0, trained for FIM, MultiPL-E C# 64.6) is the natural size floor. It is also the only candidate that supports logit distillation from an Apache teacher. Run it through the same eval. If a fine-tuned 1.5B matches your code on your repos, it beats a pruned 3B on simplicity.

On licensing, **Qwen2.5-Coder-3B stays excluded** for anything that might be rebranded, served or made public. It is under the Qwen Research License (non-commercial only), and that license requires "Built with Qwen" attribution if its outputs train a public model ([Qwen2.5-Coder-3B-Instruct LICENSE](https://huggingface.co/Qwen/Qwen2.5-Coder-3B-Instruct/blob/main/LICENSE)). Granite 4.x, Qwen2.5-Coder 1.5B/14B and the 14B teacher's outputs are all Apache 2.0. Hybrid alternatives carry their own caveats: LFM2's license terms vary by company size, and Falcon-H1's license is described inconsistently ([Falcon-H1 blog](https://falcon-lm.github.io/blog/falcon-h1/)).

## Many claims here are vendor numbers or unverified

All code benchmarks for Granite 4.x and Qwen2.5-Coder are vendor-reported, and they are not comparable across vendors or releases. The NCM speedups, the NCP-ArchPreview gains, Hope's results and the HARP +0.3 perplexity figure are all author-reported. HARP is a two-day-old preprint without code. GHOST's ICML 2026 acceptance comes from the authors' own blog ([Kyrillidis blog](https://akyrillidis.github.io/2026/05/08/ghost-mamba2-blog.html)). Unsloth's QAT recovery numbers are vendor figures.

The following are unverified and must be measured: Granite 4.1 3B fine-tuning in Unsloth on a T4; tokenizer sharing between Granite 4.1 3B and 8B; T4 throughput for the 14B AWQ teacher; ShortGPT's code retention, since its published numbers are MMLU and some came from search snippets; llama.cpp acceptance of non-uniform pruned widths or per-layer SSM state sizes; H-Tiny's CPU speed; and every CPU-gain figure for SSM state compression, which is arithmetic, not a benchmark. Your own laptop measurements (Granite 4.1 3B throughput and thread behavior) are the only hard numbers in the speed analysis.

## Conclusion

The three methods ask a different question from yours. They ask how to build or pretrain a better architecture. You need to know how to bend an existing checkpoint toward your code without breaking it. On free T4s and a 15 W CPU, that is a data-and-measurement problem, not an architecture problem. The bottleneck is not a training method. It is the eval set, because every slimming step (layer drop, IQ3, a smaller base) is only justified by a number from your own repos showing it still matches your code. Build that harness first, and most decisions in this report reduce to running it.

Specialization and slimming also pull in opposite directions at this scale. A pruned model needs healing tokens, and those come from the same small budget as domain training. So the likely winner is not the most compressed model. It is the smallest unpruned base (Granite 4.1 3B, or Qwen2.5-Coder-1.5B if it holds up) with good distilled data and a domain imatrix at Q4. Layer dropping is a second-round experiment, run once the baseline is known. Re-check the exotic methods only when one of them ships small open weights that llama.cpp can run.
