# Pick a 3B Apache coder, not 7B

**The best fit for this laptop is a 3–4B dense, non-thinking, Apache-licensed model, and the strongest single candidate is IBM Granite 4.1 3B.** It is Apache 2.0, ships Base and Instruct checkpoints, uses a standard dense architecture, and is one of only two current families with documented native fill-in-the-middle (FIM). One fine-tuned model can therefore cover both code chat and autocomplete. The fallback is a two-model setup with the best tooling evidence: **Qwen3-4B-Instruct-2507** (Apache 2.0, non-thinking, official free-T4 Unsloth notebook) for chat, plus **Qwen2.5-Coder-1.5B** (Apache 2.0, trained for FIM) as an autocomplete companion small enough to sit entirely on the 2 GB MX150. Size matters most because of how this CPU behaves. On an i7-8550U, a 7B Q4 model generates about **6 tok/s but processes prompts at only 13–16 tok/s**, so a 4,000-token file context takes about 4–5 minutes before the first output token. That rules out 7B+ models and thinking-mode models for interactive use, even though Qwen3.5-9B, Gemma 4 and JetBrains Mellum2.1 post much higher headline scores. Licensing removes the one 3B model that scores best on raw benchmarks: **Qwen2.5-Coder-3B is under the non-commercial Qwen Research License, not Apache 2.0**, unlike its 0.5/1.5/7/14/32B siblings. Almost every 2026 benchmark here is vendor-reported, and several claims (Granite 4.1 on Unsloth, Qwen3.5's linear attention in llama.cpp, Mellum2.1's numbers) still need a short validation run before you commit.

## Prompt processing, not generation, sets the size ceiling

This laptop has an i5/i7-8250U/8550U: 4 cores, 15 W, AVX2, dual-channel DDR4-2400 with a **37.5 GB/s theoretical memory bandwidth ceiling** ([Intel ARK](https://www.intel.com/content/www/us/en/products/sku/124967/intel-core-i58250u-processor-6m-cache-up-to-3-40-ghz/specifications.html)). The only direct measurement for this CPU class is a Yoga 730 with an i7-8550U and 16 GB, running a late-2025 llama.cpp build. A 7B Q4_0 model reached **pp512 16.3 tok/s and tg128 6.4 tok/s with 8 threads** (13.4 / 5.6 with 4 threads) ([mgroeber.de](https://www.mgroeber.de/benchmarking-llamacpp-on-legacy-hardware-2.html)). Generation is bandwidth-bound: each token reads the full dense weights, so speed scales roughly with bandwidth divided by file size ([llama.cpp #1437](https://github.com/ggml-org/llama.cpp/issues/1437)). Prompt processing is compute-bound, and on a 15 W quad-core it runs only 2–3× faster than generation. A coding assistant spends most of its time ingesting file context, so time-to-first-token is the deciding cost. It is also why thinking-mode models fail here: hundreds of reasoning tokens at about 6 tok/s add minutes to every answer.

The table below scales that one measured 7B data point by model size. Rows other than 7B are bandwidth-derived estimates from the research notes, not measurements on this CPU, and sustained speeds will be lower once the 15 W chassis throttles. The 4B row is my interpolation.

| Tier | Q4_K_M RAM incl. 4k ctx | Generation tok/s | Prompt tok/s | 4k-token prompt wait |
|---|---|---|---|---|
| 1.5B | ~1.5–2 GB | 15–22 (est.) | 60–100 (est.) | ~40–70 s |
| 3B | ~2.5–3 GB | 9–13 (est.) | 30–50 (est.) | ~1.5–2 min |
| 4B | ~3–3.5 GB | ~8–11 (interp.) | ~25–40 (interp.) | ~2–2.5 min |
| 7–8B | ~5.5–6.5 GB | **5.6–6.4 (measured, Q4_0)** | **13–16 (measured)** | **~4–5 min** |
| 12B-A2.5B MoE (Mellum2.1) | ~8.1 GB file + ctx | unmeasured; faster decode than dense 8B in theory | unmeasured | unknown |

The MX150 helps, but only for small models. A Pascal GPU beats this CPU on prompt processing by an order of magnitude: a GTX 1050 with a 7B fully offloaded did **pp512 207 tok/s versus 16 on the CPU** ([mgroeber.de](https://www.mgroeber.de/benchmarking-llamacpp-on-legacy-hardware-2.html)). The MX150's 2 GB is enough to hold a whole 1.5B Q4/Q8 model, or a 3B with a short context. One anecdote reports about 52 tok/s prompt processing on an MX150, a 5,632-token usable context, and **30–40% thermal throttling at about 80 °C** ([r/LocalLLaMA snapshot](https://reddit.sentinel-team.org/posts/1sbnf8y/snapshots/2026-04-03T21%3A20%3A24.375333Z)). Pascal support is ending: CUDA 13 drops it, so you must pin llama.cpp's Windows `cuda-12.4` build or Ollama's CUDA v12 runner (driver 570+). That claim comes from a secondary source that was not checked against llama.cpp's own releases ([localaimaster](https://localaimaster.com/blog/pascal-gpus-after-cuda-13)). The practical layout is to put the small FIM model on the GPU and the chat model on the CPU, so the two do not compete for the same resource.

Quantization does not change the size verdict. For Qwen2.5-Coder-3B, **Q4_K_M kept fp16 quality on HumanEval-Infilling (64.7% vs 64.4%)**, Q2_K dropped to 0%, and the authors recommend Q8_0 for models under 3B ([arXiv 2605.04894](https://arxiv.org/pdf/2605.04894)). So run the 3–4B chat model at Q4_K_M (try Q4_0, which llama.cpp repacks for faster CPU inference) and the 1.5B companion at Q8_0.

## Licensing removes Qwen2.5-Coder-3B and Llama from a rebranded API

Your requirements are to rename the model, serve it behind your own OpenAI-compatible endpoint with API keys, and possibly open it to others later. **Apache 2.0 and MIT are the only license families that allow all of this with no strings beyond keeping notices** ([Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0); [Phi-4 MIT LICENSE](https://huggingface.co/microsoft/phi-4/blob/main/LICENSE)). The Qwen2.5-Coder family looks uniformly permissive, but it is not. The 0.5B, 1.5B, 7B, 14B and 32B models are Apache 2.0, while **the 3B is under the Qwen Research License**, which limits use to "non-commercial purposes only." That license also requires "Built with Qwen" or "Improved using Qwen" if the model or its outputs train a publicly available model, and it is governed by Chinese law ([Qwen blog](https://qwenlm.github.io/blog/qwen2.5-coder-family); [Qwen2.5-Coder-3B-Instruct LICENSE](https://huggingface.co/Qwen/Qwen2.5-Coder-3B-Instruct/blob/main/LICENSE)). This matters because the 3B is otherwise very attractive. It beat Qwen2.5-Coder-7B on single-line FIM (64.7% vs 54.0%) ([arXiv 2605.04894](https://arxiv.org/pdf/2605.04894)) and scores HumanEval 84.1 as an instruct model ([arXiv 2409.12186](https://arxiv.org/html/2409.12186v3)). A strictly private hobby project could use it. A rebranded API that might ever earn money or go public should not be built on it.

The other families sort cleanly. **Llama fails the rebranding requirement outright**: every derivative name must start with "Llama", and you must display "Built with Llama" ([Llama 3.1 license](https://dev.meta.ai/llama/llama3_1/license); [Llama 4 LICENSE](https://github.com/meta-llama/llama-models/blob/main/models/llama4/LICENSE)). Gemma 1–3 treat API hosting as distribution, so your API terms must pass Google's prohibited-use policy on to your users ([Gemma Terms](https://ai.google.dev/gemma/terms)). **Gemma 4 moved to Apache 2.0** and avoids that ([Google Open Source Blog](https://opensource.googleblog.com/2026/03/gemma-4-expanding-the-gemmaverse-with-apache-20.html)). DeepSeek-Coder and StarCoder2 permit SaaS hosting but require their use restrictions to appear as enforceable terms in your API terms of service ([DeepSeek LICENSE-MODEL](https://github.com/deepseek-ai/DeepSeek-Coder-V2/blob/main/LICENSE-MODEL); [BigCode OpenRAIL-M](https://www.bigcode-project.org/docs/pages/bigcode-openrail/)). Codestral 22B is non-production only. Every finalist below is Apache 2.0: Granite 4.1 ([HF](https://huggingface.co/ibm-granite/granite-4.1-8b)), Qwen3-4B-Instruct-2507 ([HF](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)), Qwen2.5-Coder-1.5B/7B, Qwen3.5 ([HF](https://huggingface.co/Qwen/Qwen3.5-9B)), Gemma 4 and, per news coverage, Mellum2.1 ([NYU RITS](https://rits.shanghai.nyu.edu/ai/jetbrains-ships-mellum2-1-a-12b-open-model-for-coding-agents/)). Apache 2.0 grants no trademark rights, so pick a brand name that does not use "Qwen" or "Granite". State "fine-tuned from X (Apache 2.0)" in your model card, and keep the LICENSE and NOTICE files with any weights you share. One more trap: if you fine-tune on synthetic data generated by Llama or Gemma ≤3, those licenses' obligations can follow the data into your model.

## Granite 4.1 3B is the only small model that meets every requirement

The table compares the candidates. All coding scores are vendor-reported, and **scores from different vendors are not comparable**, because harnesses and LiveCodeBench windows differ (LCB ranges from about 18 to about 80 depending on window and thinking mode).

| **Qwen3-4B-Instruct-2507** | 4.0B dense, 262K, non-thinking | LCB v6 35.1, MultiPL-E 76.8, Aider-Polyglot 12.9 | No | Apache 2.0 | **Official free-T4 notebook** | **Good: 4B tier** |
| **Qwen2.5-Coder-1.5B** | 1.5B dense | Inst HE 70.7, LCB 6.1; FIM single-line 83.5 | **Yes** | Apache 2.0 | **Official free-T4 notebook** (tool calling) | Excellent; fits on MX150 |

Sources: Qwen2.5-Coder ([arXiv 2409.12186](https://arxiv.org/html/2409.12186v3)); Granite 4.1 ([HF](https://huggingface.co/ibm-granite/granite-4.1-8b)); Qwen3-4B-2507 ([HF](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)); Qwen3.5 ([HF](https://huggingface.co/Qwen/Qwen3.5-9B)); Gemma 4 ([model card](https://ai.google.dev/gemma/docs/core/model_card_4)); Phi-4-mini ([arXiv 2503.01743](https://arxiv.org/html/2503.01743)); notebooks ([Unsloth Notebooks](https://unsloth.ai/docs/get-started/unsloth-notebooks)).

**Granite 4.1 3B is the primary pick** because it alone combines four things: the fast 3B tier, Apache 2.0, a Base checkpoint for continued pretraining or FIM-format tuning, and **FIM listed as a native capability** ([HF model card](https://huggingface.co/ibm-granite/granite-4.1-8b)). Its HumanEval/MBPP scores (81.7/71.2) sit just below the license-blocked Qwen2.5-Coder-3B-Instruct (84.1/73.6). The 4.1 card describes a plain dense decoder (GQA, RoPE, SwiGLU, RMSNorm) with no Mamba or MoE layers. That is the architecture llama.cpp and Unsloth handle most routinely, unlike the hybrid Mamba Granite 4.0-H. With a single model, you fine-tune once, keep one GGUF in RAM, and serve both chat and completions from one endpoint. The weaknesses are real and need checking. There is **no independent benchmark** and no LiveCodeBench score for it. One roundup quotes an 8B HumanEval figure (87.2) that does not match the card (85.37) ([labellerr](https://www.labellerr.com/blog/best-small-language-models-under-10b-parameters/)). No FIM benchmark has been published for Granite 4.1. The architecture details above come from the 8B card, so the 3B card should be checked separately. Unsloth has a confirmed notebook only for Granite-4.0-H, not 4.1.

**The fallback is Qwen3-4B-Instruct-2507 for chat plus Qwen2.5-Coder-1.5B for FIM**, and every link in that chain is documented. Qwen3-4B-2507 is non-thinking by design, which avoids slow reasoning traces on CPU. It scores LCB v6 35.1, up from 26.4 for the original Qwen3-4B, and has an official free-T4 Unsloth notebook ([HF](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507); [Unsloth Notebooks](https://unsloth.ai/docs/get-started/unsloth-notebooks)). Its weak spot is code editing (Aider-Polyglot 12.9). It also has no FIM, which is why the companion exists. Qwen2.5-Coder-1.5B was trained with file- and repo-level FIM tokens and scores 83.5 on single-line HumanEval-FIM, close to the 7B's 86.2 ([arXiv 2409.12186](https://arxiv.org/html/2409.12186v3)). At Q8_0 it fits on the MX150, which keeps autocomplete latency low while the CPU handles chat. Its limit is multi-line work: it is near zero on SAFIM block completion ([arXiv 2605.04894](https://arxiv.org/pdf/2605.04894)), so treat it as a single-line and short-span completer. The same 1.5B companion also works next to Granite if Granite's FIM turns out weaker than its card suggests.

**Qwen2.5-Coder-7B is the quality ceiling, not the default.** It is Apache 2.0, has FIM, and is the best-documented code specialist, with Aider Pass@2 68.4 against 39.1 for the 3B ([arXiv 2409.12186](https://arxiv.org/html/2409.12186v3)). At 13–16 tok/s prompt processing, though, it suits a "patient" mode for small prompts or overnight batch edits. It does not suit an interactive assistant that reads whole files.

## The 2026 headline models fail on CPU latency, verification, or both

The 2026 releases report the highest scores, and that is why they need the closest look. **Qwen3.5-9B's LCB v6 of 65.6 and the 4B's 55.8 come from thinking mode**, which is on by default ([HF model card](https://huggingface.co/Qwen/Qwen3.5-9B)). With `enable_thinking=False` you keep CPU latency acceptable, but you lose an unknown share of that score. A third-party guide's 82.7 for the 9B contradicts the card and should be ignored ([codersera](https://codersera.com/blog/qwen-3-5-complete-guide-2026/)). Qwen3.5 also uses a new hybrid architecture: three Gated DeltaNet linear-attention layers for every full-attention layer. That should keep the KV cache small, but **none of the research notes confirm that llama.cpp runs Gated DeltaNet efficiently on CPU**. The card also does not say whether the 9B is dense or MoE, and the Hub lists it at 10B. No small-Qwen3.5 Unsloth notebook was found; the only Qwen3.5 entry, the 35B-A3B, needs an A100 ([Unsloth Notebooks](https://unsloth.ai/docs/get-started/unsloth-notebooks)). Qwen3.5-4B is the 2026 model most likely to replace the fallback, once someone confirms llama.cpp support and measures it with thinking off on a similar CPU.

**Mellum2.1 is the most interesting and least verified model here.** JetBrains reports LCB v6 82% and SWE-bench Verified 47.0%, up from 2.0% for Mellum2 ([NYU RITS](https://rits.shanghai.nyu.edu/ai/jetbrains-ships-mellum2-1-a-12b-open-model-for-coding-agents/); [datanorth](https://datanorth.ai/news/jetbrains-mellum2-1-jumps-from-2-to-47-on-bug-fixes)). Yet JetBrains' own comparison has Qwen3.5-9B fixing more bugs and leading on SWE-bench Pro and Terminal-Bench. One outlet even reports "25 billion active" parameters, which conflicts with the 2.5B figure ([KuCoin](https://www.kucoin.com/news/flash/jetbrains-releases-open-source-mellum2-1-outperforms-qwen-in-livecodebench)). With 2.5B active parameters it should decode faster than a dense 8B. But the Q4_K_M file is about 8.1 GB ([pinggy.io](https://pinggy.io/blog/best_open_source_self_hosted_llms_for_coding/)), it is a thinking model, its FIM support is unconfirmed even though earlier Mellum versions were completion models, and no free-T4 MoE fine-tuning path for it has been documented. Put it on the watch list until independent results appear. Gemma 4 E4B (LCB v6 52.0, Apache 2.0, free Unsloth notebooks) is a credible chat alternative. However, its 8B-with-embeddings footprint and multimodal encoders cost RAM that a coding assistant gains nothing from, and it has no FIM ([Gemma 4 model card](https://ai.google.dev/gemma/docs/core/model_card_4)).

## Free T4s comfortably cover every recommended size

Fine-tuning is not the constraint. Unsloth's documented QLoRA minimums are **3.5 GB for 3B, 5 GB for 7B and 6 GB for 8B** ([Unsloth Requirements](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements.md)), all well inside a 16 GB T4. Kaggle gives 12-hour GPU sessions and a floating weekly quota that users commonly report at about 30 hours, though Kaggle does not state it. Colab publishes no quota and can disconnect early ([gpuperhour.com](https://gpuperhour.com/blog/free-cloud-gpus-and-credits)), so use Kaggle for long runs and checkpoint to the Hugging Face Hub. Pick the T4, not Kaggle's P100: the current Kaggle PyTorch image needs sm_70+ and fails on the P100's sm_60 ([Kaggle docker-python #1546](https://github-gitlab-huggingface.pages.dev/Kaggle/docker-python/issues/1546)), and Unsloth itself requires compute capability 7.0 ([Unsloth Requirements](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements.md)). Use fp16 on the T4. Forcing bf16 has been measured at about 4× slower on a Kaggle T4, though in a non-Unsloth test ([earino](https://earino.github.io/applied-deep-learning/site/blog/05_bf16_on_t4.html)). Preference tuning also fits: Unsloth ships free-T4 DPO (Zephyr 7B) and ORPO (Llama 3 8B) notebooks ([Unsloth Notebooks](https://unsloth.ai/docs/get-started/unsloth-notebooks)).

Export is a single call: `model.save_pretrained_gguf(dir, tokenizer, quantization_method="q4_k_m")` merges the adapter, converts the model, quantizes it, and writes an Ollama Modelfile with the training chat template ([Unsloth: Saving to GGUF](https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-gguf)). After that, `ollama create <yourbrand> -f Modelfile` registers the model under your own name ([Ollama Import](https://docs.ollama.com/import)). **The most common failure is a chat-template, EOS or BOS mismatch** ([Unsloth: Saving to Ollama](https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-ollama)), so test the exported GGUF against the notebook's outputs before you build the API layer. One more point is my inference rather than a sourced finding: if you fine-tune Granite or the 1.5B companion only on chat-format data, include FIM-formatted examples (prefix/suffix/middle tokens) in the mix, or autocomplete quality can degrade.

## Conclusion

On this hardware, the right question is "which model gives an acceptable time-to-first-token on a 15 W quad-core?" rather than "which model scores highest?". Asked that way, the shortlist drops to 3–4B non-thinking models, and the highest-scoring 2026 models fall out. Licensing then removes Qwen2.5-Coder-3B, which is otherwise the strongest small FIM coder, and leaves Granite 4.1 3B as the one model that meets every requirement in a single checkpoint. It is also the least independently verified model on the shortlist, so the recommendation depends on a short validation rather than on trust. Before fine-tuning, spend an hour confirming three things: Granite 4.1 3B loads in Unsloth on a free T4; its GGUF runs at roughly 30+ tok/s prompt processing under `llama-bench -t 4,8` on the laptop; and its FIM output on your own repository beats Qwen2.5-Coder-1.5B. If any of the three fails, switch to the fallback pair (Qwen3-4B-Instruct-2507 plus Qwen2.5-Coder-1.5B), which costs only a second small model in RAM.

Two developments could change this pick within months. Confirmed llama.cpp CPU support for Qwen3.5's Gated DeltaNet, together with a measured non-thinking score, could make Qwen3.5-4B the stronger Apache chat base. Independent benchmarks of Mellum2.1, plus confirmation of its FIM support, could make a 2.5B-active MoE the best balance of quality and speed for a 16 GB laptop. Whichever you choose, the largest runtime gain comes from prompt caching with a stable system prompt and file prefix (llama-server's `--cache-prompt` is on by default) and a context cap of 4–8k tokens ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). On this CPU, prompt processing is the bottleneck, so a smaller and more stable prompt saves more time than any model choice.
