# Fix the cache and the gates first

**Most of what Jazari can still gain on the T480 comes from not re-reading prompts, from not trusting small-model output until a check has passed, and from fixing about a dozen known rough edges in the terminal. New models and runtimes add little.** The model is now Granite 4.0-H Tiny (`scripts/jazari-manifest.json`), a hybrid Mamba-2/attention mixture-of-experts with about 1B active parameters. That changes the speed picture: it writes about 10.1 tok/s on four CPU threads (`DeviceTuner.cs`, repo-measured), and its prompt cache can only resume from saved *checkpoints*, not from any shared prefix. So the cheapest wins are three launcher flags (`--cache-reuse 0`, `-ctxcp 8`, a measured `-tb 8`) plus keeping changing material out of the start of the prompt. Speculative decoding, KV-cache quantization, BLAS builds and the UHD 620 are not worth more time. For `/edit` and `/review`, Jazari's grammar-forced JSON is already the right base. The weak spots are a missing `maxLength` on edit strings, a review quote check that lets `}` "verify" a finding, and no compile check before a diff is offered. A scanner pre-pass (Roslyn CA rules, Dotnetarium, gitleaks, osv-scanner, Opengrep with Jazari's own rules) should find issues in minutes, with Granite triaging and explaining them, never deleting them. That cuts the time to a useful EduCore review from 3.4–7 hours to about an hour (estimate). A tool loop is feasible once the gateway can carry tool calls at all (today it drops them), file access checks the opened handle rather than the name, and every step keeps the hybrid cache append-only. The terminal's overall approach matches Codex CLI's Windows Terminal path. Its real bugs are in width, resize and write batching. Many numbers below are estimates or still need measuring on the laptop, and the labels say which.

**Evidence labels used throughout.** **[sourced]**: a linked page or paper states it. **[source-read]**: read directly in llama.cpp code, at the pinned build b11982 (commit `8a199ad31`) unless "master" is stated. **[repo-measured]**: measured on this T480 and recorded in the repo. **[estimate]**: arithmetic or inference from the above. **[measure]**: must be run on the T480 before it is trusted. Several hosts (huggingface.co, arxiv.org, learn.microsoft.com, ibm.com) were blocked during the research, so some facts come from mirrors or search summaries; those are marked where they matter. This report covers no design for conversation memory or history retrieval, because another effort owns that. Where a finding constrains that design (history trimming, the project state note), it is stated as a constraint only.

## 1. The hybrid cache, not raw speed, decides how fast Jazari feels

### Takeaway

Granite 4.0-H Tiny is not a dense model, and the launcher still treats it like one. Most dense-model levers have already been measured on this laptop, and most lost. Four free levers remain. The first is a separate prompt thread count (`-tb 8`). The second is making the hybrid prompt cache actually hit: a byte-stable start, variable material at the end, and `-ctxcp` sized to RAM. The third is switching `--cache-reuse` off, since it cannot help a hybrid and might corrupt state. The fourth is an all-Q4 file, so that every expert tensor gets the AVX2 repacked kernels. Speculative decoding is a weaker bet on H-Tiny than it was on the dense 4.1 3B, where it already lost on review prose. It stays off.

### Cited findings

**Where the speed stands [repo-measured].** On the CPU, H-Tiny writes 10.1 tok/s at four threads and 6.4 at eight. Partial MX150 offload reads prompts at 60 tok/s but writes only 6.6 (`src/MyOwnLLM.Cli/DeviceTuner.cs` comments). In the model-choice eval, a typical answer took 8 s, the first answer after `/read` 47 s, and a follow-up 12 s (`docs/superpowers/specs/2026-11-02-model-choice-results.md`). The launcher currently passes `-t <half of logical cores> --poll 0 -fa on|off -c 16384 --cache-ram 2048 -np 1 --cache-reuse 256`. It passes no `-tb`, `-ub`, `-ctxcp`, `-cms`, `--slot-save-path`, `-lm` or `--spec-*` flag (`Tuning.cs:40-42`, `ServerLauncher.cs:40-41`, `scripts/start-llama.ps1:10`). These levers were already measured on Granite 4.1 3B and rejected (`docs/OPTIMIZATION-LOG.md`): `KMP_BLOCKTIME=0` made answers 20–28% slower. Three n-gram speculation modes gave no real gain. A 350M draft on the MX150 sped rewrites from 5.46 to 7.95 tok/s but slowed reviews from 5.47 to 2.67 tok/s. A 1B draft gave nothing, the UHD 620 managed only 12.5 / 4.1 tok/s, and `--prio -1` cut writing by 21%. On 4.1 3B, prompt speed rose from 30.4 tok/s at four threads to 35.4 at eight, while writing barely moved (`research_notes/Local model load optimization/measured_thread_sweep.md`).

**What the model is [sourced].** IBM gives 7B total and 1B active parameters ([IBM announcement](https://www.ibm.com/new/announcements/ibm-granite-4-0-hyper-efficient-high-performance-hybrid-models)). A third-party listing gives 4 attention and 36 Mamba-2 layers, and 64 experts with 6 active ([LLM Reference](https://www.llmreference.com/model/granite-4.0-h-tiny)). The repo's own GGUF metadata read agrees on 4 attention layers out of 40 (`DeviceTuner.cs`). A mirrored config gives `mamba_d_state` 128 and `mamba_n_heads` 48 ([RedHatAI mirror](https://huggingface.co/RedHatAI/granite-4.0-h-tiny/blob/main/config.json)).

**How the hybrid prompt cache works on b11982 [source-read].** The server still reuses the prompt by default, but a recurrent state cannot be cut back to an arbitrary token. When the cached state lies past the first changed token, the server restores the latest *context checkpoint* at or before that point and recomputes from there. If no checkpoint fits, it logs "forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory …)" ([server-context.cpp @8a199ad31](https://github.com/ggml-org/llama.cpp/blob/8a199ad31/tools/server/server-context.cpp)). Checkpoints are placed at batches that start a user message, always at the last user message, and twice near the prompt end (at `4 + n_ubatch` and 4 tokens before it). Checkpoints closer together than `--checkpoint-min-step` (default 8192) are skipped, except the first, the last user message and the two near the end (same file; the near-end placement came in [PR #20288](https://github.com/ggml-org/llama.cpp/pull/20288), whose tester saw time to first token drop "quite a lot"). On b11982 the defaults are 32 checkpoints per slot, `-cms` 8192 and `-cram` 8192 MiB. `--cache-reuse` is *not* switched off for hybrids: the hybrid memory reports the attention cache's shift ability ("Shifting is trivially supported for recurrent"), so chunk reuse stays enabled. Chunk reuse then calls `seq_rm`/`seq_add` and ignores the return values, while a Mamba state cannot have a middle range erased ([llama-memory-hybrid.cpp @8a199ad31](https://github.com/ggml-org/llama.cpp/blob/8a199ad31/src/llama-memory-hybrid.cpp), [llama-memory-recurrent.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-memory-recurrent.cpp)). b11982 appends context checkpoints to slot save files, so slot save/restore should keep them [source-read]. Responses carry `cache_n`, and `LLAMA_SERVER_SLOTS_DEBUG=1` prints the tokens around a prefix mismatch ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).

**Hybrid cache bugs are a recurring class [sourced].** Earlier builds forced full re-processing on every request for Nemotron-H ([#16416](https://github.com/ggml-org/llama.cpp/issues/16416)) and LFM2 ([#16491](https://github.com/ggml-org/llama.cpp/issues/16491)). One 12-turn agent test on a hybrid took 298.5 s with a median time to first token of 18.7 s, against 121.7 s and 3.15 s with the reporter's patch. That issue was closed as stale, not fixed ([#22940](https://github.com/ggml-org/llama.cpp/issues/22940)). Open issues in Sept–Oct 2026 report that whitespace re-rendering around `<think>` and `<tool_call>` breaks prefix matching on hybrids ([#30357](https://github.com/ggml-org/llama.cpp/issues/30357)). Others report that slot restore gives no reuse on hybrids because checkpoints are not persisted ([#28194](https://github.com/ggml-org/llama.cpp/issues/28194), title only), and that `--cache-ram -1` grows RAM about 640 MiB per prompt ([#29324](https://github.com/ggml-org/llama.cpp/issues/29324), title only).

**Speculative decoding on hybrids [source-read, sourced].** Granite's hybrid architecture is not in llama.cpp's list of architectures with cheap per-token recurrent rollback (`llm_arch_supports_rs_rollback`: Qwen3.5, Nemotron-H, LFM2 and a few others), so speculation runs in full-checkpoint mode. The server saves a target checkpoint before every verify and restores it on partial acceptance ([llama-arch.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-arch.cpp), [server-context.cpp](https://github.com/ggml-org/llama.cpp/blob/8a199ad31/tools/server/server-context.cpp)). The PR that enabled this calls checkpoints "not as fast" as sequence removal. Its only numbers are GPU runs: "well above 30%" faster on code and about 10% slower on ordinary text ([PR #19493](https://github.com/ggml-org/llama.cpp/pull/19493)). A later PR says that parallel decoding of hybrid models "still remains highly suboptimal" ([PR #23269](https://github.com/ggml-org/llama.cpp/pull/23269)). For MoE targets, verifying three draft tokens can activate up to 6 experts in a 2-of-8 model, "a 3x increase in data movement" ([arXiv 2506.20675](https://web3.arxiv.org/pdf/2506.20675)), and llama.cpp's own docs say "MoEs require long drafts" for `ngram-mod` ([speculative.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md)). No published speculation measurement exists for any Granite 4.0-H model.

**Quantization on AVX2 [source-read].** Runtime repacking on AVX2 covers only Q4_0, Q4_K, IQ4_NL and MXFP4, and it applies to MoE expert matmuls (`MUL_MAT_ID`) as well as dense ones. Q5_K, Q6_K and Q8_0 are repacked only on ARM or RISC-V ([repack.cpp](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/repack.cpp)). Earlier notes measured that 27% of the 4.1 3B Q4_K_M file's bytes sit in non-repacked Q6_K tensors [repo-measured, `research_notes/Whole laptop Jazari optimization/inference_speed.md`]. For a 2026 MoE, JetBrains' card gives the quality cost of Q4_K_M as KLD 0.075 with 88.0% top-token match, against KLD 0.008 and 96.1% for Q8_0 ([JetBrains GGUF card](https://huggingface.co/JetBrains/Mellum2.1-12B-A2.5B-Thinking-GGUF)).

**Other flags [sourced].** `-tb` sets the threads for batch and prompt processing, and defaults to `-t` ([arg.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp)). b11982 has `-cmoe`/`-ncmoe` to keep expert weights on the CPU. BLAS "doesn't affect the generation performance" ([build.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/build.md)). `--poll` is ignored under OpenMP [source-read]. On battery, the T480's multi-core score falls 19% ([Notebookcheck](https://www.notebookcheck.net/Lenovo-ThinkPad-T480-i7-8550U-MX150-FHD-Laptop-Review.293682.0.html)), and thermal state alone moved prompt speed about 10% [repo-measured].

### Inferences

The repo-measured 12 s follow-up against a 47 s first answer after `/read` suggests that near-end checkpoints already work on b11982 for append-only turns, so the #22940 failure does not seem to apply here [estimate]. The risk is everything that is *not* append-only. `PromptBuilder.Build` places the state note and the `/read` context as system messages *before* the history (`src/MyOwnLLM.Gateway/Prompt/PromptBuilder.cs`). On a dense model a change there costs a re-read of what follows, and `--cache-reuse` can sometimes rescue shifted chunks. On H-Tiny there is no rescue: the restore falls back to the checkpoint at the first user message, and the whole history is read again. Per-question context should therefore go inside the latest user message, at the end. Whatever the memory effort decides about the state note and history trimming, it has to meet the same rule: nothing before the history may change within a conversation.

The checkpoint size comes from the config: 48 heads × 64 head-dim × 128 state × 4 bytes ≈ 1.5 MiB per Mamba-2 layer, times 36 layers ≈ 54 MiB [estimate]. On a speculation round, copying that over single-channel DDR4 at 10–13 GB/s costs about 5–10 ms against about 100 ms per token. That is 5–10% overhead before any rejection, on top of the MoE verify cost. So H-Tiny should gain *less* than the dense 4.1 3B did, and that model already fell to 0.49× on reviews. The `--cache-reuse` danger is a checkpoint from the previous prompt being paired with shifted attention KV, which would give a recurrent state that belongs to different tokens. An erase rule in the server may prevent this, but that could not be confirmed by reading, and the flag offers nothing even at best. KV-cache quantization is irrelevant: only 4 of 40 layers hold KV (about 8 KiB per token, so about 128 MiB at 16k), and `-ctk`/`-ctv` don't touch the Mamba state. Answer speed is bound by memory bandwidth on about 1 GB read per token, so smaller formats help answers only in proportion to the bytes they save. The tuner can't measure `-tb` directly, because `llama-bench` has no separate flag for it. Take the prompt row at `-t 8` and the answer row at `-t 4`.

### Gaps

There is no H-Tiny CPU prompt rate in the repo at all, at either 4 or 8 threads [measure]. H-Tiny's tensor-type mix, and whether a Q4_0, IQ4_NL or MXFP4 build is published, could not be checked (Hugging Face was blocked). The real checkpoint size should be read from the server's "created context checkpoint … size = X MiB" log line [measure]. The two sources on slot restore disagree: the b11982 code saves checkpoints in the slot file, while the open #28194 says hybrids get no reuse after a restore. Only a timed first-question test settles it. Whether a checkpoint is made at the end of a *generated* answer was not traced. No CPU measurement of checkpointed speculation on any hybrid exists. Vulkan support for `SSM_SCAN`/`SSM_CONV` on the MX150 was not checked.

## 2. Grammar guarantees the shape; checks must guarantee the content

### Takeaway

Keep server-enforced `json_schema` for both commands. It removes the format-compliance failures that dominate small-model editing elsewhere. What a grammar cannot force is that the `search` text exists in the file, or that a review quote supports its claim. So the next work is in the gates: bound the edit strings, return the nearest real lines when an edit misses, check syntax before offering a diff, tighten the review quote gate, and stop asking for fixes in the first review pass. Don't adopt unified diffs, line numbers or a separate fast-apply model.

### Cited findings

**Current code [repo, read 2026-11-02].** `/edit` sends `{"edits":[{"search","replace"}]}` with 1–8 edits and **no `maxLength`** (`FileEdit.cs:14-15`). The applier tries an exact unique match, then a line-trimmed match with an indentation shift. Any failure cancels the whole set. `/review` allows at most 5 findings with `maxLength` caps. A finding counts as verified when its squeezed quote is a **substring** of some line (`ProjectReview.cs:164`, `Squeeze(l).Contains(wanted)`). Every request uses temperature 0.2 (`LlamaClient.cs:10`) and leaves `top_k`/`min_p` at the server defaults.

**Grammar mechanics [sourced].** The schema converter bounds whitespace between JSON tokens (`space ::= | " " | "\n"{1,2} [ \t]{0,20}`), so there is no infinite-whitespace loop between tokens. String contents are bounded only by `maxLength`, which compiles to `char{1,N}` ([json-schema-to-grammar.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/json-schema-to-grammar.cpp), [grammars README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md)). The README warns that `x? x? x?…` "may result in extremely slow sampling" and says to use `x{0,N}`. An older issue traced per-token slowdowns to grammar stack counts of up to about 800K ([#4218](https://github.com/ggerganov/llama.cpp/issues/4218)). The built-in converter puts required properties first and silently skips unsupported keywords. LLGuidance keeps declared order and returns an error instead, at about 50 µs per token, but it needs a Rust build ([llguidance.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/llguidance.md)). `json_schema` and `grammar` cannot be combined ([#11847](https://github.com/ggml-org/llama.cpp/issues/11847)), and llama-server applies the schema grammar from the first token, so a thinking model cannot think first ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). No grammar bug specific to Granite hybrids was found. The only Granite-4-hybrid issue found was template detection breaking tool calls ([#16415](https://github.com/ggml-org/llama.cpp/issues/16415), closed).

**Format restrictions and quality [sourced].** Tam et al. found reasoning accuracy falls under format restrictions, more so the stricter they are, and that "answer freely, then convert" did better ([arXiv 2408.02442](https://arxiv.org/html/2408.02442v1)). The study used general reasoning tasks, not code.

**Edit formats for small models [sourced, 2024–25 data].** On Aider's leaderboards every model under 8B was run in whole-file format and stayed 97–100% well formed. Qwen2.5-Coder-3B passed 39.1%, the 7B 57.9%, and an older Granite 3 dense 8B only 20.3% at 78.9% well formed. Qwen2.5-Coder-32B fell from 99.6% well formed (whole) to 71.6% (diff) on the polyglot set. No sub-8B model was ever run in search/replace format ([edit_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/edit_leaderboard.yml), [polyglot_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/polyglot_leaderboard.yml)). Aider's applier tries exact and leading-whitespace-tolerant matches. Its fuzzy edit-distance match sits after an unconditional `return`, so it is switched off. On a miss Aider replies with the nearest actual lines, found at 0.6 similarity ([editblock_coder.py](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/coders/editblock_coder.py)). Fast-apply models are GPU-speed products: Morph claims 98% merge accuracy at 10,500+ tok/s, but its own pages disagree and give no method ([Morph docs](https://docs.morphllm.com/models/apply)). Kortix FastApply-1.5B is Apache-2.0 with a 986 MB Q4_K_M ([Kortix](https://huggingface.co/Kortix/FastApply-1.5B-v1.0_GGUF/tree/2003d279f3890ae038f8ec58c8a181e13a97c259)).

**Review reliability [sourced].** LLM reviewers systematically overcorrect and reject correct code. Elaborate prompts, "especially those asking for explanations and fixes", increase misjudgements, and fix-guided verification is the proposed filter ([arXiv 2603.00539](https://arxiv.org/html/2603.00539v1)). Over-critique of correct code also appears in [arXiv 2508.12358](https://arxiv.org/html/2508.12358v1). Atlassian's HalluJudge detects review comments not grounded in the code, and agrees with developers about 67% of the time in production ([arXiv 2601.19072](https://arxiv.org/abs/2601.19072v1)).

**Sampling [sourced].** IBM publishes no code or JSON sampling advice that could be found. Hosting defaults vary: 0 and 0.6 on Replicate for H Small ([Replicate](https://replicate.com/ibm-granite/granite-4.0-h-small/versions/79cd422742e4dbd543569aae06db8d5c55bc932153501c2f1bd6213e78cd427d/api)). Qwen3-4B's non-thinking settings are temperature 0.7, top_p 0.8, top_k 20 and min_p 0, with `presence_penalty` 1.5 for repetition, and greedy decoding is forbidden in thinking mode ([unsloth Qwen3-4B card](https://huggingface.co/unsloth/Qwen3-4b), search snippet).

### Inferences

**The `maxLength` gap is a bug class, not a tuning issue.** A small model that loops inside a JSON string runs until `max_tokens`, the closing `"}]}` never arrives, and `Parse` returns null after the slowest possible failure. Caps of about 1,500 characters for `search` and 3,000 for `replace` bound this. Whether a bounded `char{1,3000}` costs noticeable CPU per token on b11982 is a [measure] item, using `timings` with and without the schema.

**Track edit outcomes separately.** Jazari's failure mode is "no match", not "malformed", so eval should count `parse_fail`, `no_match`, `ambiguous`, `applied_but_wrong` and `applied_and_builds` separately. Only the last one counts as success. Three `FileEdit.Apply` changes follow. First, on a miss, find the 1–3 windows of the same line count with the highest line-set similarity (≥0.6) and send them back, saying "Copy search exactly from these". Allow at most two retries, the same as the design doc's `/fix` rule. Second, on a multiple match, return the count and line numbers and ask for one more context line. Third, strip a leading `^\s*\d+[:|]\s` when every search line has one; earlier notes saw that leak once. Keep "any failure cancels the set". Then add a Roslyn `CSharpSyntaxTree.ParseText(...).GetDiagnostics()` check on every edited `.cs` file. It runs in process in milliseconds and runs no project code, so if the original parsed clean and the edit doesn't, retry automatically. The NuGet dependency adds roughly 10+ MB to the CLI [measure]. `dotnet build --no-restore` runs MSBuild targets, so it belongs only after the user agrees.

**Whole-file fallback, not fast-apply.** A fast-apply model re-emits the whole file. At 6–10 tok/s a 300-line C# file of about 3,300 tokens takes 5.5–9 minutes, plus another model of about 1 GB in RAM [estimate], so reject it. For files under about 60 lines, or after two failed retries, ask instead for the whole file under a fenced-code grammar (not JSON, to avoid escaping). That is about 65 s at H-Tiny's 10 tok/s [estimate]. JSON against Aider-style `SEARCH/REPLACE` marker blocks is worth one A/B test: at least 20 multi-line C# edits with quotes, backslashes, `@""` and raw strings, over 3 seeds. That is exactly where code-in-JSON is predicted to hurt, and the only earlier head-to-head on Jazari's model (n=3) never tested it [measure]. A full architect/editor split doubles the generation time. The cheap version is to have `/fix` write its prose first and then make the constrained edit call with that prose in context.

**Review schema and gate.** Order the fields `quote` (one whole line, `minLength` about 12), then `problem`, then `severity`. Make `fix` optional or move it to a later call, since asking for fixes raises misjudgements. Keep every field required, because the built-in converter reorders optional ones. An optional `kind` enum over the checklist items stops "style" findings and gives eval a precision figure per category. In `Check`, require the squeezed quote to equal a squeezed whole line, or cover at least 80% of it. It must contain a run of at least 3 identifier letters, and when it matches several lines it should be marked "ambiguous". Cheap deterministic per-kind checks can downgrade a finding to "unverified" without dropping it: SQL injection needs concatenation or interpolation near SQL keywords, and a hard-coded secret needs a string literal on the line. For high-severity findings only, a second constrained call can show the 20 surrounding lines and the claim and ask for `yes/no/unsure` with `max_tokens` about 5. That costs about 5–7 s per finding, almost all prompt reading [estimate]. Keep only "yes", and judge the result on a planted-bug set with clean twins [measure].

**Sampling.** Pin `top_k` (20–40) and `min_p` 0.05 explicitly so a server upgrade cannot change behaviour, and keep one sampling profile per model in the manifest, not a single constant. If Qwen3-4B is ever chosen, use the 2507 Instruct build, or send `enable_thinking: false` on every `json_schema` call.

### Gaps

No public edit-format benchmark covers any 2025–26 model under 8B, Granite 4.x included. No measurement shows how often "did you mean" retries succeed for small models, or what the CPU grammar cost is for a schema like Jazari's. The `dotnet build --no-restore` time on the owner's projects is unknown, and the retry budget depends on it. Quote-gating and yes/no re-checks have never been studied on 1–8B models, so their value is engineering judgement until `eval/` shows it.

## 3. Scanners find, Granite triages, and the review drops from hours to about one

### Takeaway

Put a `ScanPrepass` stage in front of `ProjectReview`. It runs pinned, locally installed tools with no network, reads their SARIF into one deduplicated list, writes the deterministic report sections at once, and sends grouped findings to Granite as short question cards. The full-read loop then gets a narrower checklist, focused on authorization, ownership and business logic, which is exactly where every scanner is blind. The core set is Roslyn CA security rules, Dotnetarium, gitleaks 8.30.x, osv-scanner and Opengrep with Jazari's own rule pack. Granite's job is to **sort and explain, never delete**, and an A/B test should decide whether it judges at all.

### Cited findings

**Tools [sourced].** Dotnetarium is Apache-2.0, at v2.8.1 (2026-10-19), and is a Roslyn taint scanner for ASP.NET Core. It covers SQL, command, LDAP and XPath injection, XSS, open redirect, **SSRF**, file paths, archive extraction, deserialization, weak crypto, literal secrets and permissive CORS with credentials. It writes SARIF 2.1.0 with data flows and needs no build by default. It does not list CSRF, and it has one NuGet owner and about 8.1K downloads ([README](https://raw.githubusercontent.com/dotnetarium/dotnetarium/main/README.md), [NuGet](https://www.nuget.org/packages/Dotnetarium.Analyzers)). Its author measured 41.0 s for a 21-compilation solution on a 16-thread Ryzen ([performance-budget-matrix.md](https://raw.githubusercontent.com/dotnetarium/dotnetarium/main/docs/performance-budget-matrix.md)). SecurityCodeScan has been stuck at 5.6.7 since 2022 ([NuGet](https://api.nuget.org/v3/registration5-gz-semver2/securitycodescan.vs2019/index.json)). The .NET security category has 94 rules but **no SSRF rule**. CA3001, CA3003 and CA3007 do dataflow and are off by default in .NET 10 ([security-warnings.md](https://raw.githubusercontent.com/dotnet/docs/main/docs/fundamentals/code-analysis/quality-rules/security-warnings.md), [ca3001.md](https://raw.githubusercontent.com/dotnet/docs/main/docs/fundamentals/code-analysis/quality-rules/ca3001.md)). `<AnalysisModeSecurity>All</AnalysisModeSecurity>` switches the whole category on ([msbuild-props.md](https://raw.githubusercontent.com/dotnet/docs/main/docs/core/project-sdk/msbuild-props.md)). Opengrep's SARIF flag is `--sarif-output=`. In C#, "there is no meaningful way … to make fields in a class sources of taint" ([repo](https://github.com/opengrep/opengrep), [C# wiki](https://github.com/opengrep/opengrep/wiki/Support-for-C%23)). gitleaks is now "feature complete", with security patches only, and work has moved to Betterleaks. Betterleaks v2 documents no Windows binary or SARIF output yet ([gitleaks README](https://raw.githubusercontent.com/gitleaks/gitleaks/master/README.md), [Betterleaks](https://github.com/betterleaks/betterleaks)). osv-scanner writes SARIF with one rule per vulnerability, located at the lockfile ([output.md](https://raw.githubusercontent.com/google/osv-scanner/main/docs/output.md)). NuGet audit is on by default and covers transitive packages for `net10.0`. NU1900 means the vulnerability data could not be fetched, not that the project is clean ([Auditing-Packages.md](https://raw.githubusercontent.com/NuGet/docs.microsoft.com-nuget/main/docs/concepts/Auditing-Packages.md)). SonarAnalyzer's source-available licence and CodeQL's terms both rule out bundling ([LICENSE.txt](https://raw.githubusercontent.com/SonarSource/sonar-dotnet/master/LICENSE.txt)). `Sarif.Sdk` 5.8.0 depends on Newtonsoft.Json ([sarif-sdk](https://raw.githubusercontent.com/microsoft/sarif-sdk/main/README.md)).

**What scanners miss [sourced].** `[Authorize]` alone does no resource-level checks ([OWASP .NET cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/DotNet_Security_Cheat_Sheet.html)). LLMs found 0 of 19 IDORs where checks were spread across files, and 0 of 18 where authorization lived in middleware ([Semgrep](https://semgrep.dev/blog/2025/can-llms-detect-idors-understanding-the-boundaries-of-ai-reasoning)).

**LLM triage evidence [sourced, partly via search summaries].** In Sifting the Noise (ISSTA 2026), agent frameworks cut false positives from over 92% to as low as 6.3%. But the gains were "limited or inconsistent" for weaker backbones, and aggressive filtering can suppress true vulnerabilities ([arXiv 2601.22952](https://arxiv.org/html/2601.22952v3)). QASecClaw claims 88.6% false-positive suppression with 3.1% true-positive loss; its model sizes could not be read ([arXiv 2605.01885](https://arxiv.org/html/2605.01885v1)). Semgrep Assistant agreed with researchers on 96% of true positives but only 41% of false positives, because it was "far more conservative" about calling something a false positive ([Semgrep metrics docs](https://cloudflare.semgrep.dev/docs/semgrep-assistant/metrics)). Dotnetarium's own agent guide says "uncertainty is a reason to investigate, not suppress" ([ai-development.md](https://raw.githubusercontent.com/dotnetarium/dotnetarium/main/docs/ai-development.md)). No triage study tests a model around 3B, and none tests C#.

**Baseline [repo-measured].** Hand-written EduCore code is about 363k tokens, which is 3.4 h of prompt reading at 4.1 3B's 28.8 tok/s. The observed review time is 3–7 h (`research_notes/Whole laptop Jazari optimization/repo_review.md`, `docs/OPTIMIZATION-LOG.md`). `ProjectReview.RunAsync` currently sends every 2,000-token unit through one long checklist, and no tool output is used.

### Inferences

**Coverage split [estimate from tool docs].** Roslyn tools (CA rules and Dotnetarium) see types, attributes and overloads, so they own SQL injection, path traversal, SSRF, open redirect, CSRF (CA3147/CA5391), deserialization, and JWT, cookie and TLS flags. gitleaks owns secrets, which are redacted and never sent to the model. osv-scanner and NuGet audit own packages. Opengrep carries Jazari's own 20–30 rules for configuration and authorization patterns: `[AllowAnonymous]` on mutating actions, `[IgnoreAntiforgeryToken]`, a controller with POST/PUT/DELETE but no `[Authorize]`, `FromSqlRaw($"…")`, `AllowAnyOrigin()` with `AllowCredentials()`, and `RequireHttpsMetadata = false`. Missing authorization, IDOR, tenant leaks and client-trusted amounts have **no** scanner. That is what the model should read whole files for, with Roslyn-derived facts (route, attributes, allow-list presence) supplied, because the model cannot see across files.

**Plumbing.** Read SARIF with a small System.Text.Json model of about 150 lines (`ScanFinding`: tool, rule, CWE, level, path, line, message, flow, snippet, suppressed, line hash) rather than taking `Sarif.Sdk` and Newtonsoft. Normalise URIs to repo-relative, case-insensitive paths. Map rule IDs into class buckets, and dedupe on `(path, bucket, sha256(squeezed line)[..16])`, which survives line shifts and reuses `ProjectReview.Squeeze`. When findings merge, keep the union of tools, because tool agreement is a precision signal worth showing (untested hypothesis). Run Roslyn without touching the user's repo by passing `-p:AnalysisModeSecurity=All -p:CustomAfterMicrosoftCommonTargets=<jazari.targets>`, where the targets file sets a per-project `ErrorLog` [measure: this placement is undocumented]. Install Dotnetarium with `--tool-path` rather than globally, and never pass `--verify-secrets` or gitleaks `--validate`. Run all tools before loading the model, in sequence, with timeouts. Treat a missing tool as reduced coverage and print that at the top of the report ("Dotnetarium: not installed → SSRF not checked").

**Triage cards.** Each card holds the finding, its flow steps, the enclosing method (up to 60 numbered lines), Roslyn facts, and 2–4 fixed yes/no questions per class, each answered with a quoted line. That comes to 800–1,500 tokens [estimate]. The answer is grammar-bound (`{"q":[{"id","a":"yes|no|unknown","quote"}],"verdict","why","fix"}`), and quotes go through the existing `Check`. **Jazari computes the verdict from the answers.** The model's own `verdict` is advisory, which uses Granite as an evidence extractor rather than a judge. A `likely_false` finding moves to a "probably not exploitable" section with the quote, and is never dropped. An `unknown` answer pulls the file forward into the full-read queue. Group cards by class, so the fixed prefix stays cached across cards (on the hybrid this works only if the prefix is identical; see §1).

**Time model [estimate].** Scanners take about 3–10 minutes on EduCore. With 4.1 3B speeds a card costs about 66 s (42 s reading, 24 s writing). On H-Tiny's 10.1 tok/s writing the answer half falls to about 15 s, while its prompt rate is unmeasured. Capping at about 40 grouped cards, high severity first, keeps triage under an hour. Add 20–30 minutes of hot-path and authorization reading, and a useful first report arrives in **about an hour, against 3.4–7 hours today**. The rest of the ranked code can keep reading overnight through the existing resumable JSONL loop. In `ProjectReview.cs` this means: `Units` takes a ranking function, `Key` includes a hash of the scanner facts, `PromptVersion` goes to "4", `Instructions` splits into a per-class triage prompt and an authorization/business-logic prompt, and `Finding` gains `Source` and `Verdict`.

**The go/no-go test.** Before building the triage step, compare (a) tools only, sorted by agreement and severity, against (b) the same plus Granite's question answers, on a seeded-bug branch. If (b) does not raise the rank of the seeded true bugs, ship Granite as explainer only.

### Gaps

No independent false-positive rate exists for Dotnetarium, the CA dataflow rules or Opengrep's C# rules. How many findings EduCore produces after dedup and grouping is unknown, and that number drives the triage time [measure]. Dotnetarium's handling of policy-based authorization is undocumented. The weights in the ranking formula have no evidence behind them yet. Whether osv-scanner needs a lockfile for NuGet (which Jazari must not write into the user's repo), and how `dotnet restore` behaves offline, both need a dry run.

## 4. A tool loop is safe only after the gateway, the file guard and the cache rules change

### Takeaway

Native tool calls through `/v1/chat/completions` remain the right protocol. But the gateway cannot carry tools today, and its streaming parser would silently drop tool calls. Fix that first, using a narrow request shape: chat completions only, tools never combined with `json_schema`, no parallel calls, and non-streaming tool turns. Keep four flat tools inside a harness that tells the small model what to do next: one action per step, a cap of 6 steps, a duplicate-call guard, steering error messages, and a forced final answer. File access must verify the *opened handle's* final path, not the name. And on the hybrid, every step must be strictly append-only and byte-identical, or the loop pays for a full re-read.

### Cited findings

**Gateway today [repo, read 2026-11-02].** `ChatRequest` has no `tools`, `tool_choice` or `parallel_tool_calls` field, and `ChatMessage` has no `tool_calls` or `tool_call_id` (`ChatEndpoints.cs`). `LlamaClient.ReadChunk` reads only `delta.content`, and `ChatWithEndAsync` reads only `message.content`. Non-streaming answers are cached for one hour by prompt hash. `StatusFor` maps every llama-server 400 to 413 "context overflow". `ProjectFiles.Load` reads a named file with no root check. `Walk` uses `AttributesToSkip = 0` and skips only reparse-point *directories*, and `IsSecret` checks the file name only (`ProjectFiles.cs:45, 61`).

**llama-server tool calling [sourced].** Granite 4.1 3B is listed among the natively supported formats. An unrecognised template falls back to "Generic", which "may consume more tokens and be less efficient", and the format in use can be checked via `/props`. KV quantization to q4_0 "can substantially degrade" tool calling ([function-calling.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/function-calling.md)). Open bugs as of Oct 2026, titles as filed: `tools` + `response_format` fails with "failed to parse grammar" ([#31342](https://github.com/ggml-org/llama.cpp/issues/31342)); `/v1/responses` reports truncated tool calls as complete ([#30773](https://github.com/ggml-org/llama.cpp/issues/30773)); tool-call XML emitted as content was "silently lost" ([#30490](https://github.com/ggml-org/llama.cpp/issues/30490), closed); and a JSON Schema grammar fails on template control tokens for Granite 3.1 and Qwen3 ([#29006](https://github.com/ggml-org/llama.cpp/issues/29006)).

**Small-model accuracy [sourced, via mirrors].** On BFCL v3, Granite 4.0-H Tiny scores 57.65, Granite 4.0 Micro 59.98, Granite 4.1 3B 60.8 and Qwen3-4B-Instruct-2507 61.9 ([Unsloth mirror of IBM's table](https://huggingface.co/unsloth/granite-4.0-micro), [Docker Hub](https://hub.docker.com/r/ai/granite-4.0-h-tiny), [benchmarklist](https://benchmarklist.com/models/qwen3-4b-instruct-2507/)). Aggregators put Qwen3-4B-2507's multi-turn score at 22.1%, unverified ([llmrun](https://llmrun.dev/model/qwen-qwen3-4b-instruct-2507/benchmarks)). Continue warns that even 7–13B models "may struggle with complex tool interactions" ([Continue docs](https://docs.continue.dev/features/agent/model-setup)). A single-author CPU benchmark measured `granite4:3b` at restraint 0.000 ([tool-calling-benchmark](https://github.com/MikeVeerman/tool-calling-benchmark)).

**Harness patterns [sourced].** mini-swe-agent requires "exactly ONE" action per response. It answers a token-limit hit with "Respond more concisely", and cuts outputs over 10,000 characters to the first and last 5,000 with an elision count ([default.yaml](https://raw.githubusercontent.com/SWE-agent/mini-swe-agent/main/src/minisweagent/config/default.yaml)). Anthropic's guidance says "more tools don't always lead to better outcomes", that parameters should be named unambiguously, and that errors should give "specific and actionable improvements" ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).

**Sandbox escapes are races [sourced].** CVE-2026-44112 was a symlink swap between check and use that let sandbox writes escape the root ([VulnCheck](https://www.vulncheck.com/advisories/openclaw-symlink-swap-race-condition-in-openshell-fs-bridge-writes)). A Windows broker exploit used an oplock to pause at open and swap in an NTFS junction ([Packet Storm](https://packetstormsecurity.com/files/author/11974)). CVE-2026-50526 is described as a .NET traversal through unchecked link components, but the description is vague and unverified ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-50526/)).

**Loop latency [repo-measured, dense stand-in].** On Granite 4.1 3B, caching held inside a tool loop: 424 prompt tokens, then 10–21 new tokens per call (`research_notes/Whole laptop Jazari optimization/agent_tools_and_output.md`). On hybrids, #30357 showed a 25-token prompt growth forcing 7,260 tokens of re-processing, with tool-call boundaries among the trigger points ([#30357](https://github.com/ggml-org/llama.cpp/issues/30357)).

### Inferences

**Gateway changes (item 22).** Add `Tools`, `ToolChoice` and `ParallelToolCalls` to `ChatRequest`, and reject `JsonSchema` together with `Tools` with a clear 400. Give `ChatMessage` optional `ToolCalls` and `ToolCallId`, serialise empty content as `""`, and accept `arguments` as a string or an object. Return `tool_calls` and `finish_reason` from a non-streaming call, and stream only the final answer. Bypass the one-hour answer cache whenever tools are present, because an answer computed from a file the user has since edited is wrong. Never trim history inside a loop; if the budget runs out, stop the loop with a message (trimming between turns belongs to the memory effort). Pass llama-server's own 400 text through. Treat `finish_reason: length`, or content containing `<tool_call>` or `{"name":`, as a lost call: retry once with a format error, and never show it as an answer. Log the chat format from `/props` at start-up; "Generic" for H-Tiny means weaker calls [measure]. Add a 10-case smoke test (backslashes, `:`, quotes in paths) to run after every llama.cpp upgrade.

**Harness.** Use four flat tools (`list_dir`, `search`, `read_file`, `edit_file`) with only string and integer parameters, named `path`, `start_line`, `query`, `old_text` and `new_text`. `edit_file` takes a single edit, passed as one `Replacement` to the unchanged `FileEdit.Apply`. Every result states what happened and what to do next, for example: "old_text not found in Session.cs. Nearest lines 40-44 are: … Copy old_text exactly from these." Refusals must not invite retries ("Do not try other paths to it"). The step cap is 6 tool calls per user turn. At the cap, send one last request with `tool_choice: "none"` and "Tool limit reached. Answer now from what you have." Hash `(name, normalised args)`: the first repeat returns "you already called this at step 2", and a second repeat ends the loop. Two consecutive failures force the answer step. A zero-tool answer counts as success; never add "you must use a tool". The loop ends when a response has no `tool_calls`, with no `finish` tool. Print each call as `[2/6] → read_file src/Cli/Session.cs (lines 1-150)` with elapsed seconds, so that any argument taken from file content (a README saying "read ../../secrets") is visible.

**Handle-first `SafeFs` (item 23).** Run the lexical checks first: no UNC, `\\?\`, device names or `:` streams, and a `GetFullPath` prefix check under the root. Then open the file, call `GetFinalPathNameByHandle` on the handle, check that final path against the root's own final path and the deny list, and read from the same stream. Write to a temp file in the verified directory, re-verify the target's final path, then `File.Replace`. The remaining window needs a local attacker racing the approval keypress, which should be documented. Enumerate with `AttributesToSkip = FileAttributes.ReparsePoint` for files too. Today a file symlink named `notes.txt` that points at `~/.ssh/id_rsa` passes both `Wanted` and `IsSecret` (item 9, worth fixing now for `/review` as well). The tool path must never call `ProjectFiles.Load` with a model-supplied path. Limits: 1,600 tokens per call, about 8,000 per turn, and search capped at about 2,000 files and 2 s. With no shell and no network tool, the worst an injected instruction can do is an in-root read, which is shown, or an edit, which needs approval.

**Latency and the hybrid cache.** With 4.1 3B speeds as a stand-in, a search, read, answer sequence costs about 7 + 23 + 82 s ≈ **2 minutes**, and each extra `read_file` about 50 s [estimate]. H-Tiny's faster writing cuts the generation share by about 40%, but its prompt rate is unmeasured. Keeping the cache valid takes five rules. Append strictly within a turn. Echo the assistant's tool-call message exactly, with `arguments` byte-identical and surrounding whitespace stripped (the #30357 workaround). Send a byte-identical `tools` array every step. Don't let `/infill`, `/status` or `/warm` jobs run on the slot mid-loop: hold the queue in `RequestQueue`, or use a second slot pinned with `id_slot` [measure RAM]. Log `prompt_n`/`cache_n` per step, and warn when `prompt_n` far exceeds the appended tool result. Near-end checkpoints already cover append-only growth (§1), so lowering `--checkpoint-min-step` to about 1024 only matters if mid-history divergence shows up in those logs. If the rules can't hold the cache on H-Tiny, that alone is a reason to run the loop on dense Granite 4.1 3B or Qwen3-4B-2507. That model choice should come from the existing 20-case tool eval, run on both models.

### Gaps

Whether #31342 or #29006 affects H-Tiny's template on b11982 is unknown. So is whether `tool_choice: "none"` still renders the tool list (if not, the forced final step breaks the prefix; check with `/apply-template`), and whether Granite's template re-renders a returned tool call byte for byte [measure]. No BFCL v4 or multi-turn score exists for any Granite 4.x small model. The handle-first pattern has no Windows-specific source. It needs unit tests with an in-root junction pointing out, a file symlink, and an 8.3 path. The wording of the duplicate guard and error messages has not been tested on a 3B model.

## 5. The panel technique is right; width, resize and write batching are not

### Takeaway

Jazari's bottom panel works like Codex CLI's Windows Terminal path, which writes above the panel, clears it, uses real newlines and redraws, and avoids scroll regions because ConPTY doesn't feed regions into scrollback. That validates the design. The defects are specific. The width model is rough. The answer's wrap width is fixed when the answer starts, so a resize corrupts the panel. Each conversation write is several flushes with mis-nested synchronized-output blocks. Ctrl+Break while idle leaves a hidden cursor. Paste detection depends on timing luck. And the pacer holds back the first words for up to 1.5 s.

### Cited findings

**Panel and scrollback [code: other project, sourced].** Codex says "Codex uses the terminal scrollback itself for finalized chat history". On Windows Terminal (`WT_SESSION` set) it picks a `FullScreen` strategy that "preserves terminal-native scrollback when partial scroll regions are unreliable", writing history lines with `\r\n` and pushing its viewport down ([insert_history.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/insert_history.rs), [scrollback.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/tui/scrollback.rs)). It keeps the source text so it can re-wrap on resize, and caps redraws at 120 FPS. In microsoft/terminal #3673, a maintainer blamed ConPTY "not knowing anything about scrolling regions" for regions not feeding scrollback; no fix was found ([#3673](https://github.com/microsoft/terminal/issues/3673), via search summary). Claude Code's scroll-region experiment corrupted its inline TUI ([claudeissues #66013](https://claudeissues.com/issue/66013-decstbm-scroll-region-experiment-tengu-marlin-porch-corrupts-inline-tui-on-wide)), and full-frame Ink redraws caused severe flicker in VS Code's terminal on Windows ([#18084](https://claudeissues.com/issue/18084-severe-screen-flickering-in-vs-code-cursor-integrated-terminal-on-windows)).

**Windows specifics [sourced, code: dotnet/runtime].** Windows Terminal stable 1.24 supports synchronized output (DEC 2026) "to reduce flickering and tearing" ([devblogs](https://devblogs.microsoft.com/commandline/windows-terminal-preview-1-25-release/), via search summary). Conhost, OpenConsole and Windows Terminal each have their own character-width model ([wtmux 4.0.0](https://newreleases.io/project/github/fukuyori/wtmux/release/4.0.0), third party), and conhost and terminal widths "need to be in sync" ([#16916](https://GitHub.com/microsoft/terminal/pull/16916)). In .NET, `TreatControlCAsInput` clears `ENABLE_PROCESSED_INPUT`. `KeyAvailable` consumes and discards non-key records, window-resize records included, and `ReadKey` never sees VT input such as bracketed-paste markers. Ctrl+Break still reaches `CancelKeyPress`. `Console.Out` is a `StreamWriter` with `AutoFlush = true`, so each `Write` is its own console write ([ConsolePal.Windows.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Windows.cs), [Console.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/Console.cs)). Windows pastes arrive as bursts of key events, and Codex uses a timing-based `PasteBurst` state machine so that Enter inside a paste becomes a newline ([paste_burst.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/bottom_pane/paste_burst.rs)).

**Pacing [sourced].** Delivering tokens slower than reading speed hurts experience, while faster than reading doesn't help ([Andes, arXiv 2404.16283](https://arxiv.org/pdf/2404.16283)). Users tune stream speed to their own reading pace, and adaptive streaming improved satisfaction ([arXiv 2504.17999](https://arxiv.org/pdf/2504.17999)). Codex commits only at newlines and paces by queue depth and age: catch-up at 8 lines or 120 ms ([chunking.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/streaming/chunking.rs)).

**Accessibility [sourced].** NVDA users are steered towards Windows Terminal, and fast-streaming output should be announced in batches ([t3code #6884](https://github.com/pingdotgg/t3code/discussions/6884)). A TUI whose virtual cursor didn't move the real cursor misled NVDA ([claudeissues #61497](https://claudeissues.com/issue/61497-bug-mcp-tui-arrow-key-navigation-is-inaccessible-with-nvda-screen-reader-on-wind)).

**Observed in Jazari [repo].** `WriteAbove` decides whether text reaches the panel by counting `\n` only (`PromptEditor.cs:661`). Each answer captures its width once (`Program.cs:112`). `ConsoleText.IsWide` treats every surrogate as wide and BMP emoji as narrow (`ConsoleText.cs:24-27`). `Ui.Wrap` and `MarkdownStream.Split` can split surrogate pairs, and one wide character halves a whole line's wrap width (`MarkdownStream.cs:160-171`). `StampTime` moves up by the answer's rows without allowing for the panel (`MarkdownStream.cs:54-55`). `WriteAbove` opens a DEC 2026 block, and the nested `Show` closes it early (`PromptEditor.cs:649-678`). An idle Ctrl+Break kills the process without `StopAsync` (`InputLoop.cs:456, 473`). Paste detection relies on `KeyAvailable` right after Enter (`PromptEditor.cs:547`), and each pasted character is an O(n) insert plus a completion refresh. Input polls every 25 ms. `TextPacer` holds 60 characters or 1.5 s before the first output (`TextPacer.cs:28-33`). `TakeOverScreen` wipes scrollback with `\e[3J` (`Ui.cs:31`). The palette assumes a dark background (`Theme.cs`). And the CLI spec says "no ticking timer" and "Esc clears input", while the code does neither.

### Inferences

The highest-value fix is **one grapheme-aware width function**, `ConsoleText.Columns(string)` built on `StringInfo`/`Rune`, East Asian Width and emoji presentation, used by every wrapper and by the panel-collision check. Pair it with resize handling: poll the window size, since .NET discards resize events, and on a width change during an answer either re-wrap the live tail from its source text, as Codex does, or clear and redraw the panel. That closes the three linked bugs (items 1–3 in the notes), where physically wrapped rows overwrite panel rows that the frame diff believes are intact. The cheapest fix is **one string per `WriteAbove`**, which gives one syscall and one real synchronized frame. Batch `Ui.Row`'s per-row `WriteLine`s into a single write; today a 30-row block costs 30 full lock-cursor-sync cycles, and in conhost (no DEC 2026) each one can paint separately. The idle Ctrl+Break path needs a `ProcessExit`/`PosixSignalRegistration` handler that writes `\e[?25h` and clears the panel. For pacing, Jazari's backlog-proportional `TextPacer` is sound, but the 1.5 s hold lands after 10–90 s of prompt reading, at 25–60 chars/s of real output. Andes says delay below reading speed is what hurts, so a hold of 0–300 ms, word-boundary pieces and a `Discard()` on cancel are the evidence-backed choice. Confirm with a quick A/B with the owner. For pastes, Codex's timing window replaces "is a key queued right now?", and building the inserted text once fixes the O(n²) cost. A `--plain` mode can reuse the existing piped path (`TextLineReader`, no panel) for screen readers. Smaller items: track the cursor arithmetically instead of calling `GetCursorPosition` on every write (a race on Linux and macOS), don't key Windows-Terminal-only behaviour on an inherited `WT_SESSION`, and ask the owner whether wiping scrollback at start is wanted.

### Gaps

Several things are untested: a resize while an answer streams, a 200-line paste into both conhost and Windows Terminal, NVDA with Windows Terminal during streaming, IME candidate placement, and VS Code's terminal (xterm.js over ConPTY) [measure]. Whether classic conhost honours DEC 2026 is unknown, and so is whether microsoft/terminal #3673 was fixed in 2026. Claude Code's current renderer is known only secondhand.

## Conclusion

The common thread is that the hybrid model turns hidden costs into visible ones. On the dense 4.1 3B, a changed project note or a re-rendered tool call cost a partial re-read that `--cache-reuse` sometimes covered. On H-Tiny, the same change costs a re-read back to the last checkpoint, with nothing to cover it. So prompt layout, request shape and queue discipline now matter as much as any flag. That makes the cheap telemetry item (`cache_n` per request) more valuable than any single speed lever: it is the only way to see whether the review pre-pass, the tool loop and the memory effort's choices are keeping the cache warm. If the loop runs show they can't, the model choice should be revisited for the loop specifically, not for chat.

The same thinking applies to output quality. On small models, reliability comes from deterministic checks around the model: grammar bounds, a strict quote gate, a syntax gate, scanners for the parts of a review that tools can see, and a computed verdict rather than a model's opinion. Each of these is cheap, testable on `eval/`, and independent of which 1–4B model wins next. That is why they rank ahead of every larger feature. The open question is whether a 1B-active model adds ranking value over scanners at all. One seeded-branch A/B answers it, and its result decides how much of the triage design is worth building.
