# Let the compiler check Jazari's answers

**The next gains for Jazari come from deterministic checks around the model, not from the model. Use the C# compiler as a ground-truth oracle for API names. Make the law book more precise rather than larger. And fix the eval so it can see a change at all.** Three findings shape the order. First, a 45-question test set **cannot detect a 2-3 question change**: a +3 result with no losses gives an exact McNemar p of 0.25, and only 6 wins with 0 losses reaches p < 0.05 [computed]. So the law book's test-set gate needs a decision rule written down before the run, judged on the paired per-question win/loss table. Second, an in-memory Roslyn compilation against the real reference assemblies turns invented APIs into concrete compiler errors (CS0117, CS1061, CS0246 and similar) with no project code run. That gives Jazari a "does this API exist" check the earlier reports' text-based anti-invention check could not ([CSharpCompilation.GetDiagnostics](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation.getdiagnostics?view=roslyn-dotnet-5.3.0)). Third, 2026 evidence on models of 3B and below says that the *presence* of retrieved context, not its quality, causes much of the damage, and that adding it can destroy 42-100% of answers the model already knew ([arXiv 2603.11513](https://arxiv.org/html/2603.11513), search summary only). That favours better section choice and a strict evidence gate over more passages, rerankers before embeddings, and a new "destroyed-known" count in the eval. No model released up to November 2026 clearly beats Granite 4.0-H Tiny on quality per second on this single-channel laptop. IBM's own successor line went dense, and the only like-for-like rival (LFM2.5-8B-A1B) carries a revenue-capped licence. Small-model repair evidence also argues for **one** compile-driven retry at most, and suggests a fresh resample often does as well as "repair". Many timings below are estimates, and several research sites were blocked, so labels say which claims rest on a page read, a search summary or arithmetic.

**Evidence labels.** **[sourced]** a linked page states it, read directly. **[snippet]** the claim comes from a search-engine summary or a secondary write-up, because arxiv.org, huggingface.co, sqlite.org, aider.chat, openai.com, docs.continue.dev, code.visualstudio.com and genai.owasp.org could not be fetched during this research. **[computed]** exact statistics computed locally. **[repo]** read in this repository on 2026-11-02. **[estimate]** arithmetic or inference. **[measure]** must be run on the T480 before it is trusted. Prompt-reading cost uses the measured H-Tiny rate of about 30-36 tok/s and writing about 10 tok/s from the earlier reports, so 300 injected tokens cost about 10 s.

## A 45-question test set needs six clean wins to prove anything

The law book is waiting on its test-set gate, so how that gate decides comes first. On 45 items the 95% Wilson interval for 36/45 runs from **66% to 89%**, about ±5-6 questions [computed]. For two configurations, only the questions where they disagree carry information: in McNemar's test the discordant items are the effective sample size ([MedCalc](https://www.medcalc.org/en/book/mcnemar-test.php)). The exact two-sided p-values for small win/loss splits are sobering. 3/0 gives **0.25**, 4/0 gives 0.125, 5/0 gives 0.0625 and 5/1 gives 0.22 [computed]. Power to detect a true +3-question gain at α = 0.05 is about **0.08-0.10 at N = 45**, rising to 0.64-0.94 at N = 150 and 0.93 at N = 300, depending on how many losses come with the wins [computed]. Anthropic's eval-statistics paper makes the same structural point: compare models on **paired per-question differences**, report the difference, standard error, interval and correlation, and use clustered errors when questions share a source. Clustered errors were sometimes more than 3x the naive ones ([Anthropic](https://anthropic.com/research/statistical-approach-to-model-evals)).

What this means for the law book: the gate cannot prove the book *helps*. It can show the book *does not hurt*. The rule should be written down before the run, for example "ship if wins ≥ losses, no new must_not failures, plain median ≤ 30 s and none over 2 minutes; report the 2x2 table and p". A +2 or +3 should be described as consistent with noise, not as a win. `eval/compare.py` today prints totals and per-category scores, but no per-question pairing [repo], so the change is about an hour of Python: the table, the exact binomial p, and one new count. That count is the **destroyed-known rate**: questions the baseline answered correctly that the law-book run now gets wrong. The small-model RAG evidence below says that is the failure to watch for. If sampling is used rather than temperature 0, run k ≥ 3 samples per item and average them, as the Anthropic paper advises.

Weak checks also mis-rank systems. Strengthening HumanEval's tests 80x cut pass@k by up to 19-29% across 26 models and **changed model rankings** ([LiveCodeBench citing EvalPlus](https://arxiv.org/html/2403.07974v2), snippet). Phrase matching has the same flaw: it rewards keyword stuffing, misses paraphrases and ignores whether code compiles. The cheapest fix reuses item 4's compiler. Extract fenced C# blocks from each answer and add "compiles against the target framework" as a scored field next to the phrases. For a broader "did general C# coding regress" signal, **MultiPL-E HumanEval-C#** has 158 problems with an offline `dotnet build`-plus-tests harness ([evalscope](https://evalscope.readthedocs.io/en/latest/benchmarks/multiple_humaneval.html), [MultiPL-E](https://ccs.neu.edu/~arjunguha/main/papers/2023-multipl-e.html)). At 20-60 s per problem that is a 1-2.5 hour overnight run [estimate]. Its problems are public and likely in pretraining data, so only the deltas between Jazari configurations mean anything. No offline .NET Q&A benchmark (ASP.NET Core, security) was found, so the private set stays the main decider.

The set must grow, and the cleanest source is Jazari's own log. The gateway already stores prompt, answer, duration and an `accepted` flag set through `/v1/feedback` [repo]. A weekly script can pull rejected answers, cluster them by keyword, and let the owner turn about five a week into items with must-have and must-not phrases. They go to the **dev** set by default. A fixed fraction, such as every fourth, goes to the test set, chosen *before* anyone looks at a tuned answer, so the test set never steers tuning. Each log row should also record the gateway build, the prompt and law-book version and the model hash, so acceptance rates can be compared within a category across releases. Add cheap implicit signals as well: a re-ask within two minutes, and whether an `/edit` diff was applied and kept. Copilot treats acceptance rate as its headline signal ([GitHub Docs](https://docs.github.com/en/copilot/concepts/copilot-usage-metrics/copilot-metrics)), but one user's acceptance rate moves with their topic mix, so compare like with like. If preference tuning ever happens, binary accept/reject labels fit **KTO**, which needs no paired answers and reports matching DPO from 1B to 30B ([KTO paper](https://arxiv.org/pdf/2402.01306v1.pdf), snippet). That needs hundreds of labels and a GPU, so it comes much later. Keep a hash list of test items and check every new fine-tuning or retrieval corpus against it. Scrub API keys and connection strings from log rows on write.

A local LLM judge does not fit. Small judges show position bias (the first option preferred 65.7% of the time), self-preference up to +73 points, and only moderate agreement between judges (κ = 0.357) ([AMCIS 2026](https://aisel.aisnet.org/amcis2026/sig_svs/svs/1), snippet), and every judgement costs model time at 10 tok/s.

## The C# compiler is a free oracle for invented APIs

Small models fail most often by inventing members, overloads and types. Roslyn can catch exactly that without running any code. `CSharpCompilation.Create(name, trees, references, options)` followed by `GetDiagnostics()` returns syntax, declaration and binding diagnostics without emitting ([CSharpCompilation.Create](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation.create?view=roslyn-dotnet-5.3.0)) [sourced]. Reference assemblies come from the local SDK's `packs/` folder (Microsoft.NETCore.App.Ref, Microsoft.AspNetCore.App.Ref) and the NuGet cache. Pointing Roslyn at runtime implementation assemblies "will often work on .NET Framework but will fail" on .NET Core, which is why reference assemblies are needed ([Basic.Reference.Assemblies](https://github.com/reflectronic/basic-reference-assemblies)) [sourced]. `MetadataReference.CreateFromFile` can attach an XML documentation provider, and `AssemblyMetadata` should be shared across references for performance ([MS Learn](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.metadatareference.createfromfile?view=roslyn-dotnet-5.3.0)) [sourced].

**For plain answers (item 4).** Extract each fenced C# block. Wrap top-level statements in a `Program` file with ASP.NET Core `global using`s, or wrap member snippets in a dummy class. Compile, then keep only the "this does not exist" codes: CS0117, CS1061, CS0246, CS0234, CS1501, CS1503 and CS7036. Ignore errors caused by missing context, such as undeclared locals. The codes are standard. The filter list is a design that has not yet been tested [estimate]. On a hit, annotate the answer ("`Foo.BarAsync` does not exist in .NET 10") rather than regenerating, because a retry costs a full generation of 30 s or more and would push the plain-question median past 30 s. The same compilation can check identifiers that appear in prose (`GetTypeByMetadataName`, member lookup) and tag unresolved ones as "unverified". This is the earlier report's anti-invention check, upgraded from "appears in something Jazari read" to "exists in the framework the user compiles against". Cost [estimate; measure]: loading the roughly 200 shared-framework reference assemblies once costs about 100-300 MB of RAM and a few seconds. Later compiles of a small snippet should take tens to a few hundred milliseconds in the long-lived gateway. Pre-warm in the existing `/v1/warm` path. Never use `CSharpScript`: executing model code is unnecessary and unsafe.

**For `/edit` (item 5).** Add a semantic tier between the earlier report's syntax gate and an optional `dotnet build`. Load the project once (from `MSBuildWorkspace`, or from the `obj/` reference list), keep it warm, apply the edit with `compilation.ReplaceSyntaxTree`, and report only errors the edit *introduced*. That means diffing against a baseline compile of the unedited tree. The diff matters because without source generators, Razor, `[LoggerMessage]`, Regex and JSON source-gen types show up as false CS0103 and CS0246 errors. Compiling runs no project code. Roslyn's `LookupSymbols` at the error location can supply "did you mean" names, which is grounding a 1B model cannot do for itself. A warm one-file re-check should be sub-second to a few seconds [estimate; measure on EduCore].

**How much repair is worth it.** Aider's leaderboard data, parsed directly, shows how much a second attempt with test feedback adds on its Python edit set: **+0.0 for Qwen2.5-Coder-0.5B, +3.0 for 1.5B, +5.3 for 3B, +6.0 for 7B and +10.6 for 14B** ([edit_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/edit_leaderboard.yml)) [sourced]. Weak models barely move on the harder polyglot set (gpt-4o-mini 0.9 → 3.6) ([polyglot_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/polyglot_leaderboard.yml)) [sourced]. Controlled work finds self-repair gains "often modest … and sometimes not present at all" once its cost is counted, with i.i.d. resampling sometimes equal or better at the same budget ([Olausson et al., ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/9ddc141bdbf9d1db510cefff56c586ad-Abstract-Conference.html)) [snippet]. A 2026 placebo-controlled preprint on 0.5-1.5B code models found that code plus executed facts tied blind resampling at **26 vs 26** unlocks ([arXiv 2606.31511](https://arxiv.org/pdf/2606.31511)) [snippet, single author]. H-Tiny's ~1B active parameters sit in the range where a second round adds about 0-5 points, and a repair round on the T480 costs about **1-2 minutes** (1.5-3k tokens re-read, 150-400 written) [estimate]. So: one automatic round at most, fed with at most five structured errors (`file:line | CSxxxx | message | offending line`), which work better than raw compiler text ([arXiv 2604.01680](https://arxiv.org/pdf/2604.01680)) [snippet]. Then show the diff marked "does not compile (n errors)". The earlier report allowed two "did you mean" retries for *no-match* failures. That stays reasonable, because those retries are cheap and deterministic. For *compile* failures, one round is the cap. An eval A/B should decide between (a) a repair prompt with the errors and (b) a fresh sample at a new seed with a "must compile" note and no failing code shown. "Generate two, keep the one with fewer new errors" is the pipeline-native form of (b).

**Agentless before a tool loop (item 12).** The earlier report planned a six-step native tool loop, gated on gateway tool plumbing. New evidence argues for building a fixed pipeline first. Agentless (localize → repair → validate, with no LLM-driven action selection) reached 32% on SWE-bench Lite with GPT-4o ([arXiv 2407.01489](https://arxiv.org/html/2407.01489v2)) [snippet]. Better fault localization alone added 12.8% when plugged into it ([arXiv 2601.18044](https://www.arxiv.org/pdf/2601.18044)) [snippet]. Aider found architect/editor splits gave only "modest" gains with a 32B architect, at "fairly high cost in terms of latency" ([Aider QwQ post](https://aider.chat/2024/12/03/qwq.html)) [snippet]. For Jazari, the compiler or a failing test supplies file and line, Roslyn supplies the enclosing method, the model makes one constrained edit, and tiers 1-3 validate it. That needs no tool calling at all, which sidesteps H-Tiny's 57.65 on BFCL v3 and the gateway work. Affected tests can be found by convention (`FooTests`) or by `SymbolFinder.FindReferencesAsync`, then run with `dotnet test --no-build --filter "FullyQualifiedName~Ns.FooTests"`. The value must be quoted in PowerShell, where the comma is an operator ([MS Learn](https://learn.microsoft.com/dotnet/core/testing/selective-unit-tests)) [sourced]. No evidence shows that 1B models write *useful* xUnit tests, so `/test` should stay an explicit, user-approved command.

**Build speed and safety.** MSBuild Server is **on by default from the .NET 11 SDK**, needs `DOTNET_CLI_USE_MSBUILD_SERVER=1` on earlier SDKs, and exits after 15 minutes idle ([MS Learn](https://learn.microsoft.com/visualstudio/msbuild/msbuild-server?view=visualstudio)) [sourced]. Pass `--no-restore`, because `dotnet build` otherwise restores on every loop ([MS Learn](https://learn.microsoft.com/dotnet/core/tools/dotnet-build#description)) [sourced]. Microsoft warns that `dotnet format` "may restore, compile, and run analyzers … Only invoke the tool against trusted code" ([MS Learn](https://learn.microsoft.com/dotnet/core/tools/dotnet-format)) [sourced], and the same holds for build and test. Native Windows has no mature agent sandbox. Claude Code's sandbox supports only macOS, Linux and WSL2 ([docs](https://code.claude.com/docs/en/sandboxing), snippet). OpenAI's Codex docs and engineering post disagree on whether their Windows sandbox uses AppContainer or write-restricted tokens (snippet). Windows Sandbox is Pro-only, single-instance, has networking **on by default**, and starts from a clean image, so the MSBuild Server is never warm inside it ([MS Learn](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/)) [sourced]. The realistic tiers for Jazari follow from that. In-process Roslyn checks run automatically. Anything that executes waits for a keypress showing the exact command, then runs offline with `--no-restore` inside a Job Object with memory and time caps (to protect the model's RAM), and with `/nr:false` so no build node outlives the job. Never auto-build after an edit that touches `*.csproj`, `*.props`, `*.targets`, `Directory.Build.*`, `nuget.config` or `global.json`. Show those diffs with a "build-config change" banner. Whether the MSBuild Server escapes a Job Object is unverified [measure]. Windows Sandbox fits only an occasional opt-in "safe test run".

## Precision beats recall when the reader has one billion active parameters

The law book's design (one passage of at most 300 tokens, only when the evidence gate fires) matches the newest small-model evidence, and the next work should sharpen it rather than widen it. A March 2026 preprint tested five models from 360M to 8B: with *oracle* passages, on questions the model could not answer alone, the 7B got 14.6% right, the 1.5B 10.0% and the 360M 0%. Adding retrieval destroyed **42-100% of answers the model previously knew**, and for ≤3B models "context presence, not quality, drives distraction" ([arXiv 2603.11513](https://arxiv.org/html/2603.11513)) [snippet; single-author preprint, numbers to check against the PDF]. An ACL 2025 study likewise found 3B variants in every family more distractible than larger ones ([ACL Anthology](https://aclanthology.org/2025.acl-long.892.pdf)) [snippet]. Together with the earlier reports' BM25-over-dense results and the finding that hybrid retrieval was neutral or negative under 7B, this sets three rules. Never add a second "maybe relevant" passage. Treat a wrong-section passage as worse than none. And count destroyed-known answers on the dev set, not just found and refused. Cheap prompt-side tests: say the passage is optional, and strip links, `xref` tags and Markdown noise to save tokens. No study covers hybrid Mamba/MoE models of H-Tiny's size, so its 7B total parameters may make it more robust than a dense 1B. That is unknown.

**The cheapest fix is in the ranking call (item 2).** The gateway ranks with `bm25(chunks, 1.0, 1.0)`, so title and text weigh the same, and each chunk's title holds only "page: nearest heading" [repo, `LawBook.cs`, `lawbook/build.py`]. Both known dev misses are "right page, wrong section" or "near-topic page outranks the right one". Three zero-runtime-cost changes target them. First, raise the title weight (for example 3-4 against 1). Second, store the full heading path (H1 > H2 > H3), and optionally a separate code or identifier column with low weight. Third, rank in two stages: aggregate chunk scores per page (max, or sum of the top two), pick the page, then pick the section by heading match. FTS5's `bm25()` accepts per-column weights, but sqlite.org could not be fetched to quote the documentation, so check the syntax there [estimate]. The keep-it test is the dev set: does it fix the two misses and keep 15/15 traps refused, with no destroyed-known answers?

**A reranker is the next step, if item 2 is not enough (item 8).** In Qdrant's benchmark, MiniLM-L6-v2 cross-encoder reranking of about 30 pairs took a p99 of **36-51 ms** on a 14-core M4 Max CPU ([Qdrant](https://qdrant.tech/blog/oxidizing-cross-encoders/)) [sourced, different hardware]. FlashRank ships TinyBERT-L2 at about 4 MB and MiniLM-L12 at about 34 MB, both capped at 512 tokens ([FlashRank README](https://raw.githubusercontent.com/PrithivirajDamodaran/FlashRank/main/README.md)) [sourced]. Scaled to the T480's four cores, 20-30 pairs might take 100-400 ms for MiniLM-L6 and well under 100 ms for TinyBERT, with 50-150 MB of RAM under Microsoft.ML.OnnxRuntime in the gateway [estimate; measure]. That is trivial against the 10 s a passage costs to read. But MS MARCO rerankers learned web QA, not API documentation, so the gain is unproven. The reranker should feed the evidence gate, never replace it. Static embeddings sit further back. Model2Vec's potion-retrieval-32M is very cheap but scores about **82% of all-MiniLM-L6-v2** on MTEB retrieval ([Model2Vec results](https://minish.ai/packages/model2vec/results/)) [snippet], and sqlite-vec is still `0.1.10-alpha.4` ([VERSION](https://raw.githubusercontent.com/asg017/sqlite-vec/main/VERSION)) [sourced]. Given the earlier dense-retrieval results, they are unlikely to beat weighted BM25 plus a reranker. One counterpoint: on a third-party library-documentation split, dense scored nDCG@10 0.765 against BM25's 0.687 ([hakari-bench](https://hakari-bench-leaderboard.hf.space/docs/benchmark-tasks/NanoCodeRAG)) [sourced, compact split]. Dense retrieval is not hopeless on docs, but Jazari's own measured evidence points the other way.

**An API book for exact-name questions (item 9).** `dotnet/dotnet-api-docs` holds **13,707 ECMA XML files across 391 namespace folders**, CC-BY-4.0 for text and MIT for code. Each member carries a `<MemberSignature Language="C#">` line and `FrameworkAlternate` version tags through `net-11.0`. It contains **no `Microsoft.AspNetCore` or `Microsoft.EntityFrameworkCore` folders** ([repo](https://github.com/dotnet/dotnet-api-docs), [HttpClient.xml](https://raw.githubusercontent.com/dotnet/dotnet-api-docs/main/xml/System.Net.Http/HttpClient.xml)) [sourced, files counted from a clone]. So the ASP.NET Core and EF Core half must come from walking the local reference assemblies with Roslyn (`ISymbol.ToDisplayString()`, `GetDocumentationCommentXml()`). That also guarantees the signatures match what the user compiles against. Whether the ASP.NET Core ref pack ships complete XML docs is unverified. CloudAPIBench found documentation retrieval "significantly enhances low-frequency API performance" but "can degrade high-frequency API performance with irrelevant retrievals", and a frequency-gated variant balanced the two ([arXiv 2407.09726](https://arxiv.org/html/2407.09726v1)) [snippet]. Jazari should therefore look APIs up by **exact name** only when the question names one (`IOptionsMonitor<T>`, `AddDbContextPool`), and inject only the overload lines. Five lines cost about 3-6 s, against about 10 s for a prose passage [estimate]. The same table gives items 4 and 5 their "real overloads" for annotations. Its size, roughly 30-80 MB of SQLite if remarks go in a separate column, is an estimate to measure.

**A repo map for questions about the user's own code (item 10).** Aider's repo map is a signature-only outline of "the most important identifiers, the ones which are most often referenced", ranked over a file-dependency graph, with a default budget of 1k tokens ([aider repomap.md](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/docs/repomap.md)) [sourced]. Roslyn syntax-only parsing (no restore) can produce a sharper C# version: symbols with signatures, attribute routes and `Map*` calls, `builder.Services.Add*` registrations, `DbSet<>`s and `appsettings` keys, given as `label: value` facts. That is the format the earlier recall test and reame's bench favoured. Re-parse only changed files. The hybrid cache sets the main constraint. A 300-600-token map costs 10-20 s to read, so it pays only if it sits in the stable prefix and stays **byte-identical for the whole conversation**, frozen like the project note. A map that changes mid-conversation forces a re-read back to the last checkpoint. No study measures repo-map benefit at ~1B parameters.

## Three gateway gaps decide which tools can plug into Jazari

The gateway already binds to `127.0.0.1`, puts an API key on every `/v1` route and streams OpenAI-style SSE ending in `data: [DONE]` [repo, `Program.cs`, `ChatEndpoints.cs`]. Three gaps remain.

**Origin and Host checks (item 3).** The MCP specification says local servers MUST validate `Origin` to prevent DNS rebinding, returning 403 if it is invalid, and SHOULD bind only to localhost ([MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)) [sourced]. The gateway has the binding but no `Origin`/`Host` check [repo]. The API key already blocks a rebinding page that cannot read the key, but a filter that rejects a present, non-allow-listed `Origin` and any `Host` other than `127.0.0.1`/`localhost` costs a few lines and closes the class. Indirect prompt injection is the other live threat. A hidden README comment made Cursor's agent hunt for and exfiltrate API keys ([HiddenLayer](https://www.hiddenlayer.com/research/how-hidden-prompt-injections-can-hijack-ai-code-assistants-like-cursor)) [sourced], and CVE-2025-53773 turned instructions hidden in repository files into file writes and code execution in Copilot agent mode ([ARMO](https://www.armosec.io/blog/indirect-prompt-injection-examples/)) [snippet]. Wrap `/read`, `/review` and law-book text in delimiters labelled as untrusted data, strip or flag invisible Unicode and HTML comments, and never let file text trigger an action. Scrub secrets before rows reach the `interactions` table. These map to OWASP's LLM01, LLM02, LLM05, LLM06 and LLM10 ([Invicti summary](https://www.invicti.com/blog/web-security/owasp-top-10-risks-llm-security-2025)) [snippet, official document not fetched].

**`/v1/models` and conformance (item 7).** The gateway exposes `/chat/completions`, `/infill`, `/status`, `/warm`, `/feedback` and `/info`, but no `/v1/models` [repo]. IDE clients use that listing. Continue takes `provider: openai` plus an explicit `apiBase` ([UCSB guide](https://docs.cloud.college.ucsb.edu/AI-LLM/API-Access/Coding-Agents/Continue-VSCode)) [snippet]. VS Code's BYOK Custom Endpoint reportedly went stable and stopped requiring GitHub sign-in in **VS Code 1.122 (May 2026)**, but a model that declares no tool support disappears from Agent mode ([Requesty guide](https://docs.requesty.ai/integrations/github-copilot.md)) [snippet]. Visual Studio's September 2026 update added a "Bring Your Own Model" preview with **custom OpenAI and Ollama endpoints**, centred on Agent Mode ([DevBlogs](https://devblogs.microsoft.com/visualstudio/visual-studio-september-update-power-your-workflow-with-your-model)) [sourced]. Rider's AI Assistant accepts an OpenAI-compatible URL, but local models appear only in chat until assigned to features ([JetBrains help](https://www.jetbrains.com/help/ai-assistant/use-custom-models.html)) [sourced]. Adding `/v1/models` and running the official OpenAI .NET SDK against the gateway as a conformance client unlocks *chat* in all of them for about half a day. Agent modes need the earlier report's tool plumbing and a model that calls tools reliably, which H-Tiny's BFCL v3 score of 57.65 does not promise. Expect chat and edit to work and agent modes to stay weak. Cline treats tool calling as required, while Roo Code falls back to XML-in-text tools, which suits a small model better ([Roo Code docs](https://docs.roocode.com/providers/openai-compatible)) [sourced].

**MCP rather than being the chat model (item 11).** A stdio MCP server, launched by the client as a subprocess with JSON-RPC over stdin and stdout ([MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)) [sourced], lets any MCP client call `law_book_search` or `jazari_review_file` while a different model chats. Stdio also avoids network exposure entirely. How clients treat a tool that takes 30 s or more is unknown, so timeouts need testing.

**Skip inline completion.** FIM needs a FIM-trained model on `/infill` or `/v1/completions` with `suffix` ([llama-server endpoints](https://mvysny.github.io/llama-server-endpoints/)) [sourced]. At about 10 tok/s, a 20-50-token completion takes 2-5 s, against the few hundred milliseconds that make completion feel usable [estimate]. Granite H-Tiny's FIM support is unverified, and no CPU latency benchmark was found.

## No small model released by November 2026 beats H-Tiny here

The new model and runtime research confirms the earlier reports' verdict and adds one candidate. IBM's Granite 4.1 (3B, 8B, 30B, April 2026) is **dense**. IBM moved away from the hybrid MoE design, and no hybrid successor to H-Tiny turned up ([NYU RITS](https://rits.shanghai.nyu.edu/ai/ibm-releases-granite-4-1-dense-8b-matches-prior-32b-moe-flagship/)) [snippet]. On this bandwidth-bound laptop, future IBM gains will therefore come at dense-3B speed (6.2 tok/s measured earlier), which weakens any "stay on IBM" roadmap. The only like-for-like rival is **Liquid AI's LFM2.5-8B-A1B** (May 2026): about 8.3B total, about 1.5B active, hybrid, 128K context, with llama.cpp support ([lavx.hu](https://news.lavx.hu/article/lfm2-5-8b-a1b-a-more-capable-on-device-mixture-of-experts-model)) [snippet]. Its predecessor's card gives HumanEval+ 69.5 and LiveCodeBench v6 21.0 ([Liquid AI blog](https://www.liquid.ai/ja/blog/lfm2-8b-a1b-an-efficient-on-device-mixture-of-experts)) [snippet], which is not clearly better than H-Tiny. At 1.5x the active parameters it would likely write at about 7-9 tok/s here [estimate]. The LFM Open License is revenue-capped, so one 45-question run is worth it only if that licence is acceptable. Every 2026 model with clearly stronger coding scores (Qwen3.6-35B-A3B, Mellum2.1 12B-A2.5B, LFM2.5-24B-A2B) reads 2.5-3.5x the bytes per token or needs more than 8 GB. On a different desktop CPU, Qwen3.5-35B-A3B ran at 5.6 tok/s against 12-13 for Qwen3-30B-A3B ([r/LocalLLaMA snapshot](https://reddit.sentinel-team.org/posts/1rei65v/snapshots/2026-02-25T19%3A22%3A50.330313Z)) [snippet].

Runtime news offers no free win for H-Tiny. llama.cpp's native MTP speculation (merged 2026-05-16) needs models trained with MTP heads, and its published gains are GPU-only ([PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)) [sourced]. ik_llama.cpp's CPU prompt-speed gains depend on the model: about 35-40% faster on Qwen3-Coder but 20-30% *slower* on Qwen3.5-35B in one comparison ([r/LocalLLaMA snapshot](https://reddit.sentinel-team.org/posts/1ruew2g/snapshots/2026-03-16T20%3A46%3A16.316967Z)) [snippet]. Whether it loads GraniteMoeHybrid at all is unverified, so it stays an optional evening experiment. OpenVINO 2026.3 added native MoE kernels and MoE disk offload, but lists no Granite or Mamba models ([release notes](https://docs.openvino.ai/nightly/about-openvino/release-notes-openvino.html)) [sourced], and disk-backed experts would break the 30 s median [estimate]. bitnet.cpp gained 1.15-2.1x in January 2026, but its x86 speed-ups are measured against llama.cpp FP16, not Q4, and no new BitNet model or code score appeared ([wavect.io](https://wavect.io/de/blog/bitnet-cpu-llm-ram-requirements/)) [snippet].

Decoding-side tricks fail the time budget. At 10 tok/s, a 1,000-token think trace adds about 100 s, so the ≤30 s median leaves room for only about 300 generated tokens after prompt reading [estimate]. Self-consistency multiplies generation time by k. It makes sense only for 5-token yes/no checks over a shared cached prefix, which is the earlier report's review re-check.

Fine-tuning should teach behaviour, not facts. Unsloth's free Colab notebook covers Granite-4.0, and Micro and Tiny "fit comfortably" on a 15 GB T4 ([Unsloth](https://unsloth.ai/docs/models/tutorials/ibm-granite-4.0)) [sourced]. A June 2026 study found fine-tuning does **not** replace retrieval once external knowledge is removed: retrieval supplies volatile API content and tuning improves how it is used ([papers.cool 2606.03657](https://papers.cool/arxiv/2606.03657)) [snippet]. RAFT found that training with distractor documents builds robustness, and that training on golden documents alone does poorly ([arXiv 2403.10131](https://arxiv.org/pdf/2403.10131)) [snippet]. So the right adapter trains "answer from the law-book passage, cite it, refuse when it is absent or irrelevant", using **dev-set-style** questions with distractor passages and no test items. Merge it and re-quantize to an all-Q4 file, because runtime `--lora` on a hybrid MoE GGUF is untested and may lose the repacked AVX2 kernels [estimate].

## Conclusion

The law book changes what "enhancement" means for Jazari. Before it, the gains were in speed and cache discipline. Now Jazari has a ground-truth source of text, and the compiler is a second ground-truth source that costs no model time. The pattern that runs through all four research areas is the same one the earlier reports found for reviews: at about one billion active parameters, quality comes from what Jazari's code verifies, not from what the model is asked to do. The compiler checks APIs, BM25 with the right weights picks sections, and paired statistics judge changes. The model's role narrows to writing and explaining. That is also why the evaluation fix ranks first. Every later item will produce changes of two or three questions on 45, and without a paired table and a pre-registered rule each one will look like either a win or noise, depending on the run.

One implication is easy to miss. The small-model RAG evidence means the law book's best outcome on the test set may be "no worse, fewer invented APIs, and a source shown" rather than a higher score. That is a legitimate reason to ship it, as long as the destroyed-known count stays at zero. Growing the test set from real misses, at a fixed test fraction chosen blind, is the only way to make future gates sharper than that. It also turns everyday use of Jazari into its own benchmark.
