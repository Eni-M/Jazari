# Keep the prompt cache warm, then tune

**On this laptop, Jazari gets faster mainly by re-reading fewer prompt tokens. Swapping runtimes or adding hardware tricks gains far less.** Measured here, Granite 4.1 3B Q4_K_M on the CPU reads prompts at about 24–35 tok/s and writes answers at 6.2 tok/s, falling to 2.8 tok/s once the prompt reaches 5k tokens ([optimization log](C:/MyOwnLLM/docs/OPTIMIZATION-LOG.md)). Every 1,000 tokens llama-server has to re-read therefore costs about 30–40 seconds. The gateway currently causes some of those re-reads itself. After every chat turn, `StateNoteUpdater` runs a background model job that rewrites the project note (up to 220 answer tokens, so roughly a minute of CPU). That note sits second in every prompt, so each rewrite changes the prompt near its start. A question asked while the job is running waits behind it. The bridge also hides what users most need to see: llama-server already reports prompt-reading progress, cached-token counts and exact token counts, and Jazari shows none of them. **Fixing the bridge comes first:** a stable prompt prefix, progress and ETA, exact token counts, cache telemetry, clean cancellation and server supervision. All of it is safe .NET work. Second, measure a few server settings on the laptop (flash attention at depth, priority, slot save/restore, the MX150 as a prompt accelerator), because measurements here have already overturned web advice twice. The paid RAM upgrade, quality-trading quants and dropping features stay with the owner. **One correction to the research notes:** the bridge notes assumed Granite 4.1 3B is a hybrid Mamba model. It is not. It is a dense transformer, so `--cache-reuse` and normal prefix reuse work as on any dense model, and the checkpoint-tuning advice in those notes does not apply.

## The gateway breaks its own cache, and the model is dense, not hybrid

**Correction, stated plainly:** `gateway_bridge.md` reasons throughout from the premise that Granite 4.1 3B is a hybrid Mamba/attention model. Its config says otherwise: `"model_type": "granite"`, `GraniteForCausalLM`, **40 layers, 40 attention heads, 8 KV heads, hidden size 2560, head size 64, and no Mamba or SSM fields** ([config.json](https://huggingface.co/ibm-granite/granite-4.1-3b/raw/main/config.json)). IBM describes the 4.1 family as dense decoder-only transformers, a return to dense design after the hybrid Granite 4.0 "H" generation, and there is no hybrid 4.1 variant ([IBM Granite 4.1 blog](https://huggingface.co/blog/ibm-granite/granite-4-1)). Three of that file's conclusions are therefore wrong:

- **`--cache-reuse` is not a no-op.** The launcher's existing `--cache-reuse 256` is valid, and KV shifting works on this model.
- **Normal prefix reuse applies.** The server keeps the longest common token prefix, as on any dense model. Reuse is not limited to resuming from saved checkpoints.
- **The checkpoint flags don't matter here.** Tuning `--checkpoint-min-step` and `--ctx-checkpoints` matters only for SWA or recurrent state, so on this model they should sit idle.

The file's process advice still stands, because prefix stability matters on any model. That covers keeping the prefix byte-stable, putting per-question context after the history, storing assistant replies exactly as streamed, compacting rarely, and showing progress and cache hits. One more consequence of a dense model: the KV cache grows linearly. At f16 it is **80 KiB per token, so 1.25 GiB at the current `-c 16384`** (arithmetic from the config). That matches the design doc's measured working sets of 3.8 GB at 4k context, 4.1 GB at 8k and 4.7 GB at 16k ([design doc](C:/MyOwnLLM/docs/superpowers/specs/2026-10-30-myownllm-design.md)).

With caching confirmed to work normally, the question becomes what stops it from working. `cache_prompt` defaults to true and reuses the longest common token prefix with the previous request ([llama.cpp server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). Any changed byte early in the prompt therefore forces everything after it to be re-read. `--cache-reuse` can sometimes rescue chunks of 256 tokens or more that only moved position. It does this by re-applying positions to the shifted keys, which its author calls "not mathematically identical" to reprocessing ([PR #9787](https://github.com/ggml-org/llama.cpp/pull/9787)). It is a safety net, not a design. Jazari's `PromptBuilder` orders the prompt as system → project note → `/read` context → history → question. That order is right only if the first three stay fixed for the whole conversation, and the note does not. `ChatEndpoints` calls `StateNoteUpdater.Record` after every answer. That queues a background request carrying the old note, the latest exchanges and `git status`, asking for a new note of up to 220 tokens, and the result replaces the note in the next prompt. Three costs follow. At 6 tok/s the job itself is roughly 40 seconds of generation plus its own prompt reading [estimate]. It evicts the chat's state from the single slot, so the next question depends on `--cache-ram` swapping that state back in ([PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391)). And the queue gives chat priority only over waiting work, not over a job already running, so a follow-up question asked within the next minute waits for the note job. **Freezing the note for the length of a conversation, and updating it only on `/status`, on exit or after real idle time, removes all three costs.**

Two smaller prefix rules follow from the same logic. First, keep `/read` context in front of the history only while it stays the same. Context that changes with each question belongs after the history, just before the question, so only that part is paid for again. Second, `PromptBuilder` currently drops the oldest question/answer pair once history overflows. That changes the prompt near its start on every overflowing turn. On a dense model `--cache-reuse` may recover the shifted history, but this hasn't been measured here. Compacting history once, at about 80% of the context, into a short summary is the cleaner policy. It costs one re-read per compaction instead of one per turn ([particula analysis](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)). Context shift is off by default and should stay off, because silently cutting early context is worse than a clear "too long" error ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)).

## A proper bridge reports progress, counts exactly and cancels cleanly

The current bridge is a thin pass-through. `LlamaClient` posts to `/v1/chat/completions`, streams only `delta.content`, and discards everything else llama-server sends. It budgets with a characters ÷ 4 estimate (`PromptBuilder.cs:48`), uses a context size of 16,384 hard-coded in `GatewayOptions`, and never checks whether the model server is healthy beyond the CLI's start-up poll. llama-server exposes everything a better bridge needs.

**Progress.** With `stream: true` and `return_progress: true`, each streamed chunk during prompt reading carries `prompt_progress {total, cache, processed, time_ms}`. That is enough for a progress bar reading "2,410 / 4,980 tokens (1,200 cached), about 1 min 31 s left", with the rate computed as `(processed − cache) / time_ms` ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). The README documents this field under `/completion`. Whether `/v1/chat/completions` honours it on build b11982 is unverified, and one curl settles it. If it does not, the gateway can render the prompt with `/apply-template` and stream from `/completion` instead.

**Cache telemetry.** The final chunk carries `timings` (`cache_n`, `prompt_n`, `prompt_ms`, `predicted_n`, `predicted_per_second`), and the OpenAI-style `usage.prompt_tokens_details.cached_tokens` is also returned ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). The gateway should forward these to the CLI as one muted end-of-turn line, for example "4,980 prompt tokens (3,700 cached) in 41 s · 312 answer tokens at 6.1 tok/s". It should also log them in `InteractionLog`. That is the only cheap way to notice when the prefix broke, and it shows the user what costs time.

**Exact counts.** `POST /apply-template` returns the rendered prompt without running the model. `POST /tokenize` then returns the exact token list. `GET /props` reports `n_ctx`, `chat_template` and `build_info` ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). The gateway should read `n_ctx` once at start-up rather than trusting its own setting, and count each new piece of a prompt once, caching the count by content hash. Tokenizing uses the same CPU as inference, so it should run before a request is queued, not while the model is generating. Earlier measurements here put this repo's C# at **9.9–11.6 tokens per line** ([earlier notes](C:/MyOwnLLM/research_notes/Whole%20laptop%20Jazari%20optimization/agent_tools_and_output.md)), so characters ÷ 4 is only roughly right.

**Cancellation.** Mainline llama-server has stopped tasks on a closed connection since December 2025, including during prompt reading ([PR #18459](https://github.com/ggml-org/llama.cpp/pull/18459)). The streaming chat path already links `HttpContext.RequestAborted` through the queue into `HttpClient`, which is correct. The non-streaming paths (`/review` parts, `/status`, JSON-schema calls) run through `HybridCache.GetOrCreateAsync`. With that wrapper, whether a caller's cancellation reaches the shared factory should be verified rather than assumed. After a cancel, the gateway can poll `GET /slots` until `is_processing` is false before starting the next job, so a cancel that fails to stop the server shows up instead of passing silently.

**Supervision and structured output.** `/health` returns 503 "Loading model" until the model is ready, then 200. `--metrics` adds Prometheus counters, and `--no-webui` and `--alias` are cheap hardening ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). Leave `--sleep-idle-seconds` off. A request that arrives just before the server goes to sleep can hang or crash it, and no fix has been released ([dev.to report](https://dev.to/homelabpm/llama-servers-sleep-mode-loses-or-crashes-on-a-request-that-arrives-just-before-it-sleeps-5e41)). For `/review`, the JSON schema already caps findings at five, but its strings are unbounded. llama.cpp compiles `maxLength` into bounded repetition and warns that unbounded constructs can make sampling "extremely slow" ([grammars README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md)). Adding `maxLength` to `quote`, `problem` and `fix` bounds both time and the classic small-model failure of never closing a string. Treat `finish_reason: "length"` as a parse failure that gets one retry.

**Pre-warming.** A `/read` of 5,000 tokens takes about three minutes to process. The gateway can send the new stable prefix with `n_predict: 0` as a background job the moment `/read` finishes ("0 evaluates the prompt without generating"), so the reading happens while the user types the question ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). This is the pattern llama.vim uses, where one request needed only **260 new tokens out of a 15,186-token context** ([PR #9787](https://github.com/ggml-org/llama.cpp/pull/9787)). Saving a warmed slot to disk (`--slot-save-path`, `POST /slots/0?action=save|restore`) could carry it across restarts. The bridge notes left this open only because of the hybrid premise, so on a dense model it should work, but it still needs one check.

## Measured settings beat web advice, and little weight is left to cut

The laptop has already contradicted published tuning advice twice, so measurements here take precedence. The memory research proposed `-t 4` and `KMP_BLOCKTIME=0` to free cores and stop idle threads spinning. Measured here, **`KMP_BLOCKTIME=0` made answers 20–28% slower, and `-t 4` with blocktime 0 was still slower than `-t 6`**. The log concludes that `-t 6` on the CPU alone was already close to the best this laptop can do without new hardware ([optimization log](C:/MyOwnLLM/docs/OPTIMIZATION-LOG.md)). Speculative decoding shows the same pattern. A Granite 4.0 350M draft on the MX150 sped up file rewriting from **5.46 to 7.95 tok/s**, but slowed reviewing from **5.47 to 2.67 tok/s**. N-gram speculation gave no real gain. Since Jazari edits by search/replace rather than whole-file rewrites, speculation stays off. `--poll 0` does nothing on this OpenMP build, because the poll setting is read only in non-OpenMP code ([ggml-cpu.c @8a199ad31](https://raw.githubusercontent.com/ggml-org/llama.cpp/8a199ad31/ggml/src/ggml-cpu/ggml-cpu.c)). It can be dropped from the launcher without effect.

On weight, the stack is already lean. The remaining cuts are small and should be ranked honestly:

| Item | Current | Change | Effect | Verdict |
|---|---|---|---|---|
| Background state-note job | Runs after every chat turn | Freeze per conversation; update on `/status`, exit or idle | Removes about 1 min of CPU per turn and a prefix break [estimate] | **Build now** |
| Context size | `-c 16384` | `-c 8192` | **About −0.6 GB, measured** (4.7 → 4.1 GB) | Optional: still within the owner's 6–8 GB budget |
| KV cache type | f16 | Keep f16 | q8_0 cost 11–19% prompt speed on CPU ([edge-cpu-gguf-tuner](https://clawhub.ai/orionshaowswmw/edge-cpu-gguf-tuner)). q4_0 output matched f16 only 8.3% on code ([InventiveHQ](https://inventivehq.com/blog/kv-cache-quantization-quality-benchmark)) | Keep |
| Weight quant | Q4_K_M | Keep; IQ4_XS is the only candidate | Q4_0 is only about 5% smaller, and uploaders call it legacy ([bartowski](https://huggingface.co/bartowski/Qwen2.5-Coder-3B-Instruct-GGUF)) | Quality floor first |
| Gateway GC | Server GC with DATAS (Web SDK default) | `<ServerGarbageCollection>false</ServerGarbageCollection>` | Smaller working set for a single-user service ([MS Learn](https://learn.microsoft.com/aspnet/core/performance/memory?view=aspnetcore-10.0)) | Build now |
| Unused `ggml-cpu-*.dll` variants | Shipped | Keep only `ggml-cpu-haswell.dll` | Tens of MB on disk, no RAM change | Trivial |

Flash attention is the one flag with real upside. The 2.8 tok/s at 5k tokens is too slow for memory bandwidth alone to explain. The weights (2.1 GB) plus about 0.4 GB of KV per token suggest about 5 tok/s, so attention compute at depth is the likely remaining cost [estimate]. `-fa` defaults to `auto` ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)), and `auto` has picked badly before, on Vulkan ([issue #27137](https://github.com/ggml-org/llama.cpp/issues/27137)). No published CPU-only measurement exists, so one `llama-bench` run at depth decides it. Priority is the other open question. `--prio -1` would keep the IDE responsive, but Windows may infer a lower quality-of-service class for low-priority threads, which can mean lower clocks ([MS Learn QoS](https://learn.microsoft.com/windows/win32/procthread/quality-of-service)). Never use Efficiency mode (EcoQoS), which "should not be used for performance critical or foreground user experiences" ([MS Learn](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)).

## The MX150 is the only idle resource worth a test, and other runtimes are not

Generation here is pinned by one DDR4 channel at about 12–13 GB/s. Any runtime that reads weights over that same bus inherits the same ceiling. The other devices were measured: the UHD 620 is slower than the CPU (12.5 / 4.1 tok/s), and splitting 24 layers onto the MX150 gave the same generation speed (6.1). The **MX150 has its own GDDR5 bus**, though, and a 1.76 GB model running entirely on it earlier reached about **12 tok/s, twice the CPU** ([earlier notes](C:/MyOwnLLM/research_notes/Whole%20laptop%20Jazari%20optimization/inference_speed.md)). Two configurations are worth one evening.

The first runs a Granite 4.1 3B quant small enough to fit the card entirely: Q3_K_M at 1.73 GB, or `UD-Q2_K_XL` at 1.41 GB ([Unsloth GGUF](https://huggingface.co/unsloth/granite-4.1-3b-GGUF/tree/main)). Use the CUDA 12.4 build, because CUDA 13 dropped Pascal ([bestllmfor](https://bestllmfor.com/guide/llm-gtx-1080-ti/)). A third-party i7-8550U + MX150 laptop ran an 8B 1-bit model fully on the card at **52 tok/s prompt and 8–9 tok/s answers**, while losing 30–40% to heat ([r/LocalLLaMA snapshot](https://reddit.sentinel-team.org/posts/1sbnf8y/snapshots/2026-04-03T21%3A20%3A24.375333Z)). The catch is quality: Q3 is below the Q4_K_M floor until the planted-bug review shows otherwise. That makes it an owner decision backed by a measurement, not a default. The second configuration keeps the Q4_K_M weights in RAM and lets op-offload send prompt batches of 32 or more tokens to the GPU ([llama-server man page](https://manpages.debian.org/unstable/llama.cpp-tools/llama-server.1.en.html)). This targets the real pain, prompt reading, and leaves answers unchanged. The earlier report suspected op-offload copies over the narrow PCIe link cancelled the gain under Vulkan ([earlier report](C:/MyOwnLLM/reports/Local%20model%20load%20optimization.md)). CUDA's integer kernels for Pascal and a large `-ub 2048` might change that, but only a benchmark can say.

Among other runtimes, only **ik_llama.cpp** has credible evidence of a gain on AVX2. Against a December 2024 mainline, its prompt processing was 2–3.6× faster on K-quants, while answers improved only modestly ([ik_llama #164](https://github.com/ikawrakow/ik_llama.cpp/discussions/164)). Mainline has since added its own Q4_K repacking, so today's gap is smaller. The maintainer has no Windows machine, and a 2026 test found the two equal on bandwidth-bound work ([ik_llama #1291](https://github.com/ikawrakow/ik_llama.cpp/discussions/1291)). It is a source-build experiment, not a migration. **OpenVINO** officially supports 6th-generation Core and later and "Intel UHD Graphics" ([OpenVINO requirements](https://docs.openvino.ai/system_requirements)). No LLM result exists for Kaby Lake or the UHD 620, and the iGPU shares the same memory channel. Ollama, KoboldCpp and LM Studio wrap llama.cpp, and LM Studio is closed source. DirectML is in sustained engineering ([MS Learn](https://learn.microsoft.com/lb-lu/windows/ai/directml/dml-min-app)). T-MAC itself warns of no guaranteed x86 gain, "especially for 4-bit token generation" ([T-MAC](https://github.com/lessw2020/T-MAC)). **Stay on mainline llama.cpp.**

## Waiting well, and asking for less, matter more than raw speed

At 6 tok/s, how the wait feels matters about as much as its length. Nielsen's long-standing guidance is to show percent-done for any operation over about 10 seconds ([NN/g](https://nngroup.com/articles/response-times-3-important-limits)). Jazari's three-minute silent prompt read breaks that rule. The progress bar described above can also be mirrored to the Windows Terminal tab and taskbar with the OSC 9;4 sequence, `ESC ] 9 ; 4 ; 1 ; <percent> BEL` ([MS Learn](https://learn.microsoft.com/en-us/windows/terminal/tutorials/progress-bar-sequences)). That lets the user switch windows and still see progress, for about ten lines of code guarded by `WT_SESSION`. Before sending, a pre-flight estimate from exact counts and the measured rate ("this /read is 4.8k tokens, about 2 min 50 s; send / outline only / cancel") prevents accidental long waits. For long `/review` runs, a detached job plus `jazari jobs` and a plain toast on completion changes waiting into leaving ([MS Learn toast](https://learn.microsoft.com/en-us/windows/uwp/design/shell/tiles-and-notifications/send-local-toast)).

Asking for less also improves quality directly. Across five models, performance fell **13.9% to 85% as input grew, even when retrieval was perfect**. Having the model recite the relevant evidence first is a measured mitigation ([Du et al., arXiv 2510.05381](https://arxiv.org/abs/2510.05381v1)). That supports a default `/read` of a folder that sends a signature outline, built with Roslyn's syntax-only parser and costing about 5–10% of the file. Full method bodies come on request, and retrieval is grep/BM25 rather than embeddings. For models under 7B, combining BM25 with semantic retrieval showed "limited or even negative impact" ([arXiv 2507.18515](https://arxiv.org/pdf/2507.18515)). One-shot and pipe modes fit a slow model because their inputs are small by nature: `jazari ask`, `git diff | jazari ask`, `jazari commit` with a `max_tokens` cap and an explicit keypress, and `jazari explain` for the last error. PrettyPrompt, already a dependency, provides persistent history, completion, multi-line input and per-prompt cancellation tokens ([PrettyPrompt](https://github.com/waf/PrettyPrompt)). Inline autocomplete is not worth building on this CPU. Every CPU reference setup uses a 0.5–1.5B coder, and llama.vscode warns quality is "significantly lower" ([llama.vscode](https://github.com/ggml-org/llama.vscode)). An editor "External Tool" that runs `jazari ask --file` gives most of the value at no cost.

### (b) Measure on the laptop first, with the exact commands

Run these from Eni-M's own terminal on AC power with Jazari's chat idle. Use `curl.exe`, not the PowerShell `curl` alias. Logs from a Claude Desktop session land under the redirected AppData path. Read the real ones at `\\localhost\C$\Users\enim\AppData\Local\MyOwnLLM\logs\llama-server.log`.

1. **Load-log facts** (KV size, flash-attention decision, repack, CPU backend):
   ```
   Select-String -Path "$env:LOCALAPPDATA\MyOwnLLM\logs\llama-server.log" -Pattern "llama_kv_cache|flash_attn|CPU_REPACK|loaded CPU backend|n_ctx"
   ```
   Expect a KV size of about 1,280 MiB at `-c 16384`.
2. **Does `/v1/chat/completions` stream `prompt_progress`?** Save a request with a long user message to `req.json`, with `"stream":true,"return_progress":true,"max_tokens":8`, then run:
   ```
   curl.exe -N http://127.0.0.1:8080/v1/chat/completions -H "Content-Type: application/json" --data-binary "@req.json"
   ```
   If no chunk contains `prompt_progress`, item (a)2 uses `/apply-template` plus `/completion`.
3. **Prefix reuse and `--cache-reuse` on the dense model.** Send the same 2k-token request twice, then again with one word changed in the first system message. Read `timings.cache_n` and `timings.prompt_n` each time:
   ```
   curl.exe -s http://127.0.0.1:8080/v1/chat/completions -H "Content-Type: application/json" --data-binary "@req.json" | Select-String '"cache_n":\d+|"prompt_n":\d+' -AllMatches
   ```
   The second run should show nearly all tokens cached. The third shows how much `--cache-reuse 256` recovers after an early change.
4. **Flash attention at depth** (most promising single flag):
   ```
   llama-bench -m C:\MyOwnLLM\models\granite-4.1-3b-Q4_K_M.gguf -dev none -t 6 -fa 0,1 -p 512 -n 64 -d 0,2048,4096 -r 3
   ```
   If `-fa 1` lifts answer speed at depth 4096 well above about 2.8 tok/s, pin `-fa on`.
5. **Priority.** Start the server twice, once with `--prio 0` and once with `--prio -1`, and send the same request from item 3. Compare `predicted_per_second`, and note how the IDE feels while it runs. Keep `--prio 0` if answers slow down.
6. **Slot save/restore across a restart:**
   ```
   llama-server -m <model> -dev none -t 6 -c 16384 -np 1 --cache-reuse 256 --slot-save-path C:\MyOwnLLM\slots --port 8080
   curl.exe -X POST "http://127.0.0.1:8080/slots/0?action=save" -H "Content-Type: application/json" -d "{\"filename\":\"warm.bin\"}"
   (restart the server)
   curl.exe -X POST "http://127.0.0.1:8080/slots/0?action=restore" -H "Content-Type: application/json" -d "{\"filename\":\"warm.bin\"}"
   ```
   Then resend the request and check that `cache_n` is close to the full prefix. If it is, build a "resume after lunch" restore keyed by prefix hash, model file and build.
7. **Cancellation.** Start a 5k-token request, press Ctrl+C in Jazari, then run `curl.exe http://127.0.0.1:8080/slots` and confirm `is_processing` turns false within a few seconds.
8. **MX150 as prompt accelerator** (needs the CUDA 12.4 zip plus cudart, installed from your own terminal):
   ```
   llama-bench -m granite-4.1-3b-Q4_K_M.gguf -dev CUDA0 -ngl 0 -ub 512,1024,2048 -b 2048 -p 2048 -n 64 -t 6
   llama-bench -m granite-4.1-3b-Q4_K_M.gguf -dev none -t 6 -p 2048 -n 64
   ```
   Adopt it only if prompt speed rises clearly and answer speed holds. Watch GPU temperature.

## Conclusion

The research changes what to optimize first. Before this round, the open questions were hardware ones: threads, devices, runtimes. Now the measurements show the hardware side is nearly exhausted short of a second RAM stick, and the gateway itself wastes about as much as any setting could recover. It runs an LLM job after every answer and puts that job's output near the start of the next prompt. That inverts the usual priority. On a machine that reads 30 tokens a second, the bridge's job is to make sure llama-server never reads the same token twice, and to tell the user the truth about how long the remaining tokens will take.

The dense-architecture correction removes a whole class of planned workarounds, such as checkpoint tuning and treating `--cache-reuse` as a no-op. What remains is ordinary prefix discipline, which is cheap and fully testable with the `cache_n` counter the server already reports. Every claim in the plan above is either measured here or falsifiable with one command. On this laptop, that standard has already overturned three pieces of plausible web advice: fewer threads, `KMP_BLOCKTIME=0` and `--poll 0`.
