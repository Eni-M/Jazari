# Quality and evaluation practices in open-source AI coding assistants (and what Jazari could adopt)

Scope: how Aider, Continue, OpenHands/SWE-agent, Agentless, Tabby, Cline/Roo Code and community/academic benchmarks measure and improve answer and edit quality, with focus on small local models, mapped onto Jazari (Granite 4.0-H Tiny, 7B total / 1B active, llama.cpp CPU, ~10 tok/s; JSON search/replace edits under grammar; 45 substring-scored questions; McNemar comparisons).

Tags used on each claim: **[sourced]** = read on the primary page this session; **[abstract-only]** = only the arXiv abstract/landing page was read; **[snippet-only]** = from a search-result snippet or a secondary site, not verified on the primary page; **[inferred]** = my reasoning, not from a source. Sources dated before 2025 are flagged **(pre-2025, possibly outdated)**. Research date: 2026-11-03.

Jazari's own harness files (for reference): `C:\MyOwnLLM\eval\run_eval.py`, `score.py`, `compare.py`, `recall.py`, `gateway.py`, `test_questions.py`.

## 1. Which edit and output formats do small models (<=8B, ideally <=3B active) handle best, by published numbers?

### Takeaway
Every published small-model number points the same way: models under ~7B are most reliable when they emit plain text (whole file or plain SEARCH/REPLACE blocks), and they lose accuracy when code is wrapped in JSON or forced through a hard schema, even though the schema guarantees parseable output. Search/replace beats unified diff at every size where any format works (1.5B up), but diff *generation* at 1-3B is still poor in absolute terms (EM 0.14-0.20), so Jazari's JSON-plus-grammar edit format is the configuration the evidence is most skeptical about.

### Cited Findings
- **Aider code-editing leaderboard (133 Python Exercism tasks, page last updated 2025-04-12; leaderboard now superseded by polyglot).** Every <=8B row uses the `whole` format: Qwen2.5-Coder-7B-Instruct 57.9% (100% well-formed), Qwen2.5-Coder-3B 39.1%, 1.5B 31.6%, 0.5B 14.3%, llama-3.1-8b-instruct 37.6%, llama3.2:3b fp16 26.3% (97.0% well-formed), **ollama/granite3-dense:8b 20.3% with only 78.9% correct edit format** [sourced] — [Aider edit leaderboard](https://aider.chat/docs/leaderboards/edit.html)
- Aider describes `whole` as "the easiest format for an LLM to use" but token-hungry; `diff` (SEARCH/REPLACE blocks) is efficient; `udiff` was introduced to stop GPT-4 Turbo "lazy coding"; `diff-fenced` exists because Gemini fails diff's fencing; `editor-diff`/`editor-whole` are slimmed formats for the editor model in architect mode [sourced] — [Aider edit formats](https://aider.chat/docs/more/edit-formats.html)
- **Qwen2.5-Coder technical report, Aider benchmark pass@1 / pass@2:** 0.5B 14.3/14.3; 1.5B 28.6/31.6; 3B 33.8/39.1; 7B 55.6/68.4 (the report's prose gives 51.9 for 7B pass@1, conflicting with its own table) [sourced] (Sept 2024, pre-2025, possibly outdated) — [Qwen2.5-Coder report](https://arxiv.org/html/2409.12186)
- **Diff-XYZ (JetBrains Research, NeurIPS 2025 workshop, v2 2025-11-17)**, Qwen2.5-Coder family, diff *generation* exact match by format: 1.5B search-replace 0.20 vs udiff 0.00 / udiff-h 0.01; 3B search-replace 0.14 vs udiff 0.01; 7B search-replace 0.28 vs udiff 0.06; 32B search-replace 0.68 vs udiff 0.23. Verbose `udiff-l` scored ~0 at all sizes. *Applying* a given diff becomes reliable only around 7B (udiff Apply EM: 1.5B 0.11, 3B 0.36, 7B 0.59, 14B 0.82). Authors: small models "still struggle regardless of representation"; search-replace wins partly because it avoids global constraints like hunk-header line numbers [sourced] — [Diff-XYZ](https://arxiv.org/html/2510.12487)
- A secondary benchmark page claims small models benefit from verbose udiff-l; the paper's own Table 5 contradicts it (udiff-l near zero) [snippet-only; contradicted by primary] — [alphaXiv page](https://alphaxiv.org/benchmarks/jetbrains-research/diff-xyz); contradicted by [Diff-XYZ](https://arxiv.org/html/2510.12487)
- **Aider polyglot leaderboard (225 hard Exercism tasks in C++, Go, Java, JS, Python, Rust; page updated 2025-11-20), open models <=32B:** Qwen3 32B 40.0% (diff, 83.6% well-formed); QwQ-32B solo 20.9% (diff, 67.6% well-formed) vs QwQ-32B architect + Qwen2.5-Coder editor 26.2% (100% well-formed); Qwen2.5-Coder-32B 16.4% with `whole` (99.6% well-formed) vs 8.0% with `diff` via a different provider (71.6% well-formed); openhands-lm-32b 10.2%; gemma-3-27b 4.9%. No 7B/8B or Qwen3-30B-A3B rows exist [sourced] — [Aider leaderboards](https://aider.chat/docs/leaderboards/)
- **Aider "LLMs are bad at returning code in JSON" (2024-08-14):** Claude 3.5 Sonnet, DeepSeek Coder V2, GPT-4o (two versions), 133 Python tasks x 5 runs. All models scored lower when returning code inside JSON (tool call) than in markdown fences; OpenAI strict mode gave no improvement over non-strict JSON; JSON produced more SyntaxError/IndentationError; Sonnet had no syntax errors yet still scored lower, suggesting JSON hurts problem-solving itself [sourced] (pre-2025, large models only, possibly outdated) — [Aider code-in-JSON](https://aider.chat/2024/08/14/code-in-json.html)
- **"The Constraint Tax" (arXiv 2605.26128, May 2026), Qwen2.5-0.5B/1.5B and SmolLM2-1.7B, 15,000 generations:** hard schema decoding raised schema validity 61.5% -> 100% but cut answer accuracy 19.7% -> 11.0%; wrong-but-valid outputs rose 49.5% -> 88.9%. On a tool-call task Qwen2.5-1.5B dropped from 91.5% executable accuracy (prompt-only JSON) to 48.0% (hard schema), both 100% schema-valid. Author says 3B still pays the tax; recommends "reason free, constrain late" and reporting validity, accuracy, executable accuracy and wrong-valid rate separately [abstract-only] — [Constraint Tax](https://arxiv.org/abs/2605.26128)
- **"Constrained Decoding Eliminates Structural Failures in Small LLMs but Reveals a Scale-Dependent Semantic Gap" (arXiv 2609.23742, Sept 2026), five 0.6B-4B models, 14 tasks, Outlines and XGrammar:** validity 78.6-92.9% -> 100%; type-coercion failures fixed; instruction-semantic failures (multi-step function calling) not fixed; schema conformance "necessary but not sufficient" [abstract-only] — [Chavan 2026](https://arxiv.org/abs/2609.23742)
- **"The Format Tax" (arXiv 2604.03616, April 2026):** requiring JSON/XML/LaTeX/Markdown output degrades reasoning and writing across six open-weight models; most of the loss comes from the format *instructions in the prompt*, not the decoder constraint; decoupling (free-form first, reformat in a second pass, or thinking before formatting) recovers most of the loss; recent closed models show little tax [abstract-only] — [Format Tax](https://arxiv.org/abs/2604.03616)
- "Let Me Speak Freely?" (Aug 2024) reported JSON-restricted prompts lowering reasoning accuracy [snippet-only] (pre-2025, possibly outdated) — [arXiv 2408.02442](https://arxiv.org/html/2408.02442v1)

### Inferences
- [inferred] Jazari's grammar-constrained JSON edit is the exact pattern the 2026 small-model papers measure as harmful: it guarantees `parse_rate = 100%` while possibly lowering `edit_correct_rate`. A 100% parse rate in Jazari's harness is therefore not evidence the format is good. JSON also forces the model to escape C# string literals, quotes, backslashes and newlines inside JSON strings, which is the failure mode Aider observed (more syntax errors).
- [inferred] **Adoptable experiment (cheap, uses existing McNemar tooling):** run the /edit scenario set under three arms with identical prompts otherwise: (A) current JSON+grammar; (B) plain aider-style `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` blocks parsed by a tolerant parser, no grammar; (C) "reason free, constrain late": the model writes the new code in a fenced block first, then a second short constrained pass (or deterministic code) packages it into the JSON search/replace pair. Score each on four separate metrics (parse, apply, compiles, task-correct) and compare task-correct with exact McNemar. Granite3-dense:8b's 78.9% well-formed rate on Aider suggests the grammar may still be worth keeping as a fallback for arm B's parse failures.
- [inferred] Consider a **"replace whole method"** variant for C#: Aider's data says small models do best with `whole`, and a C# method is a natural, bounded unit (find it by Roslyn/tree-sitter, have the model rewrite only that method). This keeps the token cost bounded at ~10 tok/s while avoiding exact-match SEARCH text, which Diff-XYZ shows is hard below 7B.
- [inferred] Jazari's whitespace-tolerant line match is the right instinct; Diff-XYZ attributes search-replace's advantage to avoiding line numbers and global constraints, so never add line numbers to the edit schema.

### Gaps
- No published edit-format comparison for Granite 4.0 (any size) or for a ~1B-active MoE; no Aider rows for Qwen3-30B-A3B (3B active) or any 2025-2026 <=8B model on polyglot. Small-model edit numbers above are Python, not C#.
- The 2026 constrained-decoding papers were read at abstract level only; model lists (2604.03616, 2609.23742) and per-task numbers were not verified. None tests code edits specifically.
- Aider's code-in-JSON result covers large 2024 models only.

## 2. What automated feedback loops (lint, compile, tests, retries) do these tools use, and what do they gain on small models?

### Takeaway
Aider (lint after every edit by default, optional auto-test), SWE-agent (linter guardrail that rejects syntactically broken edits) and Agentless (sample many patches, filter by regression/reproduction tests, majority vote) all close the loop with tool feedback; the measured gains are +3 points for a lint guardrail (SWE-agent, GPT-4 Turbo), +3 to +13 points for one test-feedback retry on 1.5B-7B models (Qwen Aider pass@1 -> pass@2), and +6.3 points from test-based patch selection (Agentless). A single compile-error retry is the best-evidenced, cheapest loop for Jazari; multi-sample selection is likely too slow at 10 tok/s except as a fallback.

### Cited Findings
- **Aider:** "By default, aider will lint any files which it edits" (`--no-auto-lint` to disable); `--lint-cmd` must print errors and exit non-zero; `--test-cmd` + `--auto-test` runs tests after each AI edit and aider "will try and fix any errors"; for compiled languages it suggests `--lint-cmd` to compile changed files or `--test-cmd` such as `dotnet build && dotnet test` [sourced] — [Aider lint/test](https://aider.chat/docs/usage/lint-test.html)
- **Aider built-in linter (2024-05-22):** tree-sitter parses each edited file and finds `ERROR` nodes; instead of raw `file:line:col` messages the LLM is shown each flagged line inside its enclosing function/method/class with the rest of the file elided; the fix loop "may iterate a few times"; no quantitative benefit published [sourced] (pre-2025, possibly outdated) — [Aider linting blog](https://aider.chat/2024/05/22/linting.html)
- **Aider benchmark harness** reports `pass_rate_1`, `pass_rate_2` ("percent of the tasks which had all tests passing"; number of entries depends on `--tries`), example 57.1 -> 77.4, plus `percent_cases_well_formed`, `num_malformed_responses`, `syntax_errors`, `indentation_errors`, `lazy_comments`, `exhausted_context_windows`, `test_timeouts`, `seconds_per_case` [sourced] — [Aider benchmark README](https://github.com/Aider-AI/aider/blob/main/benchmark/README.md)
- The README does not say what is fed back on the second try; Aider's older benchmark write-ups describe sending the failing test output back to the model [inferred from memory of Aider's 2023 benchmark blog; not re-verified this session].
- **Gain from one retry on small models** (Aider benchmark, Qwen2.5-Coder instruct, pass@1 -> pass@2): 0.5B +0.0; 1.5B +3.0; 3B +5.3; 7B +12.8 points [sourced] (Sept 2024, pre-2025) — [Qwen2.5-Coder report](https://arxiv.org/html/2409.12186)
- **SWE-agent ACI ablations (SWE-bench Lite, GPT-4 Turbo):** edit with linting guardrail 18.0% vs without 15.0% vs no edit command 10.3%; file viewer 100-line window 18.0% vs 30 lines 14.3% vs full file 12.7%; keeping last 5 observations 18.0% vs full history 15.0%; summarized search 18.0% vs iterative search 12.0% (worse than no search, 15.7%). Four principles: simple actions, compact actions, "informative but concise" feedback, guardrails. Llama 3 and DeepSeek Coder were tried and found "subpar" in the agent setting, partly due to context length [sourced] (May 2024, pre-2025, possibly outdated) — [SWE-agent paper](https://arxiv.org/html/2405.15793)
- **Agentless (SWE-bench Lite, 300 issues):** 40 sampled search/replace patches per issue; majority voting alone 25.67%; + regression-test filtering 27.00%; + reproduction-test filtering 32.00%; oracle upper bound if any sample counted 42.0%; plateau around 40 samples; ~$0.70 and ~78K tokens per issue; greedy single location set 88 fixes vs 96 with 4x10 sampling [sourced] (2024, pre-2025) — [Agentless](https://arxiv.org/html/2407.01489)
- **C# is harder for agents:** SWE-Sharp-Bench (150 C# tasks, 17 repos, Microsoft Research, Nov 2025) best result OpenHands + GPT-5 47.3%; SWE-agent + Claude Sonnet 3.7 solves 62.4% of Python SWE-bench Verified but 30.67% of C# tasks; C# gold patches average 4.88 files, 10 hunks, 131 lines; median repo ~235k LoC; regression controlling for patch complexity still finds a language effect. Only proprietary models evaluated [sourced] — [SWE-Sharp-Bench](https://arxiv.org/html/2511.02352v2)

### Inferences
- [inferred] **Highest-value loop for Jazari:** after the existing C# syntax check, run a *semantic* compile of the edited file in context (Roslyn diagnostics, or `dotnet build` on the project when one exists), and on failure send **one** retry containing only the error lines plus the enclosing method (Aider's tree-sitter context trick; SWE-agent's "informative but concise"). Cap at one retry: Qwen's +3 to +5 points at 1.5-3B suggests modest but real gains; 0.5B gained nothing, so a 1B-active model is near the floor and more retries are unlikely to pay. At ~10 tok/s a 150-token retry costs ~15 s plus prompt processing [inferred estimate].
- [inferred] Jazari's eval should report `pass_rate_1` and `pass_rate_2` for /edit (with and without the retry) so the McNemar test can show whether the loop helps on Granite specifically.
- [inferred] Agentless-style sampling (N=10-40) is unaffordable interactively at 10 tok/s (N x edit length). A bounded variant is plausible: only when the first edit fails to apply or compile, sample 2-3 alternatives at higher temperature and keep the first that applies and compiles.
- [inferred] Keep views short: SWE-agent found a 100-line window beat full-file views. For /read and /review on large C# files, showing the relevant ~100 lines (method plus neighbours) is likely better for a 1B-active model than whole files, independent of context length.
- [inferred] For /review, the planted-password check is a single-signal test; Agentless's finding that ~10% of SWE-bench issues lacked enough information is a reminder to audit each eval item for ambiguity before trusting failures.

### Gaps
- No published ablation of lint/compile retry loops on <=3B models specifically (Qwen's pass@2 is the closest). No C#/.NET numbers for any small model in a feedback loop.
- Aider's exact retry limit and feedback content were not confirmed on the current docs.

## 3. How do they evaluate cheaply and avoid overfitting (held-out sets, contamination checks, statistical tests)?

### Takeaway
The projects keep evals cheap by using small, hard, executable task sets, dropping items every model solves, stamping every run with code version and settings, and reporting several failure counters instead of one score; contamination is handled by date windows (LiveCodeBench), n-gram decontamination (Qwen) and manual filtering of flawed tasks (Agentless, SWE-Sharp-Bench). None of the tool projects publishes a held-out/dev split or significance testing as a routine practice, so Jazari's McNemar test is already ahead of Aider's leaderboard; its weakest point is substring scoring, which execution-based benchmarks show inflates scores.

### Cited Findings
- **Polyglot construction:** 697 Exercism problems in 6 languages; 7 models attempted all; 258 solved by all were dropped; kept 225 solved by <=3 models (66 solved by none); goal is top models scoring ~5-50%; created because the old 133-task benchmark saturated above 80% where new records added only 1-2 solved problems. No contamination discussion [sourced] (Dec 2024, pre-2025) — [Aider polyglot blog](https://aider.chat/2024/12/21/polyglot.html)
- **Run hygiene in Aider's harness:** results record model, edit format, aider version and git commit hash, marked "(dirty)" with uncommitted changes; recommends committing before a run; `--num-tests` and `--keywords` for partial runs; `--stats` reports on in-progress runs; runs in Docker because it executes model-written code [sourced] — [Aider benchmark README](https://github.com/Aider-AI/aider/blob/main/benchmark/README.md)
- Aider's code-in-JSON study ran each model x format 5 times and judged a 0.4-point gap "within the margin of error for 5 trials" [sourced] (pre-2025) — [Aider code-in-JSON](https://aider.chat/2024/08/14/code-in-json.html)
- **LiveCodeBench:** problems from weekly LeetCode/AtCoder/CodeForces contests tagged with release dates; models are scored only on problems after their cutoff; DeepSeek-Instruct dropped on problems released after Sept 2023 and GPT-4o dropped after its Nov 2023 cutoff, read as contamination; repo supports `--start_date/--end_date` [snippet-only, from search results citing the paper] (paper 2024, pre-2025) — [LiveCodeBench](https://arxiv.org/html/2403.07974v2)
- A 2026 commentary argues date windows reduce but do not eliminate exposure, and that gaps can also come from difficulty or prompt policy [snippet-only, secondary] — [benchlm.ai](https://benchlm.ai/md/blog/posts/livecodebench-contamination-free.md)
- **Qwen2.5-Coder decontamination:** removed any training example with a 10-gram word-level overlap with HumanEval, MBPP, GSM8K, MATH [sourced] (pre-2025) — [Qwen2.5-Coder report](https://arxiv.org/html/2409.12186)
- **Weak tests inflate scores:** Granite 4.0-H Tiny instruct scores HumanEval 83 vs HumanEval+ 76, MBPP 80 vs MBPP+ 69 (the "+" versions add many more tests to the same problems) [sourced] — [Granite 4.0-H Tiny model card](https://huggingface.co/ibm-granite/granite-4.0-h-tiny)
- **Flawed-task filtering:** Agentless found ~10% of SWE-bench Lite issues lacked information to solve, ~5% had misleading suggested solutions, ~4.3% contained the exact fix; built a 249-issue filtered subset (rankings shifted only slightly) [sourced] (pre-2025) — [Agentless](https://arxiv.org/html/2407.01489)
- **SWE-Sharp-Bench verification:** keeps only instances whose tests go pass -> fail -> pass across base / base+test patch / base+test+fix; two authors manually annotated each item for underspecification and misaligned tests; normalizes NUnit/xUnit/MSTest output; no explicit contamination test (53% of issues from 2024) [sourced] — [SWE-Sharp-Bench](https://arxiv.org/html/2511.02352v2)
- **Separate metrics, not one score:** Diff-XYZ reports exact match, IoU, apply rate and parsing rate separately [sourced] — [Diff-XYZ](https://arxiv.org/html/2510.12487); Constraint Tax recommends reporting schema validity, answer accuracy, executable accuracy and wrong-but-valid rate separately [abstract-only] — [Constraint Tax](https://arxiv.org/abs/2605.26128)
- **Statistics:** Miller, "Adding Error Bars to Evals" (Nov 2024) gives formulas for analyzing eval data, measuring differences between two models and planning an experiment [abstract-only; specific recommendations such as paired/clustered errors not verified this session] (pre-2025) — [arXiv 2411.00640](https://arxiv.org/abs/2411.00640)
- **C#/.NET-specific benchmarks available:** MultiPL-E includes C# (Qwen2.5-Coder instruct C# scores: 0.5B 62.7, 1.5B 64.6, 3B 78.5, 7B 80.3) [sourced] (pre-2025) — [Qwen2.5-Coder report](https://arxiv.org/html/2409.12186); SWE-Sharp-Bench for repo-level C# [sourced] — [SWE-Sharp-Bench](https://arxiv.org/html/2511.02352v2); "Benchmarking the Titans" .NET code-quality study (arXiv 2608.22529) and a self-reported dotnet-coder-14b fine-tune (97% compile rate on ~30 tasks) exist but were not verified [snippet-only] — [arXiv 2608.22529](https://arxiv.org/pdf/2608.22529), [dotnet-coder-14b](https://huggingface.co/zipaltrivedi/dotnet-coder-14b/blob/main/README.md)

### Inferences
- [inferred] **Split the 45 questions into dev and held-out.** Tune prompts/sampling only against dev; run held-out only to confirm a change before merging. With 45 items this is thin, so grow the held-out set with new items written *after* each tuning round (a LiveCodeBench-style date stamp per item), and record the date each item was added.
- [inferred] **Prune saturated items** (pass under every config for N runs) into a "regression canary" bucket, like polyglot did, so McNemar's discordant pairs come from items that actually discriminate; McNemar only gains power from discordant items anyway.
- [inferred] **Add execution where cheap.** For questions whose answer is code, compile the extracted code block (Roslyn `CSharpCompilation` with reference assemblies, or `dotnet build` on a scratch project) and, where feasible, run 2-5 xUnit asserts. Granite's 7-11 point drop from HumanEval to HumanEval+ is a direct warning that weak checks (substrings are weaker than tests) overstate quality. Keep required/forbidden substrings for prose and security facts.
- [inferred] **A cheap external C# yardstick:** MultiPL-E's C# split (HumanEval translated, ~160 problems) gives a comparable number for Granite vs Qwen-class models. Rough cost at ~10 tok/s and ~200 output tokens per problem: ~55 min generation plus prompt processing [inferred estimate], i.e., an overnight job, not per-commit.
- [inferred] **Stamp every run** with Jazari git hash + dirty flag, GGUF file hash/quant, llama.cpp build, sampling params and seed (Aider README pattern), and report per-scenario failure counters (parse fail, apply fail, compile fail, wrong answer, timeout, seconds per case) alongside pass rate.
- [inferred] Because Jazari samples at temperature 0.2 (not greedy), single runs are noisy; either fix the seed for A/B runs or run each item k times (k=3) and compare per-item pass rates, which is what Aider's 5-trial study did.

### Gaps
- No tool project (Aider, Continue, Cline, Roo, Tabby) documents a held-out/dev split or significance tests for its own prompt changes; Aider leaderboards publish single runs.
- EvalPlus, BigCodeBench and LiveCodeBench primary pages were not fetched this session; numbers for those come only via model cards or snippets.
- No found C#-specific function-level benchmark beyond MultiPL-E with independent small-model results; "Benchmarking the Titans" content unverified.

## 4. How do they collect user feedback/telemetry (opt-in, local-only) and turn it into improvements?

### Takeaway
Continue logs development data locally by default (`.continue/dev_data`) with versioned event schemas and optional custom destinations, and Tabby reports completion acceptance rate, total completions and acceptances per language and user; both treat implicit accept/reject signals as the main quality metric. I found no primary source showing any of these projects turning thumbs up/down into a fine-tune; the documented improvement levers are per-role model routing (Continue), compact or per-mode prompts (Cline, Roo) and choosing models by measured acceptance.

### Cited Findings
- **Continue dev data:** "automatically collects data on how you build software"; saved locally to `.continue/dev_data` by default; custom destinations (HTTP endpoints, local directories) in the `data` section of `config.yaml`; an HTTP destination receives a JSON event blob tagged with a schema version; event schemas live in source code; page links to a blog post on why to collect this data. No opt-in setting is described [sourced] — [Continue development data](https://docs.continue.dev/customize/deep-dives/development-data)
- **Continue model roles:** chat, autocomplete, edit, apply ("used to decide how to apply edits to a file"), embed, rerank; assigned per model in `config.yaml` via `roles` [sourced] — [Continue model roles intro](https://docs.continue.dev/customize/model-roles/00-intro)
- A third-party guide advises using a fast, usually smaller, model for the autocomplete role [snippet-only, secondary] — [Merge gateway guide](https://docs.merge.dev/merge-gateway/coding-agents/continue-dev)
- **Tabby (self-hosted) Reports page:** tracks "Acceptance Rate, Total Completions, and Total Acceptances" for code completion, filterable by language and time range, team and individual views; chat usage tracked across IDE and Answer Engine [sourced] — [Tabby usage analytics](https://tabby.tabbyml.com/docs/administration/usage-analytics/)
- Tabby collects usage stats for the Tabby team by default; disable with `TABBY_DISABLE_USAGE_COLLECTION`; an Events API logs completion acceptance and other client events [snippet-only] — [Tabby usage collection](https://tabby.tabbyml.com/docs/administration/usage-collection/), [Tabby Events API listing](https://apis.io/apis/tabby-ml/tabby-ml-events-api/)
- **Cline:** for local models enable "Use Compact Prompt" (Settings -> Features); "Keep tasks focused (smaller context = faster responses)"; "Start a new task when context gets too large" [sourced] — [Cline local models read-me-first](https://docs.cline.bot/running-models-locally/read-me-first). Search snippets add that the compact prompt cuts prompt size ~90% and that Cline recommends Qwen3 Coder 30B [snippet-only] — [Cline local models overview](https://docs.cline.bot/running-models-locally)
- **Roo Code:** per-mode system prompt override via `.roo/system-prompt-{mode-slug}` ("footgun prompting"), which replaces standard tool-use instructions and shows a warning icon when active [snippet-only] — [Roo footgun prompting](https://docs.roocode.com/features/footgun-prompting); Roo's local-models page (updated 2026-05-15) warns local models "may not always match the capabilities of the largest, most advanced cloud models" and often lack prompt caching; suggests a smaller model if speed is a problem [sourced] — [Roo local models](https://roocodeinc.github.io/Roo-Code/advanced-usage/local-models)

### Inferences
- [inferred] Jazari's interactions table already matches Continue's local-first model. Two cheap upgrades: (1) add a `schema_version` column/field like Continue's events so later fine-tuning exports survive format changes; (2) log **implicit** signals that are far more plentiful than thumbs: edit proposed / applied by match tier (exact vs whitespace) / rejected by syntax check / declined by user at confirm / user re-asked the same question within N turns. Then report a Tabby-style **edit acceptance rate** per command and per week, which is a production metric that complements the offline eval.
- [inferred] Turn logged failures into eval items: every thumbs-down or declined edit is a candidate held-out test (after the user approves it and secrets are scrubbed). This feeds the "grow held-out over time" practice from section 3 without any telemetry leaving the machine.
- [inferred] For a future LoRA, the most useful pairs are (prompt, accepted edit) and (prompt, rejected edit) for preference tuning; plain thumbs-up answers are lower value. Keep this opt-in and local, as now.
- [inferred] Model routing (Continue's roles) is mostly irrelevant on a 16 GB CPU laptop running one model, but one role split is cheap: if a smaller/faster model (or the same model with a shorter prompt) is used for "apply"/packaging only, it can follow a free-form answer, matching the "constrain late" pattern from section 1.

### Gaps
- No primary source found showing Continue, Tabby, Cline or Roo converting thumbs feedback into fine-tunes or automatic prompt changes; Continue's linked blog post on dev data was not read.
- Exact Continue event names/fields and Tabby's acceptance-rate formula (per suggestion vs per session) were not verified.
- Cline's compact-prompt contents and the 90% figure were not verified on the primary page.

## 5. Techniques for making tiny models more reliable (architect/editor split, self-consistency, constrained decoding, prompt patterns, repo conventions files)

### Takeaway
The best-evidenced levers for small models are: separate reasoning from formatting (architect/editor split or "reason free, constrain late"), keep inputs and outputs short and local (100-line windows, compact prompts, focused tasks), add guardrails that reject broken edits, and supply project conventions as a short read-only file. Self-consistency/majority voting works (Agentless +6 points from test-filtered selection) but costs N times the tokens, which at 10 tok/s makes it a failure-path tool, not a default.

### Cited Findings
- **Architect/editor (Aider, 2024-09-26):** architect describes the solution freely; editor turns it into edits. Pass rates vs solo: gpt-4o-mini paired with itself 60.2% vs 55.6% solo (whole); gpt-4o 75.2% vs 71.4%; Claude 3.5 Sonnet 80.5% vs 77.4%; o1-mini + DeepSeek editor 71.4% vs o1-mini solo 61.1%. Motivated by reasoning models that produce badly formatted edits. Whole-format editor runs called slow and probably impractical interactively. No small/local models tested [sourced] (pre-2025, possibly outdated) — [Aider architect blog](https://aider.chat/2024/09/26/architect.html)
- Later polyglot data with open models: QwQ-32B solo 20.9% (67.6% well-formed) vs QwQ-32B architect + Qwen2.5-Coder editor 26.2% (100% well-formed), 2025-03 [sourced] — [Aider leaderboards](https://aider.chat/docs/leaderboards/)
- **Decoupling reasoning from formatting** recovers most accuracy lost to format requirements [abstract-only] — [Format Tax](https://arxiv.org/abs/2604.03616); "reason free, constrain late" [abstract-only] — [Constraint Tax](https://arxiv.org/abs/2605.26128)
- **Constrained decoding** fixes structure (100% validity) but not semantics in 0.6B-4B models [abstract-only] — [Chavan 2026](https://arxiv.org/abs/2609.23742)
- **Self-consistency / selection:** Agentless majority voting over AST-normalized patches + test filtering, plateau at ~40 samples, 32.0% vs 25.67% majority-only [sourced] (pre-2025) — [Agentless](https://arxiv.org/html/2407.01489)
- **Interface design (ACI):** simple, compact actions; concise feedback; guardrails; 100-line window and last-5-observation history beat full file / full history [sourced] (pre-2025) — [SWE-agent paper](https://arxiv.org/html/2405.15793)
- **Agentless localization** uses compact "skeleton" views of files (signatures) which it says works better than full contents [sourced] (pre-2025) — [Agentless](https://arxiv.org/html/2407.01489)
- **Conventions files:** Aider loads `CONVENTIONS.md` read-only via `/read` or `--read` (or `read:` in `.aider.conf.yml`), cached when prompt caching is on; the example (prefer httpx, add type hints) changed output only when loaded; community repo at github.com/Aider-AI/conventions [sourced] — [Aider conventions](https://aider.chat/docs/usage/conventions.html)
- **Compact prompts for local models** (Cline) and per-mode prompt overrides (Roo) [sourced/snippet-only as noted in section 4] — [Cline](https://docs.cline.bot/running-models-locally/read-me-first), [Roo footgun prompting](https://docs.roocode.com/features/footgun-prompting)
- **Model capability context for Jazari:** Granite 4.0-H Tiny (released 2025-10-02; 7B total / 1B active): HumanEval 83, HumanEval+ 76, MBPP 80, MBPP+ 69, CRUXEval-O 39.63, BigCodeBench 41.06, IFEval average 81.44, BFCL v3 (tool calling) 57.65; recommended sampling not stated on the card [sourced] — [Granite 4.0-H Tiny model card](https://huggingface.co/ibm-granite/granite-4.0-h-tiny)
- Larger local alternatives the communities recommend: Devstral Small 24B reported 46.8% SWE-bench Verified with OpenHands (May 2025) [snippet-only, model-card mirror] — [Devstral Small 2505](https://cnb.cool/ai-models/mistralai/Devstral-Small-2505); Cline recommends Qwen3 Coder 30B [snippet-only] — [Cline local models](https://docs.cline.bot/running-models-locally); these exceed a 16 GB CPU laptop's comfortable budget [inferred].

### Inferences
- [inferred] **Single-model architect/editor for /edit:** pass 1 (free text, no grammar): "describe the change and write the new method body"; pass 2 (grammar-constrained, short): package into search/replace JSON, or do it deterministically by locating the method. Self-pairing helped gpt-4o-mini by +4.6 points and fixed QwQ's 67.6% well-formed rate; the 2026 small-model papers predict the same direction. Cost: roughly doubles /edit latency; measure it in the timed scenario before adopting.
- [inferred] **Reasoning-before-answer in any schema:** if JSON stays, order fields so any free-text "plan/why" field comes before the `search`/`replace` fields (the Constraint Tax's wrong-but-valid failure is worst when the answer is forced first) [inferred; the field-ordering advice is from secondary blog snippets, not verified].
- [inferred] **Conventions file:** support a short project file (e.g., `JAZARI.md` or reuse `AGENTS.md`/`CONVENTIONS.md` if present) loaded read-only into the system prompt, with a hard size cap. On CPU, prompt processing time grows with every token, so cap it (a few hundred tokens) and measure with the timed scenarios. Good C# content: target framework, nullable on/off, minimal APIs vs controllers, EF Core vs Dapper, test framework, logging library, "never hardcode secrets, use user-secrets / Key Vault".
- [inferred] **Self-consistency, bounded:** for short factual answers, k=3 samples with a majority/agreement check is affordable only for very short outputs (~50 tokens -> ~15 s at 10 tok/s); for edits, use "sample again only on apply/compile failure" rather than up-front voting. Use compilation as the verifier (Agentless used tests), since majority voting alone gave the smallest gain in Agentless.
- [inferred] **Keep context local and short** (SWE-agent 100-line window, Agentless skeletons): for /edit and /review on C#, send the target method plus a signature-only skeleton of the file rather than whole files; this also cuts CPU prompt-processing time.
- [inferred] **Sampling:** temperature 0.2 / min_p 0.05 is in the normal range for code; no source here measured sampling settings for Granite. If edits are generated twice (architect/editor), the editor pass can be greedy (temperature 0) since it is a transcription task [inferred].
- [inferred] **What not to adopt yet:** full agent loops (SWE-agent/OpenHands) — the SWE-agent paper found Llama 3 / DeepSeek Coder subpar as agents, Aider polyglot shows even 32B models at 8-40%, and C# repo tasks average ~5 files per fix; a 1B-active model at 10 tok/s will not sustain multi-turn tool use. Granite's BFCL v3 of 57.65 also suggests tool calling is a weak spot.

### Gaps
- No published architect/editor or self-consistency results for <=8B models; all architect numbers are for large models (2024) or 32B (2025).
- No source measured conventions-file effects quantitatively (Aider's example is anecdotal).
- No Granite-specific guidance on edit formats, sampling or prompt style was found; IBM's card does not state recommended sampling.
- Mini-swe-agent and OpenHands' own small-model guidance were not verified this session.
