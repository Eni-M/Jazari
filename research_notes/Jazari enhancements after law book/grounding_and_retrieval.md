# Grounding and retrieval for Jazari beyond the law book

Scope note (read first). Researched 2026-11-02. Network limits in this session: arxiv.org, aider.chat, sqlite.org and huggingface.co could not be fetched directly (DNS block or proxy 403). arXiv content below therefore comes from search-engine summaries of the papers, not from reading them, and is marked "[snippet]". GitHub raw files, github.com pages and Microsoft Learn could be read, and repository facts marked "[checked]" were verified directly (files counted from a shallow clone of dotnet/dotnet-api-docs at its 2026-10-29 commit).

Things the earlier reports already cover, and which these notes do not repeat: Roslyn syntax-only signature skeletons for `/read`; the Roslyn syntax gate and `dotnet build` after edits; "BM25 80/95% vs dense 25/45%" from the Italian bench; "absence can't be scored" and the anti-invention check; Du et al. (2510.05381), where performance falls 13.9–85% as input grows; and arXiv 2507.18515, where BM25+semantic hybrid had "limited or even negative impact" for models under 7B. Where the new findings point the same way, they are added as more evidence.

## 1. API reference grounding (dotnet/dotnet-api-docs and alternatives)

### Takeaway
dotnet/dotnet-api-docs is a good, permissively licensed source for exact signatures and overloads of the BCL and Microsoft.Extensions (13,707 ECMA XML files, CC-BY-4.0 text and MIT code, current through .NET 11). It does **not** contain ASP.NET Core or EF Core API reference. So for Jazari's main domain the signatures have to come from somewhere else, best of all straight from the reference assemblies plus their XML doc files via Roslyn metadata. Study evidence says API-doc retrieval helps most for rare APIs and can hurt common ones when retrieval is noisy, so it should be gated, not always on.

### Cited Findings
- About text: ".NET API reference documentation (.NET 8+)", published to learn.microsoft.com/dotnet/api/. .NET Framework API reference is in a separate repo, dotnet/dotnetfw-api-docs. The repo has 7,443 commits. Some namespaces are documented in their source repos and "edits to the XML here are auto-generated and ported" — [dotnet/dotnet-api-docs](https://github.com/dotnet/dotnet-api-docs)
- Licence [checked]: `LICENSE` is Creative Commons Attribution 4.0 International and `LICENSE-CODE` is MIT (Copyright Microsoft). An index built from the text needs attribution (Jazari's source row already gives it) — [LICENSE](https://raw.githubusercontent.com/dotnet/dotnet-api-docs/main/LICENSE), [LICENSE-CODE](https://raw.githubusercontent.com/dotnet/dotnet-api-docs/main/LICENSE-CODE)
- Size and structure [checked]: `xml/` holds 13,707 files in 391 namespace folders (one file per type), and `snippets/` holds 28,999 files. The last commit was 2026-10-29. **No folder starts with `Microsoft.AspNetCore` or `Microsoft.EntityFrameworkCore`**, while `Microsoft.Extensions.DependencyInjection` and its `.Extensions` are present — [repo tree](https://github.com/dotnet/dotnet-api-docs)
- Per-type file format [checked, `xml/System.Net.Http/HttpClient.xml`]: 251 KB with 56 `<Member>` entries. Each member has a `<MemberSignature Language="C#" Value="public HttpClient (System.Net.Http.HttpMessageHandler handler, bool disposeHandler);" />` line, which makes overloads explicit. `<AssemblyVersion>` lists run from 4.0.0.0 to 11.0.0.0, and `FrameworkAlternate="net-10.0"`/`"net-11.0"` attributes mark which versions a member exists in. `<remarks>` is Markdown inside CDATA with `<xref:...>` links. A type file is large (HttpClient alone is about 60k tokens) but very regular — [HttpClient.xml](https://raw.githubusercontent.com/dotnet/dotnet-api-docs/main/xml/System.Net.Http/HttpClient.xml)
- Roslyn can load an assembly with its XML documentation: `MetadataReference.CreateFromFile(path, properties, DocumentationProvider documentation)`, where `documentation` "Provides XML documentation for symbol found in the reference". The method "eagerly reads the entire content of the file into native heap". Use `AssemblyMetadata.CreateFromFile` to share or dispose metadata when many references are made — [MS Learn, Roslyn 5.3.0](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.metadatareference.createfromfile?view=roslyn-dotnet-5.3.0)
- API-doc retrieval versus API frequency (CloudAPIBench, Amazon; first posted July 2024 and listed as a 2025 publication, so older work): documentation-augmented generation (DAG) "significantly enhances low-frequency API performance" but "can degrade high-frequency API performance with irrelevant retrievals". The authors use BM25. DAG++ retrieves only when needed, based on API frequency, and "effectively balances" the two [snippet] — [arXiv 2407.09726](https://arxiv.org/html/2407.09726v1); [Amazon Science](https://www.amazon.science/publications/on-mitigating-code-llm-hallucinations-with-api-documentation)
- MARIN (ACM 2025) reduces API hallucination by mining hierarchical dependencies (local project plus global library) and adds "Micro Hallucination Number / Macro Hallucination Rate" metrics. It notes that older-repo benchmarks may leak into training data [snippet] — [arXiv 2505.05057](https://arxiv.org/pdf/2505.05057v1)
- Older (2022) DocPrompting: retrieving docs helps code generation. BM25 matched trained dense retrievers on one dataset but "performed poorly on CoNaLa", and retrievers pretrained on the target language were stronger [snippet] — [arXiv 2207.05987](https://arxiv.org/pdf/2207.05987)

### Inferences
- **Two sources for one "API book" table.** (a) For System.* and Microsoft.Extensions.*, parse the ECMA XML into one row per member: `type`, `member`, `csharp_signature`, `summary` (first sentence), `min_version`/`max_version` from `FrameworkAlternate`, `remarks_md` and `doc_url`. (b) For ASP.NET Core and EF Core, load the reference assemblies already on the T480 (shared framework ref packs and the EF Core NuGet packages) with Roslyn and walk public symbols. `ISymbol.ToDisplayString()` gives signatures, and `GetDocumentationCommentXml()` gives summaries when the side-by-side XML doc file exists. This guarantees the signatures match what the user actually compiles against. Whether ASP.NET Core ref packs ship complete XML doc files is unverified (see Gaps).
- **Size estimate (not measured):** if only C# signature plus summary is kept (about 150–300 bytes per member) and the full remarks are kept in a separate FTS column, a BCL plus Extensions index is roughly 100–300 MB of raw XML in, and about 30–80 MB of SQLite out. That is the same order as the 65 MB law book. A per-member build is a one-off batch job of minutes. Treat these numbers as estimates to measure.
- **Use for exact-API questions, gated as in DAG++.** When the question (or a drafted answer) names an identifier such as `HttpClient.SendAsync`, `AddDbContextPool` or `IOptionsMonitor<T>`, look it up by exact name rather than BM25 and inject only the overload list (about 20–60 tokens per overload). At ~30 tok/s prompt reading, 5 overload lines cost about 3–6 s, against about 10 s for a 300-token prose passage. For questions that name no API, keep the law book as it is.
- **Does API reference beat conceptual docs for a ~1B model?** I found no direct study. CloudAPIBench suggests reference docs help rare APIs and hurt common ones under noisy retrieval. Section 5 says small models are distracted by any context. Together that points to short, exact signature lines (high precision, few tokens) as more useful to Granite H-Tiny than more prose. This is an inference, not a measured result.

### Gaps
- Total byte size of `xml/` was not measured: lazy blob fetching was too slow, so only file counts are known.
- Where the ASP.NET Core and EF Core API reference XML lives publicly (if anywhere besides the source repos' `///` comments), and whether `Microsoft.AspNetCore.App.Ref` ships complete IntelliSense XML for .NET 10/11, were not verified.
- No study compares API-reference grounding with conceptual-doc grounding for models of about 1B parameters.

## 2. Better retrieval on CPU: field weighting, reranking, static embeddings, hybrid

### Takeaway
The cheapest gains for the known misses ("right page, wrong section"; "near-topic page outranks right one") are structural: index sections with their heading path as a separately weighted field, and rerank the top candidates. A tiny cross-encoder (FlashRank TinyBERT-L2 at about 4 MB, or MiniLM-L6/L12 at about 34 MB) reranks about 20–30 pairs in tens of milliseconds on a modern CPU, which is negligible next to Jazari's ~10 s cost per 300 injected tokens. Static embeddings (Model2Vec potion) are very cheap but only about 82% of MiniLM on MTEB retrieval, and evidence that hybrid retrieval helps sub-7B generators is weak or negative.

### Cited Findings
- Cross-encoder CPU latency: in Qdrant's benchmark of the MiniLM-L-6-v2 ONNX export with about 30 query–document pairs per request on a 14-core Apple M4 Max CPU, p99 was 36 ms (cross-encode-rs), 49 ms (fastembed) and 51 ms (sentence-transformers), with minimums of about 14–17 ms. CoreML was much slower (213 ms p50 versus 29 ms on CPU) — [Qdrant blog](https://qdrant.tech/blog/oxidizing-cross-encoders/)
- Older Java/non-ONNX numbers for a MiniLM cross-encoder: about 12.3 ms for 1 document, 58.7 ms for 10 and 740 ms for 100 (hardware unclear) — [Metarank docs](https://github.com/metarank/metarank/blob/stabledoc/doc/guide/search/cross-encoders.md)
- FlashRank (Apache-2.0) ships `ms-marco-TinyBERT-L-2-v2` (default, "~4MB"), `ms-marco-MiniLM-L-12-v2` ("Best Cross-encoder reranker", ~34MB) and `rank-T5-flan` (~110MB, best zero-shot). Speed "is a function of # of tokens in passages, query + model depth (layers)". Cross-encoders have a 512-token maximum — [FlashRank README](https://raw.githubusercontent.com/PrithivirajDamodaran/FlashRank/main/README.md)
- Model2Vec (MIT) distils a sentence-transformer into static embeddings, "up to 50" times smaller and "up to 500 times faster" on CPU. The base package's "only major dependency is numpy". Models include potion-base-8M, potion-base-32M, potion-retrieval-32M (32.3M params) and **potion-code-16M-v2** (16.2M). The best model is "~30 MB on disk" — [Model2Vec GitHub](https://github.com/MinishLab/model2vec)
- potion-retrieval-32M MTEB retrieval score is 35.06, against 42.92 for all-MiniLM-L6-v2 (about 82%) and 32.67 for potion-base-32M — [model card](https://huggingface.co/minishlab/potion-retrieval-32M) via search snippet; [Model2Vec results](https://minish.ai/packages/model2vec/results/)
- sqlite-vec is still pre-1.0: the `VERSION` file on main reads `0.1.10-alpha.4` [checked] — [sqlite-vec VERSION](https://raw.githubusercontent.com/asg017/sqlite-vec/main/VERSION)
- Code/API-doc retrieval, BM25 versus dense: on a derived "NanoCodeRAG" split of CodeRAG-Bench (library-documentation queries), BM25 scores nDCG@10 0.687 against 0.765 for dense. That is a compact third-party split, not the paper's own table — [hakari-bench NanoCodeRAG](https://hakari-bench-leaderboard.hf.space/docs/benchmark-tasks/NanoCodeRAG). CodeRAG-Bench (NAACL Findings 2025) finds that high-quality contexts help, but "retrievers often struggle to fetch useful contexts, and generators face limitations in using those contexts" [snippet] — [ACL Anthology](https://preview.aclanthology.org/dashboard/2025.findings-naacl.176); [repo](https://github.com/code-rag-bench/code-rag-bench)
- BMX (2024): entropy-weighted lexical search with "semantic-enhanced" query expansion, proposed as a BM25 improvement without dense vectors [title/snippet only] — [arXiv 2408.06643](https://arxiv.org/pdf/2408.06643)

### Inferences
- **Section-level chunks with a weighted heading field (BM25F-style).** Store `page_title`, `heading_path` (H1 > H2 > H3), `body` and `code` as separate FTS5 columns and pass per-column weights to `bm25()`, for example title 4, heading 3, body 1, code 0.5. FTS5's `bm25()` takes per-column weights as extra arguments; I could not re-fetch sqlite.org this session to quote it, so verify against the FTS5 docs. This targets "right page, wrong section" directly. Cost: a re-index of the 65 MB book, no runtime cost.
- **Page-then-section two-stage ranking.** Aggregate chunk scores by page (max or sum of the top 2), pick the best page, then pick the section within it by heading match. This attacks "near-topic page outranks right one" when the right page has several moderately matching sections. Zero model cost.
- **Query expansion without a model.** Build a synonym and alias table from the API book (type ↔ namespace, `AddX` ↔ `XOptions`, abbreviations like DI ↔ dependency injection, EF ↔ Entity Framework). Adding identifiers that appear in the question to a code/identifier column is likely to help more than generic expansion. This has not been measured for Jazari.
- **Reranking budget on the T480.** Scaling Qdrant's M4 Max numbers (14 cores) to a 4-core 8th-gen i5/i7 suggests very roughly 100–400 ms for 20–30 MiniLM-L6 pairs of up to 256 tokens, and well under 100 ms for TinyBERT-L2. These are estimates to measure. RAM is about 50–150 MB with ONNX Runtime. In .NET, Microsoft.ML.OnnxRuntime can host it in the gateway, with a BERT WordPiece tokenizer needed. The reranker should feed the existing evidence gate, not replace it. MS MARCO rerankers were trained on web QA, not API docs, so their gain on dotnet docs must be measured on the 20-question dev set. One cheap test: does it fix the 2 known misses without losing any of the 15 trap refusals?
- **Static embeddings and sqlite-vec are a later, optional step.** potion-code-16M-v2 or potion-retrieval-32M embed 58k chunks in minutes and take tens of MB (58k × 256 dims × 4 B ≈ 60 MB of float32; less if quantized). But two earlier findings (Italian bench: dense 25/45% vs BM25 80/95%; 2507.18515: hybrid neutral or negative under 7B) plus the 82%-of-MiniLM ceiling make it unlikely to beat a well-weighted BM25 plus reranker. sqlite-vec still being alpha is a further reason to wait.

### Gaps
- No measured cross-encoder latency on an 8th-gen 4-core Intel laptop CPU was found. A 15-minute benchmark on the T480 is needed.
- No evaluation of MS MARCO cross-encoders on .NET/ASP.NET documentation was found.
- No direct BM25 versus potion-retrieval comparison on code docs was found.
- ColBERT/PLAID CPU latency was not researched within the budget. Its larger index (multi-vector) makes it a poor fit for 16 GB RAM at 58k chunks, but this is unverified.

## 3. Grounding in the user's own repository

### Takeaway
The proven pattern is Aider's repo map: a ranked, signature-only outline of the most-referenced symbols under a fixed token budget (default 1k tokens). For a C# repo, Roslyn gives a more precise version of the same thing (exact symbols, references and DI registrations). Combined with exact-name lookup, it lets a 16k-context, 30 tok/s model answer "where/how is X done in my code" by injecting a few hundred tokens instead of files.

### Cited Findings
- Aider builds "a concise map of your whole git repository" with key symbols per file, "the most important classes and functions along with their types and call signatures". "It only includes the most important identifiers, the ones which are most often referenced by other portions of the code". Selection uses "a graph ranking algorithm, computed on a graph where each source file is a node and edges connect files which have dependencies". The budget "defaults to 1k tokens" (`--map-tokens`) and can grow "especially when no files are added to the chat"; the map "selects the parts of the codebase that are most relevant to the current chat state" — [aider repomap.md](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/docs/repomap.md)
- MARIN's finding that local-project plus library dependency context reduces API hallucination [snippet] — [arXiv 2505.05057](https://arxiv.org/pdf/2505.05057v1)

### Inferences
- **Roslyn repo map, built in the gateway.** Parse all `.cs` files (syntax only, which needs no restore and is fast) into a `symbols` table: `kind`, `fully_qualified_name`, `signature`, `file`, `line`, `containing_type`, `attributes` (for example `[HttpGet("...")]`, `[ApiController]`) and `doc_summary`. Also add a `refs` table with identifier occurrences per file (syntax-level, cheap). Rank by in-degree, as Aider does (PageRank over file→file reference edges), and personalize toward files and identifiers mentioned in the question or the last `/read`. Add an FTS5 index on names and signatures with camel-case split tokens (`AddDbContext` → `add db context`).
- **Domain-specific facts that are cheap and useful for ASP.NET Core:** routes (attribute and minimal-API `Map*` calls), DI registrations (`builder.Services.Add*`), options bindings, EF `DbSet<>`s and the `appsettings*.json` keys. These can be extracted syntactically and given as `label: value` facts, the format that tested best in the earlier Italian bench.
- **Freshness cost (estimate):** re-parse only files whose mtime or size changed. A `FileSystemWatcher` or a check before each question costs milliseconds. Syntax parsing a few hundred files is typically sub-second to a few seconds on a laptop (not measured). A full semantic model (MSBuildWorkspace) needs restore and is much heavier (seconds to tens of seconds and hundreds of MB), so keep it for explicit commands. Universal ctags is an alternative for non-C# files, but adds an external binary.
- **Budget:** 300–600 tokens of map per question costs about 10–20 s of prompt reading at 30 tok/s. If the map is placed in a stable prefix and the llama.cpp prompt cache reuses it, it is paid once per session (see the cache findings in the earlier reports). So rebuild the map text only when the ranked content changes.

### Gaps
- No study found that measures repo-map benefit for models of about 1B parameters, and none measures Roslyn-based maps against tree-sitter maps.
- Aider's tree-sitter and PageRank implementation details (repomap.py) were not read; aider.chat was blocked and only the docs markdown was fetched.
- No measured parse or index times for Roslyn on a T480.

## 4. Verifying an answer's code after generation

### Takeaway
An in-memory Roslyn compilation of each C# snippet against the right reference assemblies turns invented APIs into concrete compiler diagnostics (missing type, member or overload) in well under a second after warm-up. That lets Jazari flag or retry before showing the answer. This is the strongest CPU-cheap correctness lever for exact-API questions, because it checks against ground truth rather than retrieval.

### Cited Findings
- `CSharpCompilation.Create(assemblyName, syntaxTrees, references, options)` builds a compilation, and `GetDiagnostics()` returns "all the diagnostics for the compilation, including syntax, declaration, and binding", without emit diagnostics. So no emit or run is needed to detect unknown members — [CSharpCompilation.Create](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation.create?view=roslyn-dotnet-5.3.0); [GetDiagnostics](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation.getdiagnostics?view=roslyn-dotnet-5.3.0)
- `MetadataReference.CreateFromAssembly` is obsolete ("Use CreateFromFile(assembly.Location) instead"). Reusing `AssemblyMetadata` across references is recommended for performance — [MS Learn](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.metadatareference.createfromassembly?view=roslyn-dotnet-5.3.0)
- Basic.Reference.Assemblies (NuGet, 1.8.x) packages reference assemblies for in-memory Roslyn compilations (net8.0, netstandard2.0, net472, plus per-TFM packages) and offers `WithReferenceAssemblies(...)` to retarget. Pointing at runtime implementation assemblies "will often work on .NET Framework but will fail with running on .NET Core" — [Basic.Reference.Assemblies (NuGet)](https://www.nuget.org/packages/Basic.Reference.Assemblies); [GitHub](https://github.com/reflectronic/basic-reference-assemblies)
- API-doc retrieval reduces hallucinated invocations mainly for low-frequency APIs (CloudAPIBench, 2024/25) [snippet] — [arXiv 2407.09726](https://arxiv.org/html/2407.09726v1)

### Inferences
- **Pipeline.** (1) Extract fenced C# blocks from the answer. (2) Wrap fragments: put top-level statements in a `Program` file with `global using`s for the ASP.NET Core shared framework, or wrap member snippets in a dummy class. (3) Compile against the user's TFM ref pack: Microsoft.NETCore.App.Ref and Microsoft.AspNetCore.App.Ref from the local SDK's `packs/` folder, plus EF Core DLLs from the NuGet cache when the snippet uses them. (4) Keep only "symbol does not exist" diagnostics: CS0117 (no definition), CS1061 (no extension/instance member), CS0246 (type not found), CS0234 (namespace member missing), CS1501 (no overload with N arguments) and CS1503 (argument type mismatch). Ignore errors caused by the missing context (undeclared locals, CS0103, unless the name looks like an API). (5) On a hit, either annotate ("`Foo.BarAsync` does not exist in .NET 10") or retry once with the API book's real overloads injected. The diagnostic codes are standard compiler codes, but this filter list is my design and has not been tested.
- **Cost (estimate):** loading the ~200 reference assemblies of the ASP.NET Core shared framework once costs about 100–300 MB RAM and seconds at first use. Later compilations of a small snippet take tens to a few hundred ms on a warm process. Keep it in the long-lived gateway and pre-warm in the existing idle `/v1/warm` path. A retry costs a full extra generation (30+ s), so only retry on a confirmed invented API; otherwise annotate.
- **Cheaper complement:** check API names in prose against the symbol table from §1 (exact FQN or member-name lookup), with no compilation. This catches invented names that appear outside code blocks. It extends the earlier report's "anti-invention check" to APIs using real metadata instead of retrieved text.
- **CSharpScript** (Microsoft.CodeAnalysis.CSharp.Scripting) would also accept top-level snippets, but executing model code is unnecessary and a security risk. Compile only, never run.

### Gaps
- Could not retrieve measured API-hallucination rates for models of about 1B parameters (CodeHalu, De-Hallucinator and similar papers were not readable with arxiv.org blocked). The only numbers obtained are qualitative summaries.
- No published measurement of Roslyn in-memory compile latency per snippet on a laptop CPU was found. It must be benchmarked.
- No study found on compile-check-and-retry loops specifically for C#.

## 5. How much retrieved context a ~1B-active model can use

### Takeaway
Recent evidence says that for models of 3B and smaller, the presence of context, not its relevance, drives much of the damage. Even oracle passages are poorly used, and adding context can destroy previously correct answers. For Jazari this argues for strict precision over recall: at most one short passage (or a few signature lines), injected only when the evidence gate fires, which is what the law book already does. Spend effort on picking the right section rather than adding more passages.

### Cited Findings
- "Can Small Language Models Use What They Retrieve?" (Pandey, arXiv 2603.11513, March 2026, single-author preprint, not reproduced): five instruction-tuned models from 360M to 8B (SmolLM2, Qwen2.5, Llama 3.1), 4-bit, 1,000 NQ and HotpotQA questions. With oracle retrieval, on questions the model could not answer alone, the 7B got 14.6% right, the 1.5B 10.0% and the 360M 0%. Adding retrieval "destroys 42 to 100 percent of answers the model previously knew". For ≤3B models "context presence, not quality, drives distraction". The dominant oracle failure is irrelevant generation (73% for the 3B). The pilot dense-retrieval penalty was −11.0 points at 1.5B and −7.5 at 3B. The paper hypothesizes a ~1B threshold below which RAG is non-functional [snippet] — [arXiv 2603.11513](https://arxiv.org/html/2603.11513); [alphaXiv](https://www.alphaxiv.org/abs/2603.11513)
- "The Distracting Effect" (ACL 2025): 3B variants in all model families were more susceptible to distraction by irrelevant passages than larger ones [snippet] — [ACL Anthology](https://aclanthology.org/2025.acl-long.892.pdf)
- "Beyond Relevance: Quantifying Distraction of Irrelevant Passages in RAG" (CEUR-WS): a 0–1 distraction score, with distraction rankings correlating across models from 3B to 70B (Spearman 0.47–0.76). Which passages are distracting is largely model-independent, so one could be tested offline with a bigger model [snippet] — [CEUR-WS Vol-4026](https://ceur-ws.org/Vol-4026/paper7.pdf)
- Long-context LLMs meet RAG (ICLR 2025): more retrieved passages consistently raise recall but add hard negatives that can lower accuracy [snippet] — [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/5df5b1f121c915d8bdd00db6aac20827-Paper-Conference.pdf)
- "Do RAG Systems Really Suffer From Positional Bias?" (EMNLP 2025) questions how much lost-in-the-middle matters in realistic RAG, compared with distractors [title/snippet only] — [arXiv 2505.15561](https://arxiv.org/pdf/2505.15561); [ACL Anthology](https://aclanthology.org/2025.emnlp-main.1422.pdf)
- RAFT (2024, older): training with distractor documents improves robustness, and training only on golden documents does poorly. This is relevant only if Jazari ever fine-tunes [snippet] — [arXiv 2403.10131](https://arxiv.org/pdf/2403.10131)

### Inferences
- **Passage count and length for Granite H-Tiny (~1B active, 7B total MoE).** Its total parameter count may make it behave better than a dense 1B, but no study covers hybrid MoE models of this size, so assume small-model behaviour. Keep to one passage of at most 300 tokens (current design), or up to 5 signature lines for API questions. Never add a second "maybe relevant" passage. Lost-in-the-middle is mostly moot at this length, but place the passage right next to the question (as Jazari does).
- **The refusal gate is worth more than recall.** Given "context destroys known answers", a wrong-section passage is worse than none. Rerank and section-select (§2), then keep the evidence gate strict. Measure on the dev set: answers changed from right to wrong by adding a passage (the "destroyed-known" rate), not just found/refused.
- **Cheap prompt-side mitigations to test:** tell the model the passage is optional ("use it only if it answers the question"); have it quote the one relevant line first (consistent with Du et al., already in earlier reports); strip Markdown noise, links and xref tags from passages to save tokens.

### Gaps
- No study sweeps passage count or length for models of about 1B (or for hybrid Mamba/MoE models like Granite 4.0-H). All numbers come from 360M–8B dense models on open-domain QA, not code or API questions.
- The key 2026 small-model paper is a single-author preprint read only through search summaries. Its exact numbers should be checked against the PDF once arxiv.org is reachable.
