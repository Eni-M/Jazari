## 1. Compile-check and repair loops for C#

### Takeaway
For a model this small, the compiler is worth far more as a **gate** than as a **teacher**. Run a cheap compile check after every edit and refuse to offer a diff that adds errors. But budget at most **one** model repair round, fed only with structured, filtered errors. Small models gain little from a second attempt, and a fresh resample often does as well as "repair". The fast path is an in-process Roslyn semantic compile, which takes milliseconds to seconds once warm. `dotnet build` is the slow, authoritative fallback, and it runs project code (MSBuild targets, analyzers, source generators), so it needs consent or a sandbox.

### Cited findings

**How much does a second attempt help small models? (direct data, 2024–25, Python/polyglot, not C#)**
- Aider's benchmarks report `pass_rate_1` (first try) and `pass_rate_2` (second try after seeing the failing unit-test output) for each model. Parsed from the leaderboard YAML for the 133-exercise Python edit set, whole-file format, the gain from the test-feedback round was: Qwen2.5-Coder-0.5B 14.3→14.3 (+0.0), 1.5B 28.6→31.6 (+3.0), 3B 33.8→39.1 (+5.3), 7B 51.9→57.9 (+6.0), 14B 58.6→69.2 (+10.6); llama3.2-3B 20.3→26.3 (+6.0); granite3-dense-8B 17.3→20.3 (+3.0, only 78.9% well formed); gemini-1.5-flash-8b 33.1→38.3 (+5.2). Frontier models gain about 11–20 points on the same set (gemini-exp-1206 whole 60.9→80.5) — [edit_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/edit_leaderboard.yml) [primary, parsed 2026-11-02]
- On the harder polyglot set, the second round is where strong models earn most of their score (o4-mini high 19.6→72.0; Gemini 2.5 Pro 06-05 44.9→79.1). Weak models barely move (gpt-4o-mini 0.9→3.6; gemma-3-27b 1.8→4.9). No sub-8B model appears in that file — [polyglot_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/polyglot_leaderboard.yml) [primary]

**Repair vs resampling (the controlled evidence, 2024–2026)**
- Olausson et al. (ICLR 2024; Code Llama-13B, GPT-3.5, GPT-4 on HumanEval/APPS) found that, once the cost of repair is counted, gains "are often modest, vary significantly between subsets of the data, and are sometimes not present at all". Pass rates are sometimes equal or higher with i.i.d. resampling at the same budget, especially when the budget is small. Self-repair is "bottlenecked by the model's ability to provide feedback on its own code", and stronger-model or human feedback helps a lot — [ICLR 2024 proceedings](https://proceedings.iclr.cc/paper_files/paper/2024/hash/9ddc141bdbf9d1db510cefff56c586ad-Abstract-Conference.html), [MS Research page](https://microsoft.com/en-us/research/?p=1015407) [abstract/summary]
- "Falsification, Not Exposure" (arXiv 2606.31511, preregistered, placebo-controlled; frozen 0.5B–1.5B code models; HumanEval+/MBPP+). Execution-based criticism helps mainly by counteracting the harmful conditioning of showing the failing code. Code plus executed facts beat bare code by 18 points, but **tied blind resampling (26 vs 26 unlocks)** — [arXiv listing](https://arxiv.org/pdf/2606.31511), [themodelwire summary](https://themodelwire.com/article/falsification-not-exposure-an-internally-preregistered-placebo-controlled-decomp-01KWDPQ8W0B80KSMXCRA0ZTRZW) [abstract/summary; single author; preprint]
- "Form, Not Content?" (arXiv 2607.12962, July 2026; same author). An error-content adapter tied the baseline 8–8, and "content-attributable superiority was not confirmed" — [arXiv abs](https://arxiv.org/abs/2607.12962), [papers.cool](https://papers.cool/arxiv/2607.12962) [abstract/summary; preprint]
- A blog post on a further preprint (arXiv 2607.26117) reports that blind resampling beat repair loops on MBPP+ for 1.5B, 3B and 7B models, using 2.5–5.5× fewer tokens. The paper itself was not verified — [developersdigest](https://www.developersdigest.tech/blog/blind-resampling-beats-self-repair-2026) [secondary]
- COCOS (Findings of EMNLP 2025) says small models "struggle to exhibit reflective revision behavior" and needed RL training to correct over multiple turns — [ACL Anthology PDF](https://aclanthology.org/2025.findings-emnlp.127.pdf) [abstract/summary]

**Compiler as a tool (helps when the compiler, not the model, supplies the signal)**
- "From LLMs to Agents in Programming: The Impact of Providing an LLM with a Compiler" (arXiv 2601.12146) reports that smaller models given a compiler sometimes beat larger ones given a compiler. The agents had **5 compile attempts** against the baselines' 1, and the authors concede the comparison was unequal — [arXiv html](https://arxiv.org/html/2601.12146v2) [abstract/summary; full text not reachable]
- Structured diagnostics (buggy line, buggy token, message plus explanation), reformatted for the model, worked better than raw compiler text in a patch-porting study — [arXiv 2604.01680](https://arxiv.org/pdf/2604.01680) [abstract/summary]. LSPRAG found that different error types need different context, for example an unused import versus a redeclaration — [arXiv 2510.22210](https://arxiv.org/pdf/2510.22210) [abstract/summary]
- LLMloop (ICSME 2025) runs five feedback loops, one of them a compile-error loop that runs until the code compiles or a retry cap is hit — [arXiv 2603.23613](https://arxiv.org/html/2603.23613v1) [abstract/summary]
- FeedbackEval and its Java replication (arXiv 2609.00362) stress that "feedback design" drives repair outcomes — [FeedbackEval](https://arxiv.org/pdf/2504.06939), [replication](https://arxiv.org/pdf/2609.00362) [abstract/summary]
- **No C#-specific compile-repair study was found** (see Gaps).

**Build speed levers (.NET)**
- MSBuild Server caches build context in a long-running process, so the second and later `dotnet build` runs skip most startup. It is **on by default from the .NET 11 SDK**. Earlier SDKs need `DOTNET_CLI_USE_MSBUILD_SERVER=1`. The server shuts down after **15 minutes idle**, `dotnet build-server shutdown` stops it, and `/nr:false` disables it per call. It "is primarily beneficial in repetitive build scenarios", which is exactly an edit→build loop — [MS Learn: MSBuild Server](https://learn.microsoft.com/visualstudio/msbuild/msbuild-server?view=visualstudio) [primary]. (Third-party skill pages give the variable as `MSBUILDUSESERVER` and one claims it is on by default in .NET 8+. Microsoft's page contradicts that — [claudepluginhub skill](https://www.claudepluginhub.com/skills/dotnet-dotnet-msbuild-plugins-dotnet-msbuild/msbuild-server) [secondary].)
- Incremental build skips targets whose outputs are newer than their inputs, by timestamp — [MS Learn: Incremental builds](https://learn.microsoft.com/visualstudio/msbuild/incremental-builds?view=visualstudio) [primary]. `dotnet build` equals `dotnet msbuild -restore`, so pass `--no-restore` to avoid restore (and the network) on every loop — [MS Learn: dotnet build](https://learn.microsoft.com/dotnet/core/tools/dotnet-build#description) [primary]. `-m` sets worker processes — [MS Learn: parallel builds](https://learn.microsoft.com/visualstudio/msbuild/building-multiple-projects-in-parallel-with-msbuild?view=visualstudio) [primary]
- The Roslyn compiler server (VBCSCompiler) reuses one compiler process across builds and falls back to standalone compilation if it fails — [Roslyn Compiler Server.md](https://github.com/dotnet/roslyn/blob/main/docs/compilers/Compiler%20Server.md) [primary]
- Analyzers often dominate compile time. In one 160-project solution, build time went from about 1m42s to about 8 min with StyleCop and FxCop enabled — [dev.to](https://dev.to/florinvica/7-things-that-silently-kill-your-net-build-time-and-how-to-fix-each-one-3148) [secondary]. Another estimate puts analyzers at about 70% of compile time on a large solution — [dev.to (asimmon)](https://dev.to/asimmon/optimizing-c-code-analysis-for-quicker-net-compilation-4e3d) [secondary]
- In-process incremental Roslyn: RoslynX's author reports a hello-world `dotnet build` at about 1.1 s against about 6 ms for a later in-process Roslyn rebuild. These are unverified and come from a trivial project — [RoslynX](https://github.com/MaxEden/RoslynX) [secondary]
- No-op build targets from Microsoft's dotnet/skills "build-perf-baseline" skill: under 5 s for small repos, under 30 s for large. A no-op over 30 s "suggests incremental build is broken". Measure with `dotnet build /bl:noop.binlog -m`. These are targets, not measurements — [build-perf-baseline](https://kortix.com/marketplace/dotnet--skills/build-perf-baseline) [secondary]

### Inferences
- **Three-tier check after `/edit`, before showing the diff** (order by cost):
  1. `ParseText` syntax gate (already proposed), at about milliseconds.
  2. **In-process semantic compile.** Load the project once with `MSBuildWorkspace`, or build a `CSharpCompilation` from the `obj/` reference list (the `@(ReferencePath)` items, or `project.assets.json`). Keep it warm in the CLI process. After an edit, call `compilation.ReplaceSyntaxTree(old, new)` and read `GetDiagnostics()` filtered to the edited files and to *new* errors (a baseline diff). Roslyn reuses the unchanged trees and only re-binds what changed, so a warm re-check of one edited file in a mid-size project should be sub-second to a few seconds on a T480 [estimate; measure]. Compiling runs no project code; analyzers and source generators run only if you choose to load them. Without generators, Razor, minimal-API source-gen, `[LoggerMessage]`, Regex and JSON source-gen types will show as false CS0103/CS0246 errors. So **diff against a baseline** compile of the unedited tree and only report errors the edit introduced.
  3. `dotnet build --no-restore -v:q` (with MSBuild Server warm) as the authoritative check, only on user consent or inside the sandbox (§5). A cold build of a mid-size ASP.NET Core solution on a 4-core 8th-gen laptop is plausibly 30–90 s, and a warm incremental single-project change 5–20 s [estimate; no published benchmark with stated hardware was found].
- **Repair budget:** one automatic repair round when tier 2 shows new errors. Give it at most 5 errors, each formatted as `file:line | CSxxxx | message | the offending line`, plus the edited region only. Re-check, and if still broken, show the diff marked "does not compile (n errors)" and let the user decide. On the Aider data, a 3B model gains about 5 points from a second round and a 0.5–1.5B model about 0–3. Granite H-Tiny's ~1B active parameters sit in that range, so a second repair round is not worth a minute of generation [inference from Aider data]. The placebo studies suggest that when a retry helps, much of the help would come from **resampling with the same prompt at a different seed or temperature**. A cheap A/B in `eval/`: on failure, (a) a repair prompt with errors, against (b) a fresh sample with a "must compile" note and no failing code shown.
- **Time cost [estimate]:** a repair round re-reads about 1.5–3k prompt tokens (50–100 s at 30 tok/s, less with a cached prefix) and writes about 150–400 tokens (15–40 s at 10 tok/s), so about 1–2 min per round. Two rounds would blow the "few minutes" budget once the original edit is added.
- **Compiler errors as a free "does this API exist" check.** CS0117 (no member), CS1061 (no extension/member), CS0246 (type not found), CS0103 (name not in context), CS1501 (wrong argument count) and CS7036 (missing argument) catch hallucinated APIs exactly. That is the main way small models fail. Roslyn's `compilation.GetSymbolsWithName` / `LookupSymbols` at the error location can supply "did you mean" candidates (the nearest symbol names on that type) to the repair prompt. That is deterministic grounding the model cannot do itself.

### Gaps
- No C#/.NET-specific study of LLM compile-repair loops was found, and none with ≤4B models on C#.
- No published `dotnet build` timing for a mid-size ASP.NET Core project on stated laptop hardware (4-core, 8th gen). Measure on EduCore: cold, warm no-op, warm one-file change, with and without MSBuild Server, and with analyzers on and off (`-p:RunAnalyzers=false`).
- No measurement of warm `MSBuildWorkspace` load time and memory for a mid-size solution on 16 GB, while the model (about 4–5 GB) is also loaded.
- Full texts of 2601.12146 and the placebo preprints could not be read (arXiv blocked). Effect sizes and the round counts at which gains saturate are unverified beyond the abstracts.
- Self-Debugging (Chen et al. 2023), LDB, Reflexion and RepairAgent primary sources were not retrieved in this session, so no claims from them are included.

## 2. Test-driven checks

### Takeaway
Running only the affected tests is cheap to wire up: `dotnet test --no-build --filter "FullyQualifiedName~<Class>"`, with the class found by name convention or Roslyn references. It is the strongest local check after compiling, but it executes project code and needs the sandbox or consent. Evidence that ~1B models write *useful* xUnit tests is essentially absent. Treat model-written tests as drafts the user approves, never as an automatic oracle.

### Cited findings
- `dotnet test --filter <Expression>` supports `FullyQualifiedName`, `DisplayName` and `Traits` for xUnit. The operators are `=`, `!=`, `~` and `!~`, joined with `|` and `&`. A bare value means `FullyQualifiedName~value`. Commas in generic names need `%2C`, and **the whole value must be quoted in PowerShell**, where the comma is the array operator. `[Trait("Category","bvt")]` is matched with `Category=bvt` — [MS Learn: selective unit tests](https://learn.microsoft.com/dotnet/core/testing/selective-unit-tests), [dotnet test (VSTest) filter details](https://learn.microsoft.com/dotnet/core/tools/dotnet-test-vstest#filter-option-details) [primary]
- On Microsoft.Testing.Platform runners, the filter goes after `--` (`dotnet run --project X -- --filter "..."`) or straight to the test executable — [MS Learn: MSTest running tests](https://learn.microsoft.com/dotnet/core/testing/unit-testing-mstest-running-tests#configurations-and-filters) [primary]
- Agentless's validation phase generates reproduction tests and runs existing regression tests to choose among candidate patches — [Agentless arXiv 2407.01489](https://arxiv.org/html/2407.01489v2) [abstract/summary]
- Unit-test generation evidence on C# is limited to large commercial models: a 2025 study of ChatGPT, DeepSeek and Gemini on Unity C# methods — [CITIC UCR](https://citic.ucr.ac.cr/node/1512); a Lithuanian MSc thesis comparing 7 LLMs on C# (compile, coverage, mutation), where the best were grok-4 and gemini-2.5-flash — [VU thesis](https://epublications.vu.lt/object/elaba:308157204/308157204.pdf) [secondary]. The 2023 Java study (CodeGen, Codex, GPT-3.5) found high coverage on HumanEval but **very low on SF110** real projects — [Zenodo](https://zenodo.org/records/7875338) [primary artifact page]
- Aider's second-attempt loop feeds the failing unit-test output back to the model, and §1 has the small-model gains — [edit_leaderboard.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/edit_leaderboard.yml) [primary]

### Inferences
- **Affected-test selection without coverage tooling:** (1) convention: `Foo.cs` → test classes named `FooTests` or `Foo*Tests`; (2) Roslyn: `SymbolFinder.FindReferencesAsync` on the edited methods, keeping hits inside test projects; then (3) build the filter `FullyQualifiedName~Ns.FooTests|FullyQualifiedName~Ns.BarTests`, capped at about 10 classes. Fall back to "no tests found, compile-only check" rather than running the whole suite.
- **Time [estimate]:** `dotnet test --no-build` startup plus a handful of xUnit unit tests takes seconds to about 20 s. ASP.NET Core integration tests (`WebApplicationFactory`) boot the host and can take far longer, so exclude `Category=Integration` by default.
- **"Failing test first" for a ~1B model:** generating a C# test costs about 300–600 output tokens (30–60 s) plus compile and run. The test may not compile (hallucinated APIs, as in §1) or may assert the wrong thing. A reasonable bounded form is to offer `/test <method>` as an explicit command: the model drafts one xUnit `[Fact]`, the compile gate checks it, the user approves it, and only then does it run. Do not chain it automatically into `/edit`.
- Show test output to the model trimmed to the failing test's name, assertion message and the top stack frame inside user code. Raw `dotnet test` output is long and burns prompt time at 30 tok/s.

### Gaps
- No study evaluates ≤4B models writing xUnit/NUnit tests, and none checks whether such tests catch seeded C# bugs (mutation score). This needs an `eval/` set.
- No data on whether a failing reproduction test written by a small model raises fix rates, as opposed to just costing time.

## 3. Agent patterns that survive at ~1–4B

### Takeaway
At ~1B active parameters, fixed pipelines (Agentless-style localize → edit → validate, with deterministic tools doing localization and validation) are the pattern with evidence and the right cost profile. Open-ended agent loops (SWE-agent, OpenHands, Cline) depend on multi-turn tool-calling reliability that sub-4B models lack, unless they are fine-tuned on agent trajectories. Architect/editor splits give modest gains even at 32B and double latency. Jazari's current shape (single-shot grammar-constrained edit plus human approval) is close to the evidence-backed optimum. Add deterministic validation, not autonomy.

### Cited findings
- **Agentless:** three phases (localization, repair, patch validation) "without LLM-driven action selection or complex tools". 32% (96/300) on SWE-bench Lite at about $0.70 per issue with GPT-4o (2024) — [arXiv 2407.01489](https://arxiv.org/html/2407.01489v2), [liner review](https://liner.com/review/agentless-demystifying-llmbased-software-engineering-agents) [abstract/summary; older, 2024]. RGFL (2026) reports +12.8% end-to-end when its better fault localization is plugged into Agentless, so localization is the lever — [arXiv 2601.18044](https://www.arxiv.org/pdf/2601.18044) [abstract/summary]
- **Small specialized components:** Co-PatcheR splits patching across small, component-specific reasoning models to cut task complexity and context length — [arXiv 2505.18955](https://arxiv.org/html/2505.18955v2) [abstract/summary]
- **mini-swe-agent** uses bash only and does not use the LM's tool-calling interface — [emergentmind topic](https://www.emergentmind.com/topics/mini-swe-agent) [secondary]. The SWE-TRACE paper's table lists Qwen3-4B at 38.9% and Qwen3-30B-A3B at 63.5% on SWE-bench Verified with mini-SWE-agent, against Qwen2.5-Coder-32B at 9.0%. These are likely trained or test-time-scaled variants inside that paper and are not independently checked — [arXiv 2604.14820](https://arxiv.org/pdf/2604.14820) [abstract/summary]. Klear-Agent-8B: 39.0% after training on 66k trajectories — [Kwai-Klear dataset README](https://gitcode.com/hf_mirrors/Kwai-Klear/SWE-smith-mini_swe_agent_plus-trajectories-66k/blob/main/README.md) [secondary]. An aggregator cites about 10–12% for ≤1B models, unverified — [emergentmind](https://api.emergentmind.com/topics/mini-swe-agent) [secondary]
- 3B-*active* MoE models with large total size (Qwen3-Coder-Next 80B-A3B: 70.6% SWE-Agent, 71.3% OpenHands) are not comparable. Total parameters, not active ones, carry the knowledge, and they do not fit 16 GB — [Qwen3-Coder-Next report](https://arxiv.org/html/2603.00729v1) [abstract/summary]
- **Aider architect/editor:** an architect model describes the solution and an editor model turns it into edits. The SOTA of 85% came from o1-preview plus DeepSeek or o1-mini (Sonnet alone 84%) — [Aider architect post (2024-09)](https://aider.chat/2024/09/26/architect.html). With QwQ-32B as architect, the gain was "modest" over Qwen alone and "comes with a fairly high cost in terms of latency" — [Aider QwQ post (2024-12)](https://aider.chat/2024/12/03/qwq.html). o1 plus Sonnet was no better than o1 alone — [R1+Sonnet post (2025-01)](https://aider.chat/2025/01/24/r1-sonnet.html) [primary blog, via search summary; older]
- **Tool-calling reliability, BFCL v4 (2025–26):** aggregator figures put LFM2.5-8B-A1B at 49.7%, MiniCPM5-1B at 25.1% and LFM2.5-230M at 21.0%. Leaderboard snapshots disagree on the leaders, and the official Gorilla page was last updated 2025-12-16 — [BenchLM BFCL v4](https://benchlm.ai/benchmarks/bfcl-v4), [llm-stats](https://llm-stats.com/benchmarks/bfcl-v4), [Gorilla leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html) [secondary]. No BFCL v4 figure was found for Granite 4.x or Qwen3-1.7B (the prior report has Granite H-Tiny at 57.65 on BFCL **v3**).

### Inferences
- **Map the patterns onto Jazari:**
  - *Agentless → `/fix` pipeline.* Localization is deterministic: compiler or test errors give file and line, Roslyn gives the enclosing method, and the user's `/read` set gives scope. Then a single constrained edit, then validation (tiers 1–3 from §1, plus affected tests from §2). This needs no tool calling at all, so it sidesteps the BFCL weakness and the gateway work from report §4.
  - *SWE-agent ACI lessons* that carry over without an agent loop: give file views with line numbers in the prompt but never in the edit (§2 of the prior report strips them), run a lint/compile gate on every edit and reject edits that add errors (SWE-agent's ACI does this), and keep outputs concise and truncated. These are interface rules, so they help a pipeline too. (SWE-agent's own paper was not retrievable here; the summary comes from general knowledge and is not cited — see Gaps.)
  - *Architect/editor:* already reduced to "prose first, then constrained edit" in the prior report. The evidence above (modest gain at 32B, doubled latency) supports not going further.
  - *OpenHands/Cline/Continue-style loops:* skip at ~1B active. Continue itself warns that even 7–13B models struggle (cited in the prior report). If a loop is ever added, the 6-step harness from report §4 applies.
  - *Code agents (smolagents writing Python as actions):* not applicable. Jazari would need a C# scripting host, which means arbitrary code execution, so this is ruled out on safety grounds before any accuracy question.
- **Best-of-N as cheap search:** given the resampling evidence (§1), "generate 2 candidates, keep the one that compiles with the fewest new diagnostics" is a pipeline-native alternative to repair. It costs one extra generation (about 30–60 s for a typical edit) and no extra prompt reading if both use the same cached prompt with different seeds [estimate]. `n_probs` or parallel slots are not needed; just two sequential calls.

### Gaps
- No Agentless or pipeline result exists for any ≤4B model on SWE-bench or a C# benchmark.
- SWE-agent (ACI design, lint-on-edit), OpenHands and RepairAgent primary papers were not reachable (arXiv blocked). Claims about them are kept out of the cited list.
- No BFCL v4 (multi-turn or agentic) score for Granite 4.0-H Tiny.
- The SWE-TRACE Qwen3-4B number's training and test-time setup is unclear from the abstract.

## 4. Cheap static checks that catch small-model mistakes

### Takeaway
Order: syntax (ms) → semantic diagnostics limited to new errors in edited files (ms–s, which catches hallucinated APIs) → new nullable warnings (CS86xx) in edited spans → diff-size and scope limits → optional `dotnet format whitespace --folder` on edited files. Full `dotnet format --verify-no-changes` and analyzers load and compile the project and may run analyzers, so treat them like a build.

### Cited findings
- `dotnet format --verify-no-changes` "terminates with a non zero exit code if any files would have been formatted". `--include` limits it to given files, `--no-restore` skips restore, and `--report` writes JSON. The subcommands are `whitespace` (with `--folder`, which treats the path as a plain folder of code files), `style` and `analyzers` — [MS Learn: dotnet format](https://learn.microsoft.com/dotnet/core/tools/dotnet-format#options) [primary]
- Caution from Microsoft: "dotnet format may restore, compile, and run analyzers from the specified project or solution. **Only invoke the tool against trusted code.**" — [MS Learn: dotnet format](https://learn.microsoft.com/dotnet/core/tools/dotnet-format) [primary]
- `EnforceCodeStyleInBuild=true` reports IDE-prefixed style violations as build warnings or errors — [MS Learn community guide](https://learn.microsoft.com/community/content/how-to-enforce-dotnet-format-using-editorconfig-github-actions#3---formatting-your-code-locally) [primary-ish]
- Analyzer cost dominates compile time in large solutions (§1: about 70% estimate; 1m42s → 8m with StyleCop and FxCop) — [dev.to](https://dev.to/asimmon/optimizing-c-code-analysis-for-quicker-net-compilation-4e3d), [dev.to](https://dev.to/florinvica/7-things-that-silently-kill-your-net-build-time-and-how-to-fix-each-one-3148) [secondary]
- Roslyn code fixes suggest changes rather than auto-apply them, and compilation-level diagnostics with no location cannot have code fixes — [Roslyn discussion #50087](https://github.com/dotnet/roslyn/discussions/50087), [devleader Roslyn analyzers guide](https://www.devleader.ca/2026/07/11/roslyn-analyzers-in-c-the-complete-guide) [primary/secondary]

### Inferences
- **"Does this API exist":** the semantic compile from §1 is the check, since CS0117, CS1061, CS0246, CS0103, CS1501 and CS7036 are exactly "this API/overload does not exist". No separate reflection-over-assemblies tool is needed once the `CSharpCompilation` has the real reference set. For prose answers (not edits), the same compilation can verify that type and member names mentioned in the answer resolve: extract `Identifier.Identifier` patterns, call `compilation.GetTypeByMetadataName` or look up members, and tag unresolved ones "unverified". This is a deterministic "is this real" check that parallels the review quote gate [inference].
- **Nullable:** if the project has `<Nullable>enable</Nullable>`, count CS8600–CS8625 warnings in the edited span before and after the edit. Show an increase as a warning on the diff, without auto-repairing, because the model's typical "fix" is `!`, which hides the problem [inference].
- **Diff-size and scope limits** (deterministic, free): reject or flag edits that touch lines outside the region the user named; that delete more than about 30% of a file's lines when the request is not a delete; that change public signatures (Roslyn: compare `ISymbol` declarations of public members before and after) when the request did not ask for it; or that add `using` directives for namespaces not in the reference set. The last one is caught by CS0246 anyway [inference].
- **Formatting:** `dotnet format whitespace <dir> --folder --include <edited files> --verify-no-changes` needs no project load or restore, so it is cheap and safe [inference from docs; time unmeasured]. Better still: auto-apply whitespace formatting to the model's output rather than reporting it, since indentation is a frequent small-model slip and carries no risk to meaning. Note that `--folder` runs whitespace rules only.
- Don't run the full analyzer set per edit. Reserve CA and security analyzers for `/review` (prior report §3).

### Gaps
- Time of `dotnet format whitespace --folder` on 1–3 files on the T480 was not measured. It may still pay .NET host startup of about 1–2 s.
- Whether a warm `MSBuildWorkspace` honours the project's `.editorconfig` severities and `<Nullable>` without extra wiring needs a check.

## 5. Safety for acting tools on a Windows developer laptop

### Takeaway
Treat `dotnet build`, `dotnet test` and `dotnet format` (non-folder) as **arbitrary code execution**: MSBuild targets, analyzers, source generators, test code and NuGet restore scripts all run. On native Windows, neither Claude Code nor any off-the-shelf product offers a mature sandbox. Codex CLI is the only one with a native Windows design (restricted or write-restricted tokens plus a sandbox SID, and firewall rules in its elevated mode). Windows Sandbox (Hyper-V) is the strongest built-in isolation, but it is heavy, Pro-only and single-instance. The realistic default for Jazari is: in-process Roslyn checks with no code execution happen automatically, and anything that executes waits for an explicit keypress, run offline (`--no-restore`) under a Job Object with time and memory limits. Windows Sandbox is an opt-in "safe build" mode.

### Cited findings
- **Codex CLI (Windows):** the official docs (via search summary) say Windows commands run under "a restricted token derived from an AppContainer profile", with filesystem access granted through capability SIDs — [Codex sandbox docs](https://developers.openai.com/codex/sandbox) [secondary via search; page not reachable]. OpenAI's engineering post says AppContainer was evaluated and rejected as fitting "a much narrower class of workloads" than a coding agent needs. It instead relied on "SIDs and write-restricted tokens", with a dedicated sandbox SID — [OpenAI: Building the Codex Windows sandbox](https://openai.com/it-IT/index/building-codex-windows-sandbox/) [via search summary of the Italian/Portuguese pages]. **These conflict.** A third-party deep dive describes an "elevated" mode (dedicated sandbox users plus firewall rules) and an "unelevated" fallback (restricted tokens under the user's own account) — [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/07/18/codex-cli-windows-sandbox-architecture-powershell-ast-safety-elevated-unelevated-appcontainer-restricted-tokens/) [secondary]
- **Claude Code:** the built-in sandbox runs on macOS (Seatbelt), Linux and WSL2 (bubblewrap plus socat). **Native Windows is not supported**, so on Windows you run it inside WSL2. Sandboxed commands in WSL2 cannot launch Windows binaries, and those need `excludedCommands` — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing) [primary via search summary]. Anthropic's open-source `@anthropic-ai/sandbox-runtime` has an **alpha** Windows backend built on a Windows Filtering Platform egress fence, a write-restricted token and explicit NTFS ACLs, described as a research preview with documented holes — [aiweekly](https://aiweekly.co/alerts/anthropic-open-sources-claude-code-sandbox-under-apache-20) [secondary, unverified]. A native-Windows sandbox is an open feature request — [claude-code #46740](https://github.com/anthropics/claude-code/issues/46740) [primary]
- **Windows Sandbox (WSB):** a hypervisor-isolated, disposable VM (separate kernel) that launches in "a few seconds". **Networking is on by default** and must be disabled via a config (`<Networking>Disable</Networking>`). Mapped folders can be `<ReadOnly>true</ReadOnly>`, and writes to writable mapped folders persist on the host. Host-installed software "isn't available in the sandbox", so the .NET SDK must be mapped or installed inside. The default instance has 4 GB memory, and **only one instance can run at a time**. Supported on Pro, Enterprise and Education, **not Home**. From Windows 11 24H2 a `wsb` CLI (`wsb start --config "<Configuration><Networking>Disabled</Networking></Configuration>"`, plus list, exec and share commands) allows scripting — [MS Learn: Windows Sandbox](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/), [configure .wsb](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file), [WSB CLI](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli) [primary]
- `dotnet format` "may restore, compile, and run analyzers … Only invoke the tool against trusted code" — [MS Learn](https://learn.microsoft.com/dotnet/core/tools/dotnet-format) [primary]

### Inferences
- **Threat model for Jazari:** the model writes the code, so the "untrusted" input is the model's output, shaped by repository content (prompt injection via README or comments). The realistic risks are (a) an edit adding a malicious MSBuild target, `.targets` import, source generator reference or `PackageReference` that runs at build or restore time; (b) test code that deletes files or makes network calls; (c) a runaway build eating RAM next to a ~5 GB model. Defences in order of cost:
  1. **Never auto-build on edits that touch `*.csproj`, `*.props`, `*.targets`, `Directory.Build.*`, `nuget.config`, `global.json` or `.editorconfig`.** Show those diffs with a red "build-config change" banner. Cheap and deterministic.
  2. **Offline, no restore:** always pass `--no-restore`. If restore is needed, ask, because restore can fetch packages that ship build logic.
  3. **Job Object** around the spawned `dotnet` process tree: kill-on-close, a memory cap (e.g. 3 GB, which protects the model process's RAM), a CPU-time or wall-clock timeout, and a cap on active processes. This is containment, not isolation: the code still runs as the user. [General Win32 knowledge; no source fetched this session — see Gaps.] Also kill the MSBuild Server and node-reuse processes, or pass `/nr:false` so no build node outlives the job.
  4. **Low-privilege token** (Codex-style write-restricted token plus a sandbox SID with ACLs on the repo and temp only) is the strongest native option short of a VM. It is real engineering effort (ACL management and cleanup), and OpenAI's own docs and blog disagree on the details, which shows how fiddly it is.
  5. **Windows Sandbox "safe build" mode** (opt-in): copy the repo to a temp folder, map it writable and map the SDK read-only, with networking off, then `wsb exec` the build and test and read results from the mapped folder. VM boot plus a cold build every time (the MSBuild Server is not warm inside a fresh VM) likely costs well over a minute on a T480, and it competes for RAM with the model. So it suits occasional "run tests on this risky change" checks, not every edit [estimate]. It is unavailable if the T480 runs Windows Home.
- **What to copy from the field:** a Codex-style approval tier. Read-only actions (Roslyn compile, which runs no project code) need no prompt. Executing actions (build, test, format) need a keypress showing the exact command, then run in a Job Object with `--no-restore` and no network. Claude Code's lesson is that a robust Windows sandbox is hard enough that a well-funded vendor ships WSL2-only, so Jazari should not promise isolation it doesn't have. State "build runs as you, offline, time- and memory-limited" in the UI.
- **Network blocking without a VM:** per-program Windows Firewall outbound block rules on `dotnet.exe` would also break the user's normal workflow, and they need admin rights. `--no-restore` plus `NUGET_PACKAGES` pointing at the existing cache is the practical approximation [inference].

It likely has to be disabled (`/nr:false`) inside a jailed build, which loses the warm-build speedup. Measure.
