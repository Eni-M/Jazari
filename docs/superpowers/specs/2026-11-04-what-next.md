# What next for Jazari

Date: 2026-11-04 · Status: options, nothing decided

These are the options left after the work up to `6d1bf0c`. Already built, so not listed: `/v1/models`, the Origin and Host check, McNemar in `compare.py`, the held-out split, the llama.cpp checksum, `/review --changed`, the secret and C# rule pass, the resumable download and the uninstaller.

Every effort estimate assumes the T480 for measuring. Every change is judged by the eval: a gain counts only if `compare.py` shows it on the dev set and the held-out third doesn't drop.

## A. Make answers more trustworthy

The small model's worst habit is writing confident code against APIs that don't exist. The C# compiler can catch that, at no model cost.

### A1. Compile-check code in answers (1–2 days)

- **What:** after an answer, compile each C# block with Roslyn against the local reference packs (`Microsoft.NETCore.App.Ref`, `Microsoft.AspNetCore.App.Ref`). Show a muted line under a block that doesn't compile, such as `does not compile: 'IServiceCollection' has no 'AddFoo'`.
- **Annotate, don't retry**, on plain questions: a retry costs 15–30 s, and a flag is enough for the reader.
- **Snippets aren't whole files.** Wrap them in a class and method with common usings. Count only "member or type doesn't exist" errors (CS0117, CS1061, CS0246, CS0234), not missing variables.
- **Measure:** cold load of the reference packs (time, and RAM with the model loaded), then 50 warm compiles. If it's cheap, load it during `/v1/warm`.
- **Open:** run it in the gateway (one load, shared) or in the CLI (no change to the API)? The gateway seems better.

### A2. Semantic check for `/edit` (2–3 days)

- **Today:** `/edit` flags a `.cs` change that breaks the syntax and retries once.
- **Next:** load the project with `MSBuildWorkspace`, record its diagnostics before the edit, apply the edit with `ReplaceSyntaxTree`, and report only the **new** errors. Errors that were already there, or come from source generators, never block an edit.
- **One round:** either a repair (error lines plus the enclosing method) or a fresh sample with a new seed. An A/B on about 20 failing edits picks which. The Aider and Qwen data say more than one retry doesn't pay at this size.
- **Measure:** workspace load time and RAM on EduCore, and the warm check time per edit.
- **Open:** keep the workspace warm across a session (fast, but costs RAM), or load it per edit?

### A3. Law-book precision (hours, plus a re-index)

- Equal title and text weight beat a heavy title (`LawBook.cs:66`), because every chunk of a page repeats the page title. So leave the weight alone and try **the section's heading path** (`Page > Section > Subsection`) as its own column. Then rank pages first and the best section within a page second.
- **Goal:** fix the two known misses in the dev set without losing a question it already gets right ("destroyed-known" count stays 0).

### A4. API book (2–4 days)

- Member signatures from dotnet-api-docs (BCL, Extensions) and from the local ASP.NET Core and EF Core reference assemblies, looked up by exact name.
- Feeds A1 ("did you mean `AddScoped`?") and answers rare-API questions without a model call, as `/docs` does today.

## B. Know the user's code

### B1. Roslyn repo map (2–3 days, a week with ranking)

- Per project: types, public members, routes, DI registrations, and which type uses which.
- `/read` fills its 5,000 tokens from the map, ranked by identifiers in the question (personalized PageRank, as Aider does), and keeps the riskiest-first prior.
- Frozen for a conversation so the prompt cache keeps working.
- **Measure:** parse time on EduCore, and tokens per question against today's `/read`.

## C. Reach Jazari from other tools

### C1. Stdio MCP server (1–2 days)

- `jazari mcp` speaks JSON-RPC over stdin and stdout, so no network port is open. Tools: `law_book_search`, `jazari_ask`, `review_file`.
- Lets Claude Code, VS Code or any other MCP client use the law book and reviews while a bigger model chats.
- **Unknown:** how clients treat a tool that takes 30 s or more. Test timeouts first.

### C2. Ollama-API emulation (about a week)

- `/api/tags`, `/api/show` and `/api/chat`, with honest metadata: the real context size, and no tool support claimed.
- Visual Studio's Bring Your Own Model preview takes an Ollama endpoint. Expect chat to work and agent modes to stay weak.

## D. New workflows

### D1. `/fix` (3–5 days, needs A2)

1. Run `dotnet build` or the failing test.
2. Pick the files from the error locations (the Agentless approach, no free-running agent).
3. Propose an edit, check it with A2, show the diff, and write it on yes.
4. Re-run only the affected tests behind a keypress, in a Job Object, offline.

### D2. Smaller items (1–3 days each)

- `/plan`: read-only mode that answers with steps and never edits.
- Checkpoints: `/undo` back to step N, not just the last edit.

## E. Improve the model

### E1. Turn misses into test items (about 1 day)

- The `interactions` table already records `accepted`. Add the model, build and law-book version to each row, plus implicit signals (a re-asked question, an edit undone).
- A script lists likely misses. Eni-M turns the real ones into dev-set items by hand, and never into held-out items.

### E2. Retrieval-aware LoRA (days, later)

- On a free Colab T4 with Unsloth: teach "answer from the passage, cite it, refuse when it's absent or irrelevant", trained with distractor passages (RAFT).
- Teach behaviour, not facts: the facts stay in the law book.
- Merge and re-quantize to one Q4 file, since a runtime `--lora` on the hybrid model is untested.
- Only after E1 has grown the dev set, so the gain can be measured.
