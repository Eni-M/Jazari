## A. Make answers more trustworthy

The small model's worst habit is writing confident code against APIs that don't exist. The C# compiler can catch that, at no model cost.

### A1. Compile-check code in answers (1–2 days)

- **What:** after an answer, compile each C# block with Roslyn against the local reference packs (`Microsoft.NETCore.App.Ref`, `Microsoft.AspNetCore.App.Ref`). Show a muted line under a block that doesn't compile, such as `does not compile: 'IServiceCollection' has no 'AddFoo'`.
- **Annotate, don't retry**, on plain questions: a retry costs 15–30 s, and a flag is enough for the reader.
- **Snippets aren't whole files.** Wrap them in a class and method with common usings. Count only "member or type doesn't exist" errors (CS0117, CS1061, CS0246, CS0234), not missing variables.
- **Measure:** cold load of the reference packs (time, and RAM with the model loaded), then 50 warm compiles. If it's cheap, load it during `/v1/warm`.
- **Open:** run it in the gateway (one load, shared) or in the CLI (no change to the API)? The gateway seems better.

### A2. Semantic check for `/edit` (2–3 days)

- **Today:** `/edit` flags a `.cs` change that breaks the syntax and retries once.
- **Next:** load the project with `MSBuildWorkspace`, record its diagnostics before the edit, apply the edit with `ReplaceSyntaxTree`, and report only the **new** errors. Errors that were already there, or come from source generators, never block an edit.
- **One round:** either a repair (error lines plus the enclosing method) or a fresh sample with a new seed. An A/B on about 20 failing edits picks which. The Aider and Qwen data say more than one retry doesn't pay at this size.
- **Measure:** workspace load time and RAM on EduCore, and the warm check time per edit.
- **Open:** keep the workspace warm across a session (fast, but costs RAM), or load it per edit?

### A3. Law-book precision (hours, plus a re-index)

- Equal title and text weight beat a heavy title (`LawBook.cs:66`), because every chunk of a page repeats the page title. So leave the weight alone and try **the section's heading path** (`Page > Section > Subsection`) as its own column. Then rank pages first and the best section within a page second.
- **Goal:** fix the two known misses in the dev set without losing a question it already gets right ("destroyed-known" count stays 0).
- **Tried 2026-11-04, nothing kept** (baseline 18/20 found, 15/15 traps refused):
  - The heading path as its own column: weight 0 matched the baseline, and weights 1 to 8 found 15 or 16.
  - Swapping a passage that has no code for its page's best section with code: 17/20.
  - **Why the two misses miss:** the right page already wins. "Service lifetimes" and "Enable Cross-Origin Requests (CORS)" rank in the top five, but the intro chunk is taken, and `AddScoped` and `AddCors` sit in a later section. So the fix is choosing the section within the page, not ranking pages. With 20 dev questions, more heuristics here would only fit the set. Grow the dev set first (E1), or let A4's API book supply the call by name.

### A4. API book (2–4 days)

- Member signatures from dotnet-api-docs (BCL, Extensions) and from the local ASP.NET Core and EF Core reference assemblies, looked up by exact name.
- Feeds A1 ("did you mean `AddScoped`?") and answers rare-API questions without a model call, as `/docs` does today.

## B. Know the user's code

### B1. Roslyn repo map (2–3 days, a week with ranking)

- Per project: types, public members, routes, DI registrations, and which type uses which.
- `/read` fills its 5,000 tokens from the map, ranked by identifiers in the question (personalized PageRank, as Aider does), and keeps the riskiest-first prior.
- Frozen for a conversation so the prompt cache keeps working.
- **Measure:** parse time on EduCore, and tokens per question against today's `/read`.

## D. New workflows

### D1. `/fix` (3–5 days, needs A2)

1. Run `dotnet build` or the failing test.
2. Pick the files from the error locations (the Agentless approach, no free-running agent).
3. Propose an edit, check it with A2, show the diff, and write it on yes.
4. Re-run only the affected tests behind a keypress, in a Job Object, offline.

### D2. Smaller items (1–3 days each)

- `/plan`: read-only mode that answers with steps and never edits.
- Checkpoints: `/undo` back to step N, not just the last edit.

## G. Further out

These come after everything above. None of it is built yet: the eval has no repo tasks, and the code has no lookup decoding, edit grammar or battery handling.

### G1. The repo benchmark from the original spec (do this first)

- The 2026-10-30 spec's quality floor: generated code passes the same `dotnet build` and tests as Eni-M's original, and looks close to it. The eval has 45 questions and no repo tasks, so nothing measures that floor.
- **How:** blank out a method in EduCore and WareFlow, ask Jazari to write it, then build and run the tests. Score pass rate, compile rate and closeness to the original. Keep a held-out set, as the question eval does.
- This is what LoRA (E2), model swaps and prompt changes should be judged by.
- The repos are private and stay local or on Colab. Employer code never goes in.

### G2. Faster answers on the same model

- **Lookup decoding for `/edit`.** An edit mostly copies existing code, and llama.cpp can draft tokens from the prompt itself (n-gram or lookup speculation). That's often 1.5–2.5× on copy-heavy output. Whether it works on the hybrid model is unverified, so measure first.
- **A grammar for the edit format.** A GBNF grammar or JSON schema forces valid SEARCH/REPLACE blocks, so parse failures can't happen.
- **Save the cache per project.** llama-server can save the prompt cache and restore it when the project is opened again. Check that this keeps Granite's recurrent state.
- **Model cascade.** `granite-4.0-350m` (in `spike/models`) sorts the question first: law book or not, edit or not, trivial or not. H-Tiny answers. A bigger model does overnight reviews.

### G3. Use idle time

- **Overnight jobs while plugged in:** a full `/review`, a rebuilt repo map (B1), a refreshed "where we are" note per project, and pre-warmed caches. Results wait in a morning report.
- **Battery and heat:** on battery or when hot, use fewer threads, shorter answers, or the 1B model. This enforces the anti-goal "the laptop stays usable".

### G4. `/test`, checked by running it

- Write xUnit tests for a method, compile them and run them. A test that fails on today's code is either wrong or has found a bug, and Jazari says which.
- **Mutation check:** break the method on purpose and see whether the tests notice.

### G5. Explain what tools print

- **`jazari why`:** pipe in `dotnet build` errors, a stack trace, an EF migration failure, or `curl -v` / TLS handshake output, and get an answer grounded in the law book. This covers the networking and security domains, which have had little attention so far.
- **Upgrade helper:** "what breaks going from net8 to net10 here?" It checks the project's APIs against Microsoft's breaking-change pages, added to the law book.

### G6. Git workflow

- **Pre-commit hook:** `/review --changed` on the staged diff. Rules only by default (seconds), with the model as an option.
- Commit messages and PR descriptions drafted from the diff.

### G7. System design and architecture

- **Diagrams from the repo map:** Mermaid for modules and dependencies, a request's path through middleware, DI lifetimes. Roslyn supplies the facts and the model only writes the captions.
- **Architecture rules** in `.jazari/rules`, checked without the model, for example "controllers never use DbContext directly".
- **Threat-model checklist:** OWASP ASVS items, each with a status from the static rules plus the model's note, marked unverified.

### G8. Personal fit

- **Style sheet from Eni-M's repos:** naming, layout, async and error-handling patterns, pulled out by code and followed by `/edit` and `/test`. G1 measures whether it helps.
- **Learning mode:** short quizzes from past questions, and guided tours of an unfamiliar codebase. This fits LearningRoadmap.

### G9. Left over from the original plan

- **Teacher distillation:** Qwen2.5-Coder-14B (Apache 2.0) generates C# training data for E2. Moved to H4, after everything else.
- **Inline completion:** H-Tiny failed fill-in-the-middle. Worth one test if a fast model that can do FIM turns up.

### G10. Open-source release

- Linux and macOS (the scripts are PowerShell only), signed release tags instead of updating from the tip of main, a public eval page, and the model choice at `jazari tune` described in the accuracy spec.

## H. Make the model smarter

On this laptop, "smarter" comes from four places, cheapest first. Most mistakes seen so far are missing knowledge (`AddSqlQuery`, `HttpContext.ValidateToken`, `record` kinds), not weak reasoning, so H2 matters as much as H1. No step here makes a laptop model cloud-class. The aim is one that rarely invents APIs, knows Eni-M's code and says when it isn't sure.

Every step is judged the same way: the repo benchmark (G1) plus the 45 questions, by `compare.py`, with no drop on held-out.

### H1. A smarter model, picked fairly (no training)

- **Finish Task 9 first.** Qwen3 4B (on disk, 41/45) with thinking on and off, through `/deep`, on G1 and the questions. That picks the smart lane, and gives G1 its first real numbers on EduCore and WareFlow.
- **More candidates for `/deep`,** each with Eni-M's yes before downloading: Granite 4.1 8B, and Mellum2.1 12B-A2.5B if it fits 8 GB.
- **A C# importance matrix (a few hours, local).** Re-quantize the chosen models from their full-precision files with `llama-imatrix` computed on C# (Eni-M's repos plus .NET samples). Same size and speed, and the weights that matter for C# keep more precision. Score it against the stock Q4_K_M file. The repos stay on the laptop.
- **Q5 for the smart lane only,** if the RAM limit allows. It's slower, so `/deep` is the only place it might pay.

### H2. Give it the knowledge it lacks

- **API book (A4):** exact .NET signatures by name, put into the prompt, so invented APIs aren't written at all instead of only caught afterwards.
- **Repo map (B1):** Eni-M's types, members, routes and DI registrations, so it stops guessing about the project.
- **Law-book precision (A3):** fix the two known dev-set misses.

### H3. Work harder only where the work can be checked

- **Best of two, with a verifier:** in `/deep`, if the one repair round fails, sample one fresh answer and keep whichever compiles. Time is spent only after a failure the compiler has shown.
- **`/fix` (D1):** run the affected tests. Passing Eni-M's tests is the strongest check there is.
- Still out: sampling several answers every time, a model judging its own answer, open-ended agent loops.

### H4. Train it on Colab (last, after everything else)

Kept until A–H3 are done, so the training has the benchmark, the API book and the best base model to build on, and so there's a measured baseline to beat. The method is in `reports/Advanced training methods feasibility.md`.

1. **Data the compiler accepts.**
   - *Self-training:* the chosen model attempts many G1-style tasks from Eni-M's repos (never the benchmark's own tasks), and only answers that build and pass the tests are kept.
   - *Teacher:* Qwen2.5-Coder-14B (Apache 2.0) writes C# and ASP.NET Core questions, answers and code on Colab, and only what compiles is kept. No commercial API as teacher: their terms usually forbid training on the output, and the budget is $0.
2. **What it learns:** answering from the law-book passage and refusing when it doesn't cover the question (E2, with distractor passages), Jazari's edit format, and Eni-M's code style. Facts stay in the law book and API book.
3. **QLoRA on a free T4,** with about 5% general replay data so it doesn't forget, then merge, re-quantize with H1's C# importance matrix, and score.
4. **Keep it only if it beats the untrained model** on G1 and the questions, with no drop on held-out and no slower answers. A careless fine-tune often makes a small model worse.
5. **Rules:** private repo code may go to Colab (allowed in the original spec), employer code never. Training data and adapters stay out of git.

Realistic effort: one to two weeks of evenings, mostly waiting on Colab and measuring.
