# `/deep` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/deep <question>` answers with a smarter model, more context, a short plan, a compiler check and one repair round, while plain questions stay on the fast model, and it ships only if it measures clearly better.

**Architecture:** llama-server runs in router mode with one model loaded at a time, so the port stays up across a swap and the gateway picks the model per request. The gateway runs the deep pipeline as one queue item, sends stages over SSE and holds the text until it has been checked. Roslyn checks snippets in the gateway with no emit, so nothing is ever run. `/deep` on `/edit` also loads the project with MSBuildWorkspace, in the CLI, after asking.

**Tech Stack:** C#/.NET 10, ASP.NET Core, Roslyn 5.9.0 (already in the CLI), xUnit, Python 3.12 stdlib (`py -I`, `unittest`), llama.cpp b11982.

**Spec:** `docs/superpowers/specs/2026-11-04-deep-mode-design.md` (on `origin/docs/deep-mode-and-next-steps`; Task 0 brings it in). It takes three items from `2026-11-04-what-next.md` in the same branch: G1, A1 and A2. Every other item in that file is out of scope. So is B1: the design only uses the repo map "once B1 exists".

## Where the code changes the design

Read these first. Each is a place where following the spec's words alone would break something. Items marked **your call** are defaults you can overrule.

| # | The spec says | The code or data says | This plan does |
|---|---|---|---|
| 1 | The gateway stops one llama-server and starts another | The CLI starts llama-server; the gateway only knows a URL. While the port is down, a second `jazari` window sees "llama down" and starts its own server. | 2 | Up to two passages instead of one | `LawBook.cs` already allows 2 passages in both lanes, capped at 300 tokens, and skips the search entirely when `/read` context is present | Deep raises the cap to 600 tokens and searches beside `/read` files. The fast lane doesn't change |
| 3 | Clearly better by the McNemar rule | Stored runs, Qwen3 against Tiny: 6 gained, 2 lost, p = 0.29 (`tiny-cpu`); 4 gained, 2 lost, p = 0.69 (`tiny-regress`). **The spec's two open questions, as defaulted here:** 3 minutes stays a foreground ceiling with no background mode, and `/edit` and `/review` stay on the fast lane unless `/deep` is typed.

## Global Constraints

- Never run the real Jazari app, `jazari update` or the installer from Claude Desktop, and never judge the install through plain `AppData` paths. A temporary `llama-server` on port 8099 and a temporary gateway on port 5099 with its own data folder are allowed. Stop them when done. Install steps are checked by Eni-M in their own terminal.
- Build and test with `--disable-build-servers`.
- Keep code that touches the registry or writes executables out of Jazari and its tests: Smart App Control blocks those builds.
- Fast lane: typical ≤ 10 s, longest ≤ 45 s, score no worse than today. It must behave exactly as today when `/deep` is never used.
- `/deep`: typical ≤ 90 s, longest ≤ 3 min or a stage says why, working set ≤ 8 GB.
- Only one model is loaded at a time, unless Task 1 sends the design to its "keep both" branch.
- If `/deep` isn't clearly better than the fast lane, it doesn't ship.
- Think cap about 400 tokens. One repair round only. No sampling several answers, no model judging its own answer, no agent loops.
- Only Eni-M's own repos in G1, and never General-CRM or other employer code. Task files and results stay git-ignored and on this PC. Web research never quotes private code.
- Downloading a candidate model needs Eni-M's yes first (file name, source, size). Budget is $0.
- Commit only on the task's branch. Don't push or merge to `main` without being asked.

## Review Focus

1. **Ctrl+C during a model load or a deep answer.** The next question still works, on the right model, with no half-loaded state. Pinned in Task 4.
2. **The smart model is missing or fails to load (out of memory, a bad file).** The user gets a clear message, the fast model comes back, and plain questions keep working. Pinned in Task 4.
3. **A second window, an IDE or a background note update asks during a deep answer or the hold.** It waits its turn or runs on the loaded model, and never starts a second model. Pinned in Task 4.
4. **Correct code that uses EF Core or another package.** It's never called wrong. Pinned in Task 3.
5. **`/deep` alone with nothing to ask again, after an error, or after a restored conversation.** It finds the last question in the saved history, or says there's nothing to retry. Pinned in Task 6.
